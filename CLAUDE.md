# Ductus: engineering guide

Code-first healthcare integration engine: Rust runtime, embedded V8 for TypeScript interface code, PostgreSQL as store and queue. Open core (Apache-2.0). This repo is the open core; commercial features and planning live in the private `ductus-enterprise` repo (`planning/` has the vision, `decisions.md`, `roadmap.md`, `STATUS.md`).

**Read first:** `docs/architecture.md` (how it works + invariants), then `../ductus-enterprise/planning/STATUS.md` (where we are, what's next).

## Non-negotiables

- The invariants in `docs/architecture.md` (persist before ACK, at-least-once, one owner per lane, expand-only migrations, no credentials in code). If a change seems to need breaking one, stop and discuss.
- **Every change ships with tests.** Unit tests next to the code; DB tests in `crates/ductus-store/tests`; script/SDK tests in `crates/ductus-script/tests` and `sdk/tests/*.test.ts` (run inside the real engine); end-to-end in `scripts/demo-*.sh` (each ends with PASS/FAIL and runs in CI); the web UI's in `ui/src/**/*.test.ts` (Vitest) and `ui/e2e` (Playwright in a real browser against a real engine, run by `scripts/demo-ui.sh`).
- **Before every commit:** `scripts/dev/check.sh` must end with `ALL CHECKS PASSED` (the web UI's format/types/lint/tests/build, fmt, build incl. the binary, the API document the UI is typed from, clippy `-D warnings`, all tests). For runtime or UI changes also run `scripts/dev/demos.sh`.
- Commits: `git commit -s` (DCO), message explains what and why, ends with the Co-Authored-By trailer. Push to `main` (solo project, CI on every push).
- **Nuances get documented, not hidden.** Any behaviour that could surprise an interface developer (limits, failure semantics, things that run twice) goes into `docs/nuances.md` in the same commit, with what/why/what to do and a level (1 foundations … 5 expert; these become the certification tracks).
- Keep `../ductus-enterprise/planning/` current: decisions in `decisions.md`, progress in `roadmap.md` and `STATUS.md`.

## Code conventions

- Rust 2024, `rustfmt.toml` (120 cols). Errors: `anyhow` with `.context(...)` that says what was being done. Comments explain *why*; doc comments on public items.
- User-facing messages are plain and actionable ("message has no PID segment; add it first with msg.add("PID")").
- Config: `serde(deny_unknown_fields)`; validate in `InterfaceConfig::validate`; new options get defaults that are safe.
- SDK (TypeScript): HL7 numbering is 1-based; missing reads as `""`; never throw on reads. Keep `sdk/src/typegen.ts` declarations in sync with the SDK's public API (that's what VS Code shows).

## Gotchas already solved (don't rediscover)

- **deno_core 0.412**: scopes via `deno_core::scope!(scope, &mut runtime)`; try/catch via `v8::tc_scope!(let scope, scope)`. `deno_error` must be pinned `=0.7.1`. Ops: `#[op2]` + `#[string]` for `Option<String>` returns, `#[serde]` for JSON. Extensions via `deno_core::extension!` with `esm = [dir "src", "file.js"]`.
- `call_with_args`/`resolve` return futures that **don't borrow the runtime**; drive the event loop separately (`poll_event_loop`). That's how concurrent async transforms work.
- Module specifiers must be canonical paths (`file_url` canonicalizes); `..` in paths broke module identity once.
- TypeScript transpile removes unused imports: tests that check import behavior must *use* the import.
- **A new migration file needs a rebuild**: `crates/ductus-store/build.rs` makes cargo watch `migrations/` (without it, `sqlx::migrate!` kept the old set and migration 0007 silently didn't apply). Describe new tables/columns in `docs/schema.md`.
- **sqlx 0.9**: dynamic SQL needs `sqlx::AssertSqlSafe(...)`; migrations must never be edited after they're applied (add a new one).
- `serde_yaml_ng`: enums in YAML maps need `with = "serde_yaml_ng::with::singleton_map"` (or `_recursive`).
- `${...}` in YAML flow style breaks parsing: always load project YAML through `ductus_core::env::parse_yaml` (protects references first).
- chacha20poly1305 0.11 changed its RNG API: we use `getrandom` directly.
- quick-xml's API churns: XML key extraction uses our own small reader (`runtime/src/keys.rs`), deliberately matching the SDK's `parseXml` rules.
- `cargo test` doesn't rebuild the `ductus` binary: `check.sh` builds it explicitly (a stale binary once hid a migration bug).
- TypeScript 6 is vendored (`vendor/typescript`) for type checking because TS 7 is a native Go binary that can't run in V8.
- Calling `wsl` from the Git Bash tool mangles `/mnt/...` paths: prefix `MSYS_NO_PATHCONV=1` (or use PowerShell). Don't put the text "ductus run" in a wrapper command line: `demos.sh` does `pkill -f 'ductus (run|...)'` and kills the wrapper.
- In scripts, never `cmd | grep -q x` under `set -o pipefail`: grep exits at the first match, `cmd` gets EPIPE, and the pipeline "fails" (bit the `ductus status` waits once its output grew). Use `grep x >/dev/null` (and `sed -n 1p`, not `head -1`). Report commands now end quietly on SIGPIPE (`quiet_on_closed_pipe` in main.rs), but under pipefail that's still exit 141; never give `run`/`gen`/`sink` the default SIGPIPE (a closed socket would kill the engine). And start the engine directly (`"$BIN" run &`), not in a subshell (`(cd p && "$BIN" run) &`): a background subshell in a non-interactive script ignores SIGINT, so `kill -INT` never reaches the engine and `wait` hangs.
- Comparing against an older version: build it from a `git worktree` into its own target dir (`CARGO_TARGET_DIR=~/target-base`). Versions before 0.6.1 read `ops.js` from their source folder at run time, so keep that worktree until you're done.
- **deno_core reads `extension!` `esm = [...]` files from the build machine's disk at every isolate start** (by absolute path; only a startup snapshot embeds them): an installed binary panicked "Failed to initialize a JsRuntime: No such file or directory". `ops::extension()` replaces the list with `ascii_str_include!` (`the_extension_reads_nothing_from_disk`). Any new JS in an extension goes through it. Packaging tests (`demo-docker.sh`, `demo-packages.sh`) run the binary away from the source tree, which is what catches this.
- Demo waits must re-evaluate their condition: `wait_for 15 '[ "$(count $OUT)" -ge 3 ]'` (quoted, `eval`ed). Passing `"$(...)"` unquoted freezes the value and the wait silently runs to its timeout.
- Logs are plain text when stdout isn't a terminal (`with_ansi`), so demos can grep fields like `started interfaces=`.
- SFTP tests use a throwaway user-level `sshd` (openssh-server installed in WSL; its system service is disabled) on 127.0.0.1:2222; see `scripts/demo-files.sh`. Clean up child processes with a `trap` whose commands each end in `|| true` (`set -e` applies inside traps).
- CI "could not find native static library `rusty_v8`" on Build (Lint passes) = a stale rust-cache restored as a partial match. Fix: `gh cache delete --all`, then `gh run rerun <id>`. Always check the run after pushing.
- **WSL stops the distro** (Docker and containers with it, exit 255, nothing in the logs) once no `wsl` command has run for a while. Not a SQL Server crash. The local SQL Server container (`scripts/dev/sqlserver.sh`, Docker Engine installed in WSL) has `--restart unless-stopped`; check.sh starts it and waits for a real login before the tests. SQL Server tests use `DUCTUS_TEST_SQLSERVER=user:password@host:port`.
- tiberius 0.13 (bb8-tiberius is stuck on 0.12, so `mssql.rs` has its own pool). SQL Server 2025 image not tried since the WSL finding; tests and CI use 2022.
- **Runaway guard (`ductus-script/src/guard.rs`)**: terminate only from inside an `IsolateHandle::request_interrupt` callback (runs on the isolate's thread; check the call generation first), never `terminate_execution` from the watchdog thread (a finished call's successor would be killed). Reading the stack there needs a context: the main context is kept in an isolate slot (`MainContext`) and entered with `v8::scope_with_context!`. After termination, `cancel_terminate_execution` (deno_core re-arms termination in `exception_to_err`). A termination during the event loop **drops all queued microtasks**, so every in-flight async transform on that isolate hangs: fail them all (worker's `interrupted` watch). `Isolate::settle` stringifies errors: use `drive` + `output` where a typed error (`Runaway`) must survive.
- **Never lock `messages` and `deliveries` (the parent tables) together in one transaction with DDL** (creating, dropping or attaching partitions): ingest locks messages→deliveries, settling deliveries→messages, so any transaction holding both in DDL deadlocks with one of them. Partition maintenance runs one table per statement (migration 0006) with `lock_timeout` (a waiting DDL queues every later insert behind it); test cleanups too. Store tests that hold long locks on purpose take `LONG_LOCKS` (store tests), or one's read makes another's urgent maintenance wait and its inserts queue. **New database work goes into the stress test** `everything_at_once_without_lock_errors` (store tests). Postgres's "deadlock detected at line 1133" is a line in its own source, not ours.
- **Sockets belong to the runtime that opened them.** The sqlx pool is shared with intake: worker threads must run store calls on the main runtime (`Worker::db`), or a busy V8 thread delays other interfaces' ACKs.
- tracing's plain log format puts the message before the fields: grep `interface stopped.*interface=x`, not the other way round.
- **The package of `crates/ductus-cli` is named `ductus`**: `cargo test -p ductus --test cli`, not `-p ductus-cli`.
- **Type checker API (`check.js`)**: to know whether a call is the SDK's `db`/`api`, resolve the callee with `checker.getSymbolAtLocation` + `getAliasedSymbol` and check its declaration sits in `declare module "@ductus/sdk"`; don't match names (a local `db` would count, an alias wouldn't). `analyze(..., false)` skips `getPreEmitDiagnostics`, which is the slow part.
- **Timing durable commits**: a transaction that only takes an xid (`SELECT txid_current()`) writes no WAL of its own, so its commit doesn't wait for the flush (0.28 ms vs 3.06 ms measured on the same disk). `ductus doctor` uses `pg_logical_emit_message(true, ...)` (WAL, no table). The TLS verifier (`rustls_platform_verifier`) logs every failed verification at ERROR: doctor's log filter turns it off.
- **REST API routes** go through `utoipa_axum::routes!` in each `api/*.rs` `routes()` (that's what puts them in the OpenAPI document); a handler's `#[utoipa::path]` path is relative to `/api/v1`. Two handlers with one path and different methods go in one `routes!(a, b)`. A plain helper with the same name as a handler breaks the macro (it picks the wrong item).
- **A statement reads as of when it started, even after waiting for a lock.** A settle that read deliveries and then waited for a message row read them as they were before a resend made one pending again (it marked the message quarantined; reconcile would then undo the resend). So settle locks in one statement and reads in the next. Any new write that moves a delivery *backwards* (final → pending) must hold the message's lock, and readers that decide from deliveries must lock first.
- **Statements that lock many rows lock them in id order** (`ORDER BY id FOR UPDATE` in a CTE, as `Store::settle` does), never in whatever order the plan visits them: the plan changes with the statistics, and two writers over overlapping sets then deadlock. The routing demo hit it once in 11 runs; no test could force the plan, so it's a rule, not a test. And **a flush may be retried after its commit** (a later statement failed): writes must be guarded (`WHERE status = 0 RETURNING`), or a route would store its messages twice (it did, before the guard).
- **Store tests that make partitions often** (the stress test) also take `LONG_LOCKS`: while another test holds its long read on purpose, each partition DDL waits up to 2 s and the inserts queue behind it (seen as "too little traffic").
- **Retention tiers (migration 0010):** `messages`/`deliveries` are LIST-partitioned by `tier`, then RANGE by `received_at` (`messages_t21_20261005`; tiers in days: 7 daily, 21 and 49 weekly). **Never hold two tier tables in one transaction for DDL**: queries lock every tier in creation order (7d first), so creating or dropping partitions of two tiers at once deadlocks (the stress test caught it, in a test cleanup too). One table and tier per statement or transaction.
- **Partition bounds are UTC midnights** (`ductus_create_tier_partition`): a date in `FOR VALUES` is read in the session's time zone, sqlx sessions are UTC and psql's aren't, and the two made overlapping partitions. Scripts that touch dates run psql with `PGTZ=UTC`.
- **Statements that look messages up by `(id, received_at)` arrays carry the batch's time range** (`span` in `Store::settle`/`update_deliveries`), and the queue read looks messages up with `LATERAL ... LIMIT 1`: with ~100 partitions (the first five-tier layout) Postgres priced per-message lookups above scanning every partition, and hashed the whole table (settle 84 ms vs 1.8 ms; one destination drained at 429/s). Look at the plan of any new statement joining these tables (`EXPLAIN ANALYZE` with near-steady-state partitions: a fresh database has only ~15 and hides it).
- **`ORDER BY x LIMIT n` needs an index that yields x order after the equality columns** (`deliveries_queue (destination_id, message_id, partition_key)`, migration 0011). With the queue index lane-first, Postgres walked each partition's primary key in id order past every delivered row (300 ms a read). It only shows with many *finished* rows ahead of the pending ones: benchmark statements that read the queue on a database with a day of delivered traffic, never a fresh one. `the_queue_read_uses_the_queue_index` checks the cached (generic) plan.
- **C: is nearly full and WSL's disk image lives there** (grows, never shrinks by itself): a benchmark that loaded 1M rows filled it and crashed WSL with I/O errors. Check `Get-PSDrive C` before loading big data; drop benchmark databases afterwards.
- **A row moved to another partition can't be re-checked**: a statement that saw it before the move fails with 40001 ("already moved to another partition"). Retention changes move finished messages and the held area (6e) moves *pending* ones while workers update them, so **every statement that updates messages or deliveries runs through `retrying`** (store `lib.rs`: 40001 and 40P01, up to 5 times; a transaction is retried whole, as `finish_routed`). Never filter those updates by `tier`: a retried statement must find the row where it is now. The stress test fails without the retry (checked by turning it off).
- **Held area tables (tier 0, `messages_held_YYYYMM`) are made on first use**, one table per transaction, and a held month only drops once it's over: store tests that move rows (`hold_step` on today's partition in the stress test) move other running tests' rows too, and dropping the current month would take their finished rows with it.
- **Expired partitions go with `DETACH PARTITION CONCURRENTLY`** (blocks no insert or read; can't run in a transaction block; an interrupted one is `FINALIZE`d next run), then `DROP`. Store tests that create old partitions and call `drop_expired` take `LONG_LOCKS` (it drops every expired partition in the database).
