# Ductus: engineering guide

Code-first healthcare integration engine: Rust runtime, embedded V8 for TypeScript interface code, PostgreSQL as store and queue. Open core (Apache-2.0). This repo is the open core; commercial features and planning live in the private `ductus-enterprise` repo (`planning/` has the vision, `decisions.md`, `roadmap.md`, `STATUS.md`).

**Read first:** `docs/architecture.md` (how it works + invariants), then `../ductus-enterprise/planning/STATUS.md` (where we are, what's next).

## Non-negotiables

- The invariants in `docs/architecture.md` (persist before ACK, at-least-once, one owner per lane and one engine per interface, expand-only migrations, no credentials in code). If a change seems to need breaking one, stop and discuss.
- **Every change ships with tests.** Unit tests next to the code; DB tests in `crates/ductus-store/tests`; script/SDK tests in `crates/ductus-script/tests` and `sdk/tests/*.test.ts` (run inside the real engine); end-to-end in `scripts/demo-*.sh` (each ends with PASS/FAIL and runs in CI); the web UI's in `ui/src/**/*.test.ts` (Vitest) and `ui/e2e` (Playwright in a real browser against a real engine, run by `scripts/demo-ui.sh`).
- **Before every commit:** `scripts/dev/check.sh` must end with `ALL CHECKS PASSED` (the web UI's format/types/lint/tests/build, fmt, build incl. the binary, the API document the UI is typed from, clippy `-D warnings`, all tests). For runtime or UI changes also run `scripts/dev/demos.sh`.
- Commits: `git commit -s` (DCO), message explains what and why, ends with the Co-Authored-By trailer. Push to `main` (solo project, CI on every push).
- **Nuances get documented, not hidden.** Any behaviour that could surprise an interface developer (limits, failure semantics, things that run twice) goes into `docs/nuances.md` in the same commit, with what/why/what to do and a level (1 foundations … 5 expert; these become the certification tracks).
- Keep `../ductus-enterprise/planning/` current: decisions in `decisions.md`, progress in `roadmap.md` and `STATUS.md`.

## Environment

- Windows host; **build and run everything in WSL2 Ubuntu** (`wsl -d Ubuntu`). Repo at `/mnt/d/Projects/integration_engine/ductus`. `CARGO_TARGET_DIR=$HOME/target` (building on `/mnt/d` is slow); binary at `~/target/release/ductus`.
- Postgres 18 in WSL. The binary has **no default database**: scripts get theirs from `scripts/dev/db.sh` (sourced by check.sh, demos.sh and every demo; CI sets `DUCTUS_DATABASE_URL` first; a personal login goes in `scripts/dev/db.local.sh`, which is not in Git: on this machine it holds `todd:ductus@localhost/ductus_dev`); at a prompt, export it yourself. `ductus dev` needs none (its own Postgres).
- From PowerShell, multi-line or `$`-heavy shell commands get mangled: write a script file and run `wsl -d Ubuntu -- bash /mnt/c/...script.sh`.
- `/tmp` in WSL is tmpfs: don't benchmark disk there.
- **WSL's disk lives on D:** (`D:\WSL\UbuntuTest\ext4.vhdx`, distro name `Ubuntu`, since 2026-10-10; C: was full). A synchronous 8 KB write takes ~5 ms there (NVMe C: was ~2.5 ms): benchmark numbers in architecture.md before 0.6.1 were measured on C:. Never `wsl --manage --move` it again: the moved 61 GB image did ~400 ms per synchronous write (commits took a second) while a fresh image on the same drive did 6 ms; export + import made a fresh one. Docker in WSL needs Ubuntu's `docker-buildx` and `docker-compose-v2` packages (installed). **The image only grows**: space freed inside WSL stays taken on D: (2026-10-25: 36 GB used inside, 48 GB image). check.sh ends with the build outputs' size and says when to `cargo clean` (over 30 GB). To give space back (Todd, as administrator, now and then): `wsl --shutdown`, then `diskpart` → `select vdisk file="D:\WSL\UbuntuTest\ext4.vhdx"` → `attach vdisk readonly` → `compact vdisk` → `detach vdisk`. Not WSL's sparse-disk setting (`--set-sparse`): after the `--move` trouble, not worth the risk on this image.
- Bash: `in` is a keyword (a helper function named `in` is a syntax error), and `tee /dev/stderr` fails in non-interactive WSL shells: write progress with `>&2`.

## Code conventions

- Rust 2024, `rustfmt.toml` (120 cols). Errors: `anyhow` with `.context(...)` that says what was being done. Comments explain *why*; doc comments on public items.
- User-facing messages are plain and actionable ("message has no PID segment; add it first with msg.add("PID")").
- Config: `serde(deny_unknown_fields)`; validate in `InterfaceConfig::validate`; new options get defaults that are safe.
- SDK (TypeScript): HL7 numbering is 1-based; missing reads as `""`; never throw on reads. Keep `sdk/src/typegen.ts` declarations in sync with the SDK's public API (that's what VS Code shows).

## Gotchas already solved (don't rediscover)

- **deno_core 0.412**: scopes via `deno_core::scope!(scope, &mut runtime)`; try/catch via `v8::tc_scope!(let scope, scope)`. `deno_error` must be pinned `=0.7.1`. Ops: `#[op2]` + `#[string]` for `Option<String>` returns, `#[serde]` for JSON. Extensions via `deno_core::extension!` with `esm = [dir "src", "file.js"]`.
- `call_with_args`/`resolve` return futures that **don't borrow the runtime**; drive the event loop separately (`poll_event_loop`). That's how concurrent async transforms work.
- Module specifiers must be canonical paths (`file_url` canonicalizes); `..` in paths broke module identity once.
- TypeScript transpile removes unused imports: tests that check import behavior must *use* the import.
- **A new migration file needs a rebuild**: `crates/ductus-store/build.rs` makes cargo watch `migrations/` (without it, `sqlx::migrate!` kept the old set and migration 0007 silently didn't apply). Describe new tables/columns in `docs/schema.md`.
- **sqlx 0.9**: dynamic SQL needs `sqlx::AssertSqlSafe(...)`; migrations must never be edited after they're applied (add a new one).
- `serde_yaml_ng`: enums in YAML maps need `with = "serde_yaml_ng::with::singleton_map"` (or `_recursive`).
- `${...}` in YAML flow style breaks parsing: always load project YAML through `ductus_core::env::parse_yaml` (protects references first).
- chacha20poly1305 0.11 changed its RNG API: we use `getrandom` directly.
- quick-xml's API churns: XML key extraction uses our own small reader (`runtime/src/keys.rs`), deliberately matching the SDK's `parseXml` rules.
- `cargo test` doesn't rebuild the `ductus` binary: `check.sh` builds it explicitly (a stale binary once hid a migration bug).
- TypeScript 6 is vendored (`vendor/typescript`) for type checking because TS 7 is a native Go binary that can't run in V8.
- Calling `wsl` from the Git Bash tool mangles `/mnt/...` paths: prefix `MSYS_NO_PATHCONV=1` (or use PowerShell). Don't put the text "ductus run" in a wrapper command line: `demos.sh` does `pkill -f 'ductus (run|...)'` and kills the wrapper.
- In scripts, never `cmd | grep -q x` under `set -o pipefail`: grep exits at the first match, `cmd` gets EPIPE, and the pipeline "fails" (bit the `ductus status` waits once its output grew). Use `grep x >/dev/null` (and `sed -n 1p`, not `head -1`). Report commands now end quietly on SIGPIPE (`quiet_on_closed_pipe` in main.rs), but under pipefail that's still exit 141; never give `run`/`gen`/`sink` the default SIGPIPE (a closed socket would kill the engine). And start the engine directly (`"$BIN" run &`), not in a subshell (`(cd p && "$BIN" run) &`): a background subshell in a non-interactive script ignores SIGINT, so `kill -INT` never reaches the engine and `wait` hangs.
- Comparing against an older version: build it from a `git worktree` into its own target dir (`CARGO_TARGET_DIR=~/target-base`). Versions before 0.6.1 read `ops.js` from their source folder at run time, so keep that worktree until you're done. **Never build a worktree into `~/target`**: our build scripts have their folder baked in (`env!("CARGO_MANIFEST_DIR")`) and cargo reuses them by fingerprint, so after the worktree is deleted check.sh's test stage panicked ("vendor/typescript/lib missing", "the web UI isn't built") from a probe's `~/wt-sspi`. Fix: `cargo clean --release -p ductus -p ductus-core -p ductus-hl7 -p ductus-mllp -p ductus-script -p ductus-store -p ductus-runtime`.
- **deno_core reads `extension!` `esm = [...]` files from the build machine's disk at every isolate start** (by absolute path; only a startup snapshot embeds them): an installed binary panicked "Failed to initialize a JsRuntime: No such file or directory". `ops::extension()` replaces the list with `ascii_str_include!` (`the_extension_reads_nothing_from_disk`). Any new JS in an extension goes through it. Packaging tests (`demo-docker.sh`, `demo-packages.sh`) run the binary away from the source tree, which is what catches this.
- Demo waits must re-evaluate their condition: `wait_for 15 '[ "$(count $OUT)" -ge 3 ]'` (quoted, `eval`ed). Passing `"$(...)"` unquoted freezes the value and the wait silently runs to its timeout.
- Logs are plain text when stdout isn't a terminal (`with_ansi`), so demos can grep fields like `started interfaces=`.
- SFTP tests use a throwaway user-level `sshd` (openssh-server installed in WSL; its system service is disabled) on 127.0.0.1:2222; see `scripts/demo-files.sh`. Clean up child processes with a `trap` whose commands each end in `|| true` (`set -e` applies inside traps).
- CI "could not find native static library `rusty_v8`" on Build (Lint passes) = a stale rust-cache restored as a partial match. Fix: `gh cache delete --all`, then `gh run rerun <id>`. Always check the run after pushing.
- **WSL stops the distro** (Docker and containers with it, exit 255, nothing in the logs) once no `wsl` command has run for a while. Not a SQL Server crash. The local SQL Server container (`scripts/dev/sqlserver.sh`, Docker Engine installed in WSL) has `--restart unless-stopped`; check.sh starts it and waits for a real login before the tests. SQL Server tests use `DUCTUS_TEST_SQLSERVER=user:password@host:port`.
- tiberius 0.13 (bb8-tiberius is stuck on 0.12, so `mssql.rs` has its own pool). Tests and CI use **SQL Server 2025** since 0.6.4.3 (2022 on Linux refuses TDS 8 strict whatever it's given; `MSSQL_IMAGE` picks another).
- **TLS to SQL Server (0.6.4.3):** the test SQL Server (`scripts/dev/sqlserver.sh`, also in CI, not as a service: a service can't be given files before it starts) presents a certificate from a test CA (mssql-conf via a mounted `mssql.conf`; hostname `sql1.ductus.test`: SQL Server accepts strict only with a certificate for its own host name; its folder is `DUCTUS_TEST_SQLSERVER_TLS`, which check.sh and CI set with `DUCTUS_TEST_SQLSERVER`). A container made before this (no `ductus.setup` label for the image) is made again. sqlcmd inside the container hangs at login when TLS 1.3 is the only protocol allowed: wait on the log, not sqlcmd, when experimenting. tiberius flattens TLS errors into `Error::Tls(String)` with advice in its own API's terms: `mssql::refusal` words them from rustls's rendered names (guarded by tests against the real server: if a tiberius bump changes the text, those fail). tiberius panics with both `trust_cert` and a CA (resources.yaml refuses the pair) and warns at every connection with `trust_cert` (the log filters set `tiberius=error`; the start warns once). Doctor's PRELOGIN (`PRELOGIN_REQUEST`, `Prelogin`: TLS records framed at each flush, as tiberius does) gives TLS 1.2 always; strict is plain TLS with ALPN `tds/8.0`.
- **Runaway guard (`ductus-script/src/guard.rs`)**: terminate only from inside an `IsolateHandle::request_interrupt` callback (runs on the isolate's thread; check the call generation first), never `terminate_execution` from the watchdog thread (a finished call's successor would be killed). Reading the stack there needs a context: the main context is kept in an isolate slot (`MainContext`) and entered with `v8::scope_with_context!`. After termination, `cancel_terminate_execution` (deno_core re-arms termination in `exception_to_err`). A termination during the event loop **drops all queued microtasks**, so every in-flight async transform on that isolate hangs: fail them all (worker's `interrupted` watch). `Isolate::settle` stringifies errors: use `drive` + `output` where a typed error (`Runaway`) must survive.
- **Never lock `messages` and `deliveries` (the parent tables) together in one transaction with DDL** (creating, dropping or attaching partitions): ingest locks messages→deliveries, settling deliveries→messages, so any transaction holding both in DDL deadlocks with one of them. Partition maintenance runs one table per statement (migration 0006) with `lock_timeout` (a waiting DDL queues every later insert behind it); test cleanups too. Store tests that hold long locks on purpose take `LONG_LOCKS` (store tests), or one's read makes another's urgent maintenance wait and its inserts queue. **New database work goes into the stress test** `everything_at_once_without_lock_errors` (store tests). Postgres's "deadlock detected at line 1133" is a line in its own source, not ours.
- **Sockets belong to the runtime that opened them.** The sqlx pool is shared with intake: worker threads must run store calls on the main runtime (`Worker::db`), or a busy V8 thread delays other interfaces' ACKs.
- tracing's plain log format puts the message before the fields: grep `interface stopped.*interface=x`, not the other way round.
- **The package of `crates/ductus-cli` is named `ductus`**: `cargo test -p ductus --test cli`, not `-p ductus-cli`.
- **Type checker API (`check.js`)**: to know whether a call is the SDK's `db`/`api`, resolve the callee with `checker.getSymbolAtLocation` + `getAliasedSymbol` and check its declaration sits in `declare module "@ductus/sdk"`; don't match names (a local `db` would count, an alias wouldn't). `analyze(..., false)` skips `getPreEmitDiagnostics`, which is the slow part.
- **Timing durable commits**: a transaction that only takes an xid (`SELECT txid_current()`) writes no WAL of its own, so its commit doesn't wait for the flush (0.28 ms vs 3.06 ms measured on the same disk). `ductus doctor` uses `pg_logical_emit_message(true, ...)` (WAL, no table). The TLS verifier (`rustls_platform_verifier`) logs every failed verification at ERROR: doctor's log filter turns it off.
- **REST API routes** go through `utoipa_axum::routes!` in each `api/*.rs` `routes()` (that's what puts them in the OpenAPI document); a handler's `#[utoipa::path]` path is relative to `/api/v1`. Two handlers with one path and different methods go in one `routes!(a, b)`. A plain helper with the same name as a handler breaks the macro (it picks the wrong item).
- **A statement reads as of when it started, even after waiting for a lock.** A settle that read deliveries and then waited for a message row read them as they were before a resend made one pending again (it marked the message quarantined; reconcile would then undo the resend). So settle locks in one statement and reads in the next. Any new write that moves a delivery *backwards* (final → pending) must hold the message's lock, and readers that decide from deliveries must lock first.
- **Statements that lock many rows lock them in id order** (`ORDER BY id FOR UPDATE` in a CTE, as `Store::settle` does), never in whatever order the plan visits them: the plan changes with the statistics, and two writers over overlapping sets then deadlock. The routing demo hit it once in 11 runs; no test could force the plan, so it's a rule, not a test. And **a flush may be retried after its commit** (a later statement failed): writes must be guarded (`WHERE status = 0 RETURNING`), or a route would store its messages twice (it did, before the guard).
- **Store tests that make partitions often** (the stress test) also take `LONG_LOCKS`: while another test holds its long read on purpose, each partition DDL waits up to 2 s and the inserts queue behind it (seen as "too little traffic").
- **Retention tiers (migration 0010):** `messages`/`deliveries` are LIST-partitioned by `tier`, then RANGE by `received_at` (`messages_t21_20261005`; tiers in days: 7 daily, 21 and 49 weekly). **Never hold two tier tables in one transaction for DDL**: queries lock every tier in creation order (7d first), so creating or dropping partitions of two tiers at once deadlocks (the stress test caught it, in a test cleanup too). One table and tier per statement or transaction.
- **Partition bounds are UTC midnights** (`ductus_create_tier_partition`): a date in `FOR VALUES` is read in the session's time zone, sqlx sessions are UTC and psql's aren't, and the two made overlapping partitions. Scripts that touch dates run psql with `PGTZ=UTC`.
- **Statements that look messages up by `(id, received_at)` arrays carry the batch's time range** (`span` in `Store::settle`/`update_deliveries`), and the queue read looks messages up with `LATERAL ... LIMIT 1`: with ~100 partitions (the first five-tier layout) Postgres priced per-message lookups above scanning every partition, and hashed the whole table (settle 84 ms vs 1.8 ms; one destination drained at 429/s). Look at the plan of any new statement joining these tables (`EXPLAIN ANALYZE` with near-steady-state partitions: a fresh database has only ~15 and hides it).
- **`ORDER BY x LIMIT n` needs an index that yields x order after the equality columns** (`deliveries_queue (destination_id, message_id, partition_key)`, migration 0011). With the queue index lane-first, Postgres walked each partition's primary key in id order past every delivered row (300 ms a read). It only shows with many *finished* rows ahead of the pending ones: benchmark statements that read the queue on a database with a day of delivered traffic, never a fresh one. `the_queue_read_uses_the_queue_index` checks the cached (generic) plan.
- **C: is nearly full and WSL's disk image lives there** (grows, never shrinks by itself): a benchmark that loaded 1M rows filled it and crashed WSL with I/O errors. Check `Get-PSDrive C` before loading big data; drop benchmark databases afterwards.
- **A row moved to another partition can't be re-checked**: a statement that saw it before the move fails with 40001 ("already moved to another partition"). Retention changes move finished messages and the held area (6e) moves *pending* ones while workers update them, so **every statement that updates messages or deliveries runs through `retrying`** (store `lib.rs`: 40001 and 40P01, up to 5 times; a transaction is retried whole, as `finish_routed`). Never filter those updates by `tier`: a retried statement must find the row where it is now. The stress test fails without the retry (checked by turning it off).
- **Held area tables (tier 0, `messages_held_YYYYMM`) are made on first use**, one table per transaction, and a held month only drops once it's over: store tests that move rows (`hold_step` on today's partition in the stress test) move other running tests' rows too, and dropping the current month would take their finished rows with it.
- **Expired partitions go with `DETACH PARTITION CONCURRENTLY`** (blocks no insert or read; can't run in a transaction block; an interrupted one is `FINALIZE`d next run), then `DROP`. Store tests that create old partitions and call `drop_expired` take `LONG_LOCKS` (it drops every expired partition in the database).
- Python on Windows writes CRLF in text mode: pass `newline='\n'` when editing repo files from a script.
- russh 0.64: `client::Handler::check_server_key(&PublicKeyOrCertificate)`; fingerprints via `key.fingerprint(HashAlg::Sha256)` print like `ssh-keygen -lf`. SFTP `rename` won't overwrite: remove the target first.
- **utoipa `IntoParams` structs need `#[into_params(parameter_in = Query)]`**, or the document publishes their fields as *path* parameters (the message browser's `status`/`before`/`limit` were, until the UI's generated types caught it). `the_document_has_path_parameters_only_where_the_path_has_them` guards it.
- **`ductus dev` (dev.rs)** uses zonky's Postgres binaries (Maven Central, `postgresql_embedded` feature `zonky`), not theseus-rs's: those link the host's `libxml2.so.2`, which Ubuntu 26.04 doesn't have (it ships `.so.16`), so Postgres wouldn't even start. Pinned to 18.6.0 (`VERSION`). The crate's TLS is rustls (aws-lc, like the rest): no OpenSSL; it added 2.5 MB to a 127 MB binary. `File::try_lock` on `.ductus/dev.lock` is the "already running" check (the OS frees it however the process ends); a `postmaster.pid` left by a killed engine means a Postgres still running: `pg_ctl stop` first. `PostgreSQL::is_running` only checks that the pid file exists.
- **Windows (0.6.1):** `cargo build --release -p ductus` works natively (MSVC; VS 2019 Build Tools are enough; Rust 1.99). **Keep `CARGO_HOME` and `CARGO_TARGET_DIR` on one drive** (here both on D:): rusty_v8's build.rs makes a directory symlink otherwise, which needs Developer Mode or an elevated shell ("Failed to create symlink"). From PowerShell: `$env:CARGO_HOME="D:\cargo-home"; $env:CARGO_TARGET_DIR="D:\target-win"`; the binary and the MSI (`packaging/windows/build.ps1`, WiX 5 via `dotnet tool`) are in `D:\target-win`. `cargo` isn't on the Git Bash PATH. Installing the MSI needs an elevated shell (UAC): `scripts/demo-windows.ps1`, started with `Start-Process powershell -Verb RunAs`, needs a database: `ductus dev --database-only` prints one. The service code is `ductus-cli/src/service.rs` (`windows-service`); the engine takes `EngineOptions.stop_request` (the service manager's Stop) and `on_started` (Running is reported then). `--env-file` (`envfile.rs`) is read before clap, so `env = ...` options see it. `pg_ctl start -w` from a PowerShell tool call hangs the call (the server keeps its stdout): redirect or use `ductus dev`.
- **WSL's VM gets killed under memory pressure** (commit charge, not RAM): this machine has a 2-4 GB fixed pagefile, Edge holds ~18 GB, and a long `check.sh` died mid-run three times ("wsl.exe" exit -1073741571 / 253, `/tmp` emptied, Application Error events for wsl.exe, "low virtual memory condition" naming vmmemWSL in the System log). Work around it: `wsl --shutdown` first, `CARGO_BUILD_JOBS=4`, run the test stage per crate (`cargo test --release -p <crate>`); detached `nohup` jobs die with the VM (only an attached `wsl` command counts as activity). The kill can leave a truncated test binary (`Exec format error` in the CLI tests): delete `~/target/release/deps/ductus-*` and rebuild. A real fix is Todd's call (system-managed pagefile, or `memory=` in `.wslconfig`).
- **`[skip ci]` in the HEAD commit of a push skips CI for every commit in that push**, including an earlier code commit: a docs-only commit on top of a code commit must not carry it. Start a run by hand with `gh workflow run ci.yml --ref main`. The `windows` job's cold build takes ~35 min (the rust cache is kept on failure); a "Data limit exceeded" pull error in "Initialize containers" is the registry, not the code (`gh run rerun <id> --failed`). Since 0.6.5.1 the `test` job's Postgres is `ductus dev --database-only` (started after Build; its binaries cached by `actions/cache`), so every push runs the suite on what `dev` ships; demos get the login, host and port from the URL (`PGUSER_`, `PGPASS_`, `PGHOST_`, `PGPORT_`, `PGDATABASE_` in `scripts/dev/db.sh`; never hardcode `localhost`/5432 in a demo's resources.yaml). Our mirrored image `ghcr.io/thorst/ductus-ci-postgres:18` (public; made by `mirror.yml` monthly or `gh workflow run mirror.yml`) stays for `demo-packages.sh` (`POSTGRES_IMAGE`). A new image CI needs from a public registry goes through `mirror.yml` too. **CI skips pushes that change only `.md` files** (except `docs/schema.md`, which a store test reads) and cancels the run of the previous commit when a newer one is pushed to the same branch (`paths` and `concurrency` in ci.yml); a push with any code file in it runs everything, so no `[skip ci]` is needed for docs. A cold `windows` build is ~35 min but a warm one 10-14 min.

- **People (0.5.8.1):** `ductus user create|list|set|password|disable|enable|unlock` works on the database directly (`--password-stdin` for scripts; a terminal asks twice, no echo). Tests and demos that read a payload through the API need a token with `--permission payloads` (admins have every permission). Test users are named `test-user-...` (the store's last-admin test deletes such admins first, so a demo that makes an admin must name it that way). **Every test and demo deletes the accounts it makes** (accounts are never deleted in the product, so a long-lived dev database piled up 386 in a week and the Users page, which renders every account, timed out demo-ui's axe test): Rust tests name them with `ductus_store::testing::TestUsers` (feature `testing`, dev-dependencies only, never in the binary) and an async test ends with `people.forget().await` (its `Drop` is the fallback on failure, with a `lock_timeout`: blocking the test's runtime in `Drop` hung once, because a refused change's ROLLBACK is sent from that runtime and its locks stay until then); scripts call `forget_test_users PATTERN...` (`scripts/dev/db.sh`) in their `trap`; accounts the Playwright specs make start with `DUCTUS_PEOPLE_PREFIX` (demo-ui's `test-user-ui-<pid>-`), which demo-ui's trap deletes (there's no API to delete one). Both helpers clear sessions, tokens, settings and `message_actions.user_id/token_id` first and refuse any name not `test-user-*`; audit rows stay. A new API operation needs a row in `ACCESS` (`api/mod.rs` tests). The store test for the last admin only checks the guard when the test database has no other admin.
- **Audit (0.5.8.2):** a change that has a transaction takes an `&Audit` (`ductus_store::{Audit, By}`) and writes its row in it (`audit::insert`); one without writes the row first with `record_first` (API) or `Store::record`. New audit actions go in `docs/schema.md` (`audit_log.action`) and in the UI's `ACTIONS` map (`ui/src/components/audit-table.tsx`). Store tests that aren't about the log pass `quiet()`. Test users are `test-user-*`; the CLI tests and `demo-ui.sh` read `/audit` as a token or person with the `audit` permission. `ductus audit export` reads the database directly. The hourly trim deletes anything older than 6 years: a test that needs old rows backdates its own and trims with its own `keep`.
- **Alerts (0.5.8.3):** ductus.yaml is parsed through `env::parse_yaml` (so `${...}` can't break it) and only `alerts:` is substituted, per environment (`Settings::alerts(&env)`); everything else in it is read as written. **lettre's pooled SMTP transport must be built inside a Tokio runtime** (`Alerts::new` spawns; a plain `#[test]` aborts with "no reactor running": use `#[tokio::test]`). `chrono` has the `serde` feature only through the runtime's dependency tree: `cargo check -p ductus-runtime` compiled a `json!` with a `DateTime` in `ductus-store` that `cargo test -p ductus-store` alone refused; put times in JSON as `to_rfc3339()`. Store tests that make alerts delete them (`forget_alert`): an open test alert would show in a demo engine's counts (the API lists only the engine's own interfaces' alerts anyway). Demos that need mail or a webhook use `ductus sink --smtp`/`--http` (`--dir` keeps each one as a file).
- **Certificates (0.5.8.4):** the engine's own checks (`certificates.rs`: `doctor.schedule`, `certificates` mode by default) store `certificate_status` and `doctor_runs` (last 30); `alerts.rs` judges each certificate every 15 s from the stored dates (`ductus_core::alerts::certificate_step`; `alert_state.stage` is the warn day last told). A certificate's alert row has `interface` = its resource and `destination` = `host:port`; the API's `ours()` knows them by `Engine::certificates`. Tests and demos make certificates at run time: rcgen in `doctor.rs` tests, and the **`cert-server` example** (`crates/ductus-runtime/examples`, rcgen is a dev-dependency so it can't be in the binary; `cargo test --release` builds it into `target/release/examples/`) for `demo-certs.sh` and `demo-ui.sh`. Stop it with SIGTERM, not SIGINT: a background job of a script ignores SIGINT and the example installs no handler (a leftover held the ports and failed the next run; `demos.sh` `pkill`s it). The engine's default log filter turns off `rustls_platform_verifier` (it logs every refused certificate at ERROR, every scheduled check). Handlers must not be named like another module's (`list`): give them `operation_id` (the certificates list once took the message browser's types).
- **Directory sign-in (0.5.8.5):** tests and demos use a throwaway OpenLDAP: `scripts/dev/slapd.sh start DIR PORT TLS_PORT` / `stop DIR` (slapd and ldap-utils from apt; its system service disabled). It copies the slapd binary into DIR because Ubuntu's AppArmor profile confines `/usr/sbin/slapd` to `/etc/ldap` and `/var/lib/ldap` (a copy runs unconfined), makes its own CA (`DIR/ca.pem`, for `ca:`), and loads people `test-user-{ada,olaf,anna,nested,nobody}` (password `<uid>-password`, service `cn=ductus-svc,ou=service,dc=example,dc=org`/`svc-password`, admin `cn=admin,dc=example,dc=org`/`admin-password`). Every group has a placeholder member (groupOfNames needs one, or removing the last member fails). Stop it with SIGTERM (the script does); `demos.sh` `pkill`s leftovers. **Use 127.0.0.1, not localhost**: in WSL `localhost` resolves only to `::1` and slapd listens on 127.0.0.1 (the certificate has both). Installing slapd non-interactively needs `sudo env DEBIAN_FRONTEND=noninteractive apt-get ...` (`sudo` drops the variable, and debconf then waits on a hidden password dialog forever). The runtime's `tests/ldap.rs` skips without slapd unless `DUCTUS_TEST_SLAPD=required` (CI). A session cookie in a bash demo: read it from `Set-Cookie` and send `Cookie:` yourself (curl's jar won't send a `Secure` cookie over http), and keep the old one when a refused sign-in sets none. ldap3's `Mod` needs one string type throughout (`Mod::Delete("member".to_string(), HashSet<String>)`).
- **Owners (0.5.8.6):** `ductus_core::owners::find` is the one rule for "which account does this owner text name" (alerts, `/owners`, `ductus owners`): add any new use there, don't match names again. `owned` takes the resources too. `ductus owners` reads accounts only when `DUCTUS_DATABASE_URL` is set, and check.sh sets it: CLI tests of the plain report use `without_a_database`. The v0.5 demo (`demo-v05.sh`) runs its browser story with its own config (`ui/playwright.story.config.ts`, tests in `ui/story/`, not picked up by `demo-ui.sh`); the story starts and stops the lab's receiver itself (`ductus sink --reject TEXT` answers AR). It deletes its directory accounts with their `message_actions` at the end: `demo-ui.sh` deletes the same directory people at its start, and a `message_actions` row would refuse that (`users` is referenced). An `<input list=...>` (a datalist) has the role `combobox`, not `textbox`. In YAML, DNs in a `[flow, list]` split at their commas (`auth.ldap` now refuses a one-part group DN).
- **Engines on one database (0.6.2):** the start claims its interfaces (`ownership.rs`) right after connecting: anything new that changes an interface's rows at start goes **after** `guard_lanes`, never before (a refused engine must change nothing). Tests and demos that start engines use interface names of their own (CLI tests add nanos; demos name theirs per demo where they can) and never run two engines with the same names at once: the second exits 3. A demo that leaves messages waiting on purpose filters them at exit (`forget_waiting` in demo-ui/demo-hotspots/demo-one-owner), or a later demo with the same names but fewer lanes is refused (and one with more sends them). Demos and tests wait for `started interfaces=`: keep `interfaces` the first field of that line. Read-only commands connect with `Store::connect_read_only` (no migrations: `validate` and `owners` may run with a newer binary than the engines). Kill a test engine's lock session by its key: `pg_locks` with `((classid::bigint << 32) | objid::bigint) = lock_key` (other tests' engines share the database).
- **Startup statements over 1,000 interfaces:** a count per destination (`CROSS JOIN LATERAL`) can get a plan that seq-scans a partition holding one destination's backlog once per destination (18 s at 1,001 destinations, 300,000 waiting): read the waiting rows once (a `MATERIALIZED` CTE over the queue index) and join the limits to them, or walk distinct values with a recursive CTE (`with_waiting`). Write upserts as read-then-write when the rows usually exist already (an `ON CONFLICT` check per row costs ~50 ms at 1,001). Time a start with `RUST_LOG=info,ductus_runtime=debug` ("start: …" per phase) and `sqlx=debug` (each statement's `elapsed`). **sqlx 0.9.0 doesn't set `TCP_NODELAY`**: statements with large parameters wait ~40 ms for a delayed ACK over TCP (a Unix socket or an `LD_PRELOAD` shim showed it); message flow measured unaffected. Fixed upstream (transact-rs/sqlx#4336, merged 2026-08-17 after 0.9.0): bump sqlx when a release has it and re-measure the start.
- **Web UI (`ui/`):** Node 24 in WSL is a per-user install in `~/.local/node` (check.sh and demos.sh put it on the PATH; non-interactive WSL shells don't read `.bashrc`). TypeScript is pinned to 6.0 (typescript-eslint doesn't support 7, the Go one); openapi-typescript's `typescript ^5` peer is overridden in package.json (`overrides`), not `--force`d. TS 6 deprecates `baseUrl`: `paths` alone. A new API field or route = run check.sh, which regenerates `ui/openapi.json` and `ui/src/api/schema.d.ts` and asks for a second run. A `<section>` is a landmark (`region`) only with a name: label cards that tests or screen readers look for (`aria-label`). axe runs in every theme in `demo-ui.sh` (AAA in high contrast): new colors must pass it. Under `set -o pipefail`, `curl` to a closed port fails the whole pipeline: capture its output first.
- **utoipa names each operation after its handler function**: two modules' `list` once shared the operationId `list`, and the UI's generated types gave `GET /tokens` the message browser's answer. A handler named like another gets `operation_id = "..."` in `#[utoipa::path]` (`every_operation_has_its_own_id` guards it).
- **Playwright sign-in waits until the URL has left `/sign-in`**: clicking "Sign in" and navigating at once can cancel the request (CI ran a test signed out), and the sign-in page has an h1 too, so "an h1 is visible" proves nothing.
- **TLS on listeners (0.6.3):** inside `impl axum::serve::Listener for X`, `tcp.accept()` on a `&mut TcpListener` resolves to axum's trait method (it takes `&mut self`), not tokio's: write `TcpListener::accept(tcp)`. A custom listener keeps `ConnectInfo<SocketAddr>` only through `.tap_io(|_| {})` (axum implements `Connected` for `TapIo<L, _>`; it can't be implemented for our type: orphan rule). Tests and demos make certificates with `ductus cert self-signed` or rcgen (now a regular dependency of the runtime); a self-signed leaf works as its own trust anchor (rustls, reqwest's `tls_certs_only`). With TLS 1.3, a refused client certificate shows on the client only at its first read, not at `connect`. **Outbound (0.6.3.2):** every outgoing TLS connection goes through `tls::Trust` (`Certificates::trust`/`client`, one `ClientConfig` per distinct `ConnectTls`, cached); a new kind of connection must too (and doctor's handshake must use the same `Trust`). reqwest takes our config with `tls_backend_preconfigured` (`tls::http_client`), which uses it as is: set ALPN yourself (`h2`, `http/1.1`) or HTTP/2 is lost. lettre can't take a rustls config: give it the extra roots and the pair's PEM (`Pair::pem`). The test helpers for certificates (a CA, an intermediate, leaves, a receiver with its clients' CA) are `tls::testing` (`#[cfg(test)]`). **Ours (0.6.3.3):** a pair the engine presents is a `CertificateTarget` with `Side::Ours`, key `cert:<name>:<this host>:0` (port 0: never a remote row's); judge, list and gauge it from memory (`certificates::our_row`), never by reading `certificate_status`; its row is written at start and when `Certificates::watch`/`reload` reports a change (renewed, or its renewal error appeared/changed/went). Anything new that reads `certificate_status` periodically must skip it when there are no remote targets. In Playwright, `getByRole(..., { name: "Certificates" })` also matches "Our certificates" (names match as substrings): pass `exact: true`. **Tools (0.6.3.4):** `gen`/`sink --tls` must keep going through `Certificates` (entries built in memory from their files), never a hand-made rustls config, so they verify and word refusals as the engine does. Demos play the hospital's CA with openssl: `openssl x509 -req ... -copy_extensions copy` (OpenSSL 3) keeps a CSR's names and uses; **`openssl req -x509` makes a CA:TRUE certificate**, which webpki refuses as a server's or client's (`CaUsedAsEndEntity`; `tls::is_ca_as_leaf` words it): make lab pairs with `ductus cert self-signed` or `cert request` + a CA. Since 0.6.5.1's side step, `tls::Verifier` (what `Trust::verifier` returns, around the platform verifier) accepts a receiver's CA:TRUE certificate when that exact certificate is trusted (`ca:` or the system store), as Windows does by itself; doctor checks connections with their own TLS stack with that stack's verdict (`doctor::Stack`: SMTP via lettre `platform_only()`, Postgres and SQL Server `webpki_only()`); a new kind of connection with its own TLS needs its `Stack`. Any new connection doctor (or anything in the engine) makes to our own listeners registers its local address with `Refusals::our_own` first, or a client-certificate listener logs it as a refused sender. `examples/tls-bench.rs` (handshakes, held connections, HTTP timings) is what `scripts/bench-tls.sh` drives.
- **Who may connect (0.6.3.5):** a listener's `allow:` is checked by `allow::Admission::admits` right after `accept()`, before any handshake: a new kind of listener must call it (and `allow::keepalive`) there, as `ingest::spawn_mllp`'s `open` and `tls::Listener` do. The engine's own connections to its listeners go through `tls::connect_own` (binds to the listener's address and registers it *before* connecting; registering after connecting is too late for the admission). Host names live in one `allow::Names` per engine (looked up at start, every 5 min, and after a refusal at most once a minute per name); accepted connections never look anything up. Tests and demos play senders elsewhere from 127.0.0.2/127.0.0.3 (`gen --from`, `curl --interface`, `TcpSocket::bind`): Linux only, so such Rust tests are `#[cfg(target_os = "linux")]`. The log's `listener` field is quoted (`listener="interface \`x\` (MLLP)"`): grep it that way. A new API field shows up in the UI's types only after check.sh regenerates them, and check.sh type-checks the UI first: run `ductus api-spec >ui/openapi.json && (cd ui && npm run -s api-types)` before it.
- **TLS to Postgres (0.6.4.2):** sqlx's `tls-rustls-aws-lc-rs` builds its own `ClientConfig` per handshake from `aws_lc_rs::default_provider()` (our `prefer-post-quantum` unifies in) and alone trusts only bundled Mozilla roots: sqlx-core's internal `rustls-native-certs` feature (named in ductus-store's Cargo.toml) makes it the system's, and `the_system_s_trusted_certificates_count` (cli tests, `SSL_CERT_FILE`) fails if a bump drops it. A handshake failure arrives as `sqlx::Error::Io` wrapping a `rustls::Error`; `ductus_store::tls::refusal` words it (the store's `connect` for the URL, `services::classify` for `db()`). The URL keeps libpq's meaning (`prefer` by default; `ductus_core::pgtls`); `sslrootcert=system` is rewritten by `tls::connect_url`. resources.yaml postgres: `tls`/`ca`/`certificate` (`DbConnection::mode`: `verify-full` when `ca` is named); sqlx copies PEM into the options, so a renewed `certificate:` pair is pushed into the pool with `Pair::on_renewal` + `set_connect_options` (new connections only). Doctor speaks the SSLRequest itself (`postgres_tls`) and watches only verified connections (`Target::has_certificate`). Tests and demos use a throwaway TLS Postgres: `scripts/dev/pgtls.sh start|reload|stop` (server binaries from `/usr/lib/postgresql/*/bin`; CA, other CA, server certificate for localhost/127.0.0.1 and listening on 127.0.0.2 too for the wrong name, a `ductus_cert` client certificate); Rust tests through `ductus_store::testing::PgTls` (skips unless `DUCTUS_TEST_PGTLS=required`, as CI). Its certificates last a year: doctor warns under 30 days. **Measured:** opening a connection over TLS takes ~60 ms more until sqlx sets `TCP_NODELAY` (transact-rs/sqlx#4336), which also puts ~0.4 s on the 1,001-interface start against a Postgres with ssl on (Todd's dev database: `prefer` is TLS there now). The plain log format doesn't quote a Display field with spaces (`database=TLS 1.3, verified (...)`).
- **Windows (0.6.5.1):** CI's `windows-tests` job runs `cargo test --release` on `windows-latest` against `ductus dev`'s Postgres (Rust cache shared with `windows`, saved by `windows-tests`). Windows takes ~2 s to report a refused connection (it resends the SYN after the reset), so **every outgoing TCP connection the engine makes itself goes through `ductus_mllp::net::{connect, socket}`** (two SYN retransmissions via `SIO_TCP_INITIAL_RTO`: refused in ~1 s; none would give up on one lost SYN), never `TcpStream::connect` (doctor's "refused" vs "no answer" depends on it; reqwest, ssh and ldap connect by themselves). `localhost` is `::1` first there, so a test with `localhost` and a short timeout against an IPv4 listener spends ~1 s on `::1`. Test helpers that run bash scripts (`PgTls`, slapd) return None on Windows with a note, before looking at `DUCTUS_TEST_*=required`. The repo's own checkout on Windows has `core.autocrlf=true`; Git for Windows on the runner does too: a test that runs `git` names `-c core.autocrlf=...`. On Windows `Path::is_absolute` needs a drive: `/etc/x` joins onto the project's drive (`Resources::without_drive` warns). Run the suite natively here with `CARGO_HOME=D:\cargo-home` and `CARGO_TARGET_DIR=D:\target-win` and a `ductus dev --database-only` URL in `DUCTUS_DATABASE_URL`/`DUCTUS_TEST_DATABASE_URL`.
- **SQL Server Windows logins (0.6.5.2):** tiberius comes from our fork (`[patch.crates-io]`, `thorst/tiberius` branch `ductus-0.13`, pinned to a commit: Negotiate on Windows, sspi 0.23 on Linux, `sspi-rs` turned on for Unix only); a change there is a commit on that branch and a new `rev`. To debug it, point the patch at `../tiberius` (path) for a while. The tests need SQL Server Express (`scripts/dev/sqlexpress.ps1`, as administrator; CI runs it in `windows-tests`) and `DUCTUS_TEST_SQLSERVER_WINDOWS` = `required` (this machine, 1433) or `DOMAIN@host:port`, with `DUCTUS_TEST_SQLSERVER_WINDOWS_PASSWORD`. **On Todd's machine it listens on 1435** (1433 on Windows is WSL's forwarded port for the Linux test SQL Server): natively `DESKTOP-GCT6E6V@localhost:1435`, from WSL `DESKTOP-GCT6E6V@<WSL's gateway>:1435` (the script's `-AllowWsl` opened the firewall to WSL's subnet); the test password isn't kept anywhere: rerun the script with a new `-Password` (it sets the accounts and `ductus_sql` again; one UAC prompt). Express gives `BUILTIN\Users` a login (every account gets in through it): the script drops it. A refused Windows login is 18452 (Windows said no) or 18456 (no login on SQL Server's side).
- **The service's account, the Event Log, the `stopped` marker (0.6.5.3):** `crates/ductus-cli/src/service/` (`run.rs` the service, `eventlog.rs`, `messages.rs`, `account.rs` for `ductus service account` and the installer's hidden `ductus service installed`). **Event Log text is a MESSAGETABLE built into ductus.exe** (`build.rs` encodes `messages.rs`'s table, embed-resource runs rc.exe): a new event ID is a row there (the test reads the table back as Windows does). The engine's log lines that become events are matched by message: their texts are constants in `ductus_runtime::events` (use them in the `tracing` call, `"{}", events::X`); any other ERROR line is event 1100, once a minute per message and target. The installer runs `ductus.exe service installed` after InstallServices (SID type unrestricted, the logon right, event 1005 when the account needs its password); which accounts need a password is `ductus_core::service_account::Kind` **and** the `NEEDSPASSWORD` condition in `ductus.wxs`: change both. Windows' account lookup doesn't take `.\name` (the service manager's way of writing local accounts): replace the dot with `COMPUTERNAME`. **`msiexec /i` of the same MSI file again is a maintenance run, not an upgrade** (nothing removed or reinstalled): `demo-windows.ps1` takes two builds (`-Msi`, `-UpgradeMsi`; each build has its own ProductCode) and checks "Installation completed". A process that formatted our events (`Get-WinEvent`, Event Viewer) holds ductus.exe as the message file: the next uninstall/upgrade waited 152 s in InstallValidate (Restart Manager off by policy here); the demo reads events in a child `powershell`. PowerShell 5.1 turns a native program's stderr into an exception under `$ErrorActionPreference = "Stop"` (the demo's `Native` helper); `net user NAME PASS /add` asks Y/N for passwords over 14 characters. Don't run `ductus dev` from `D:\target-win\release\ductus.exe` while rebuilding it (the file is locked: copy it first).
- **Accessible names in the UI:** an `sr-only` span adds a space before itself ("Where it's stuck" + `<span sr-only>: lab</span>` reads "Where it's stuck : lab"): start sr-only text with a space and a word, or scope the test by its region instead.
