# Connections and TLS

Read before changing: TLS (listeners, outbound, Postgres, SQL Server), `allow:`, certificates, LDAP/directory, SFTP. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- tiberius 0.13 (bb8-tiberius is stuck on 0.12, so `mssql.rs` has its own pool). Tests and CI use **SQL Server 2025** since 0.6.4.3 (2022 on Linux refuses TDS 8 strict whatever it's given; `MSSQL_IMAGE` picks another).
- **TLS to SQL Server (0.6.4.3):** the test SQL Server (`scripts/dev/sqlserver.sh`, also in CI, not as a service: a service can't be given files before it starts) presents a certificate from a test CA (mssql-conf via a mounted `mssql.conf`; hostname `sql1.ductus.test`: SQL Server accepts strict only with a certificate for its own host name; its folder is `DUCTUS_TEST_SQLSERVER_TLS`, which check.sh and CI set with `DUCTUS_TEST_SQLSERVER`). A container made before this (no `ductus.setup` label for the image) is made again. sqlcmd inside the container hangs at login when TLS 1.3 is the only protocol allowed: wait on the log, not sqlcmd, when experimenting. tiberius flattens TLS errors into `Error::Tls(String)` with advice in its own API's terms: `mssql::refusal` words them from rustls's rendered names (guarded by tests against the real server: if a tiberius bump changes the text, those fail). tiberius panics with both `trust_cert` and a CA (resources.yaml refuses the pair) and warns at every connection with `trust_cert` (the log filters set `tiberius=error`; the start warns once). Doctor's PRELOGIN (`PRELOGIN_REQUEST`, `Prelogin`: TLS records framed at each flush, as tiberius does) gives TLS 1.2 always; strict is plain TLS with ALPN `tds/8.0`.
- russh 0.64: `client::Handler::check_server_key(&PublicKeyOrCertificate)`; fingerprints via `key.fingerprint(HashAlg::Sha256)` print like `ssh-keygen -lf`. SFTP `rename` won't overwrite: remove the target first.
- **Certificates (0.5.8.4):** the engine's own checks (`certificates.rs`: `doctor.schedule`, `certificates` mode by default) store `certificate_status` and `doctor_runs` (last 30); `alerts.rs` judges each certificate every 15 s from the stored dates (`ductus_core::alerts::certificate_step`; `alert_state.stage` is the warn day last told). A certificate's alert row has `interface` = its resource and `destination` = `host:port`; the API's `ours()` knows them by `Engine::certificates`. Tests and demos make certificates at run time: rcgen in `doctor.rs` tests, and the **`cert-server` example** (`crates/ductus-runtime/examples`, rcgen is a dev-dependency so it can't be in the binary; `cargo test --release` builds it into `target/release/examples/`) for `demo-certs.sh` and `demo-ui.sh`. Stop it with SIGTERM, not SIGINT: a background job of a script ignores SIGINT and the example installs no handler (a leftover held the ports and failed the next run; `demos.sh` `pkill`s it). The engine's default log filter turns off `rustls_platform_verifier` (it logs every refused certificate at ERROR, every scheduled check). Handlers must not be named like another module's (`list`): give them `operation_id` (the certificates list once took the message browser's types).
- **Directory sign-in (0.5.8.5):** tests and demos use a throwaway OpenLDAP: `scripts/dev/slapd.sh start DIR PORT TLS_PORT` / `stop DIR` (slapd and ldap-utils from apt; its system service disabled). It copies the slapd binary into DIR because Ubuntu's AppArmor profile confines `/usr/sbin/slapd` to `/etc/ldap` and `/var/lib/ldap` (a copy runs unconfined), makes its own CA (`DIR/ca.pem`, for `ca:`), and loads people `test-user-{ada,olaf,anna,nested,nobody}` (password `<uid>-password`, service `cn=ductus-svc,ou=service,dc=example,dc=org`/`svc-password`, admin `cn=admin,dc=example,dc=org`/`admin-password`). Every group has a placeholder member (groupOfNames needs one, or removing the last member fails). Stop it with SIGTERM (the script does); `demos.sh` `pkill`s leftovers. **Use 127.0.0.1, not localhost**: in WSL `localhost` resolves only to `::1` and slapd listens on 127.0.0.1 (the certificate has both). Installing slapd non-interactively needs `sudo env DEBIAN_FRONTEND=noninteractive apt-get ...` (`sudo` drops the variable, and debconf then waits on a hidden password dialog forever). The runtime's `tests/ldap.rs` skips without slapd unless `DUCTUS_TEST_SLAPD=required` (CI). A session cookie in a bash demo: read it from `Set-Cookie` and send `Cookie:` yourself (curl's jar won't send a `Secure` cookie over http), and keep the old one when a refused sign-in sets none. ldap3's `Mod` needs one string type throughout (`Mod::Delete("member".to_string(), HashSet<String>)`).
- **TLS on listeners (0.6.3):** inside `impl axum::serve::Listener for X`, `tcp.accept()` on a `&mut TcpListener` resolves to axum's trait method (it takes `&mut self`), not tokio's: write `TcpListener::accept(tcp)`. A custom listener keeps `ConnectInfo<SocketAddr>` only through `.tap_io(|_| {})` (axum implements `Connected` for `TapIo<L, _>`; it can't be implemented for our type: orphan rule). Tests and demos make certificates with `ductus cert self-signed` or rcgen (now a regular dependency of the runtime); a self-signed leaf works as its own trust anchor (rustls, reqwest's `tls_certs_only`). With TLS 1.3, a refused client certificate shows on the client only at its first read, not at `connect`. **Outbound (0.6.3.2):** every outgoing TLS connection goes through `tls::Trust` (`Certificates::trust`/`client`, one `ClientConfig` per distinct `ConnectTls`, cached); a new kind of connection must too (and doctor's handshake must use the same `Trust`). reqwest takes our config with `tls_backend_preconfigured` (`tls::http_client`), which uses it as is: set ALPN yourself (`h2`, `http/1.1`) or HTTP/2 is lost. lettre can't take a rustls config: give it the extra roots and the pair's PEM (`Pair::pem`). The test helpers for certificates (a CA, an intermediate, leaves, a receiver with its clients' CA) are `tls::testing` (`#[cfg(test)]`). **Ours (0.6.3.3):** a pair the engine presents is a `CertificateTarget` with `Side::Ours`, key `cert:<name>:<this host>:0` (port 0: never a remote row's); judge, list and gauge it from memory (`certificates::our_row`), never by reading `certificate_status`; its row is written at start and when `Certificates::watch`/`reload` reports a change (renewed, or its renewal error appeared/changed/went). Anything new that reads `certificate_status` periodically must skip it when there are no remote targets. In Playwright, `getByRole(..., { name: "Certificates" })` also matches "Our certificates" (names match as substrings): pass `exact: true`. **Tools (0.6.3.4):** `gen`/`sink --tls` must keep going through `Certificates` (entries built in memory from their files), never a hand-made rustls config, so they verify and word refusals as the engine does. Demos play the hospital's CA with openssl: `openssl x509 -req ... -copy_extensions copy` (OpenSSL 3) keeps a CSR's names and uses; **`openssl req -x509` makes a CA:TRUE certificate**, which webpki refuses as a server's or client's (`CaUsedAsEndEntity`; `tls::is_ca_as_leaf` words it): make lab pairs with `ductus cert self-signed` or `cert request` + a CA. Since 0.6.5.1's side step, `tls::Verifier` (what `Trust::verifier` returns, around the platform verifier) accepts a receiver's CA:TRUE certificate when that exact certificate is trusted (`ca:` or the system store), as Windows does by itself; doctor checks connections with their own TLS stack with that stack's verdict (`doctor::Stack`: SMTP via lettre `platform_only()`, Postgres and SQL Server `webpki_only()`); a new kind of connection with its own TLS needs its `Stack`. Any new connection doctor (or anything in the engine) makes to our own listeners registers its local address with `Refusals::our_own` first, or a client-certificate listener logs it as a refused sender. `examples/tls-bench.rs` (handshakes, held connections, HTTP timings) is what `scripts/bench-tls.sh` drives.
- **Who may connect (0.6.3.5):** a listener's `allow:` is checked by `allow::Admission::admits` right after `accept()`, before any handshake: a new kind of listener must call it (and `allow::keepalive`) there, as `ingest::spawn_mllp`'s `open` and `tls::Listener` do. The engine's own connections to its listeners go through `tls::connect_own` (binds to the listener's address and registers it *before* connecting; registering after connecting is too late for the admission). Host names live in one `allow::Names` per engine (looked up at start, every 5 min, and after a refusal at most once a minute per name); accepted connections never look anything up. Tests and demos play senders elsewhere from 127.0.0.2/127.0.0.3 (`gen --from`, `curl --interface`, `TcpSocket::bind`): Linux only, so such Rust tests are `#[cfg(target_os = "linux")]`. The log's `listener` field is quoted (`listener="interface \`x\` (MLLP)"`): grep it that way. A new API field shows up in the UI's types only after check.sh regenerates them, and check.sh type-checks the UI first: run `ductus api-spec >ui/openapi.json && (cd ui && npm run -s api-types)` before it.
- **TLS to Postgres (0.6.4.2):** sqlx's `tls-rustls-aws-lc-rs` builds its own `ClientConfig` per handshake from `aws_lc_rs::default_provider()` (our `prefer-post-quantum` unifies in) and alone trusts only bundled Mozilla roots: sqlx-core's internal `rustls-native-certs` feature (named in ductus-store's Cargo.toml) makes it the system's, and `the_system_s_trusted_certificates_count` (cli tests, `SSL_CERT_FILE`) fails if a bump drops it. A handshake failure arrives as `sqlx::Error::Io` wrapping a `rustls::Error`; `ductus_store::tls::refusal` words it (the store's `connect` for the URL, `services::classify` for `db()`). The URL keeps libpq's meaning (`prefer` by default; `ductus_core::pgtls`); `sslrootcert=system` is rewritten by `tls::connect_url`. resources.yaml postgres: `tls`/`ca`/`certificate` (`DbConnection::mode`: `verify-full` when `ca` is named); sqlx copies PEM into the options, so a renewed `certificate:` pair is pushed into the pool with `Pair::on_renewal` + `set_connect_options` (new connections only). Doctor speaks the SSLRequest itself (`postgres_tls`) and watches only verified connections (`Target::has_certificate`). Tests and demos use a throwaway TLS Postgres: `scripts/dev/pgtls.sh start|reload|stop` (server binaries from `/usr/lib/postgresql/*/bin`; CA, other CA, server certificate for localhost/127.0.0.1 and listening on 127.0.0.2 too for the wrong name, a `ductus_cert` client certificate); Rust tests through `ductus_store::testing::PgTls` (skips unless `DUCTUS_TEST_PGTLS=required`, as CI). Its certificates last a year: doctor warns under 30 days. **Measured:** opening a connection over TLS takes ~60 ms more until sqlx sets `TCP_NODELAY` (transact-rs/sqlx#4336), which also puts ~0.4 s on the 1,001-interface start against a Postgres with ssl on (Todd's dev database: `prefer` is TLS there now). The plain log format doesn't quote a Display field with spaces (`database=TLS 1.3, verified (...)`).
- **SQL Server Windows logins (0.6.5.2):** tiberius comes from our fork (`[patch.crates-io]`, `thorst/tiberius` branch `ductus-0.13`, pinned to a commit: Negotiate on Windows, sspi 0.23 on Linux, `sspi-rs` turned on for Unix only); a change there is a commit on that branch and a new `rev`. To debug it, point the patch at `../tiberius` (path) for a while. The tests need SQL Server Express (`scripts/dev/sqlexpress.ps1`, as administrator; CI runs it in `windows-tests`) and `DUCTUS_TEST_SQLSERVER_WINDOWS` = `required` (this machine, 1433) or `DOMAIN@host:port`, with `DUCTUS_TEST_SQLSERVER_WINDOWS_PASSWORD`. **On Todd's machine it listens on 1435** (1433 on Windows is WSL's forwarded port for the Linux test SQL Server): natively `DESKTOP-GCT6E6V@localhost:1435`, from WSL `DESKTOP-GCT6E6V@<WSL's gateway>:1435` (the script's `-AllowWsl` opened the firewall to WSL's subnet); the test password isn't kept anywhere: rerun the script with a new `-Password` (it sets the accounts and `ductus_sql` again; one UAC prompt). Express gives `BUILTIN\Users` a login (every account gets in through it): the script drops it. A refused Windows login is 18452 (Windows said no) or 18456 (no login on SQL Server's side).
- **Directory ids (0.6.7.1):** a directory account is its person: `users.directory_id` (`entryUUID:<v>`, `objectGUID:hex:<hex>`; `ductus_core::ldap::DirectoryId`) is read at every sign-in and refresh, and the refresh searches by it (`Directory::check_all` over `DirectoryAccount`s). **`Store::save_directory_user` is the one place that decides who an account is** (by id; renamed when the directory's sign-in name changed; an account without an id takes one; a name held by another id moves aside as `<name>#<account id>`, refused): don't find directory accounts by name anywhere else. Any change of a username, display name or email writes the old value with `users::keep_former` in the same transaction (a new writer of those columns must too). Test helpers delete `<name>#%` with each name (`forget_test_users`, Rust and `db.sh`). A refresh reads **every** directory account in the database: runtime tests that refresh take `ONE_DIRECTORY` (tests/ldap.rs), or two tests check each other's people against the wrong slapd and refuse them. objectGUID is bytes: ldap3 files a value that happens to be UTF-8 under `attrs`, so `value_of` reads both. `scripts/dev/slapd.sh` has `refint` (group `member` follows a modrdn, as in AD). The refresh round is measured by `measure_a_refresh_round` (ignored test).
- **Owners' directory accounts (0.6.7.3):** the refresh is `ldap::Round` (one per engine, made from its project's owner texts and teams; `ldap::refresh` is a round without owners, for tests): first round at once, in the spawned task (never in the start path), then every `refresh`. It checks owners' accounts with the signed-in ones and makes accounts for owner emails (and texts naming a disabled account) found by `attributes.email` in a role group. A refresh saves through **`Store::check_directory_user`** (reads without a lock and writes nothing when nothing changed) and stamps the round with `directory_checked`: `SELECT … FOR UPDATE` alone assigns an xid and WAL-logs the row locks, so a "no-op" locked transaction still waits for the flush (~5 ms a commit on WSL's disk; 200 accounts were 1.25 s a round, now 0.41 s). `save_directory_user` retries once on a unique violation (two engines making one person). `owner_addresses` sends nothing for a text naming a disabled account, not even to the text as an address. Runtime tests that run a `Round` take `ONE_DIRECTORY`. The engines of demo-ldap, demo-ui and demo-v05 now refresh at start: they must delete their directory people *before* starting the engine (they do).
