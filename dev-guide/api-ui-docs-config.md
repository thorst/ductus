# API, web UI, docs, config parsing

Read before changing: REST routes/OpenAPI, the web UI and Playwright, the docs reference and site, YAML/config parsing. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- `serde_yaml_ng`: enums in YAML maps need `with = "serde_yaml_ng::with::singleton_map"` (or `_recursive`). It's only a dev-dependency of `ductus-runtime` (its unit tests compile, its library doesn't): read YAML there with `ductus_core::yaml::parse` and `ductus_core::yaml::Value` (as `changes.rs` does).
- `${...}` in YAML flow style breaks parsing: always load project YAML through `ductus_core::env::parse_yaml` (protects references first).
- chacha20poly1305 0.11 changed its RNG API: we use `getrandom` directly.
- quick-xml's API churns: XML key extraction uses our own small reader (`runtime/src/keys.rs`), deliberately matching the SDK's `parseXml` rules.
- **REST API routes** go through `utoipa_axum::routes!` in each `api/*.rs` `routes()` (that's what puts them in the OpenAPI document); a handler's `#[utoipa::path]` path is relative to `/api/v1`. Two handlers with one path and different methods go in one `routes!(a, b)`. A plain helper with the same name as a handler breaks the macro (it picks the wrong item).
- **utoipa `IntoParams` structs need `#[into_params(parameter_in = Query)]`**, or the document publishes their fields as *path* parameters (the message browser's `status`/`before`/`limit` were, until the UI's generated types caught it). `the_document_has_path_parameters_only_where_the_path_has_them` guards it.
- **Web UI (`ui/`):** Node 24 in WSL is a per-user install in `~/.local/node` (check.sh and demos.sh put it on the PATH; non-interactive WSL shells don't read `.bashrc`). TypeScript is pinned to 6.0 (typescript-eslint doesn't support 7, the Go one); openapi-typescript's `typescript ^5` peer is overridden in package.json (`overrides`), not `--force`d. TS 6 deprecates `baseUrl`: `paths` alone. A new API field or route = run check.sh, which regenerates `ui/openapi.json` and `ui/src/api/schema.d.ts` and asks for a second run. A `<section>` is a landmark (`region`) only with a name: label cards that tests or screen readers look for (`aria-label`). axe runs in every theme in `demo-ui.sh` (AAA in high contrast): new colors must pass it. Under `set -o pipefail`, `curl` to a closed port fails the whole pipeline: capture its output first.
- **utoipa names each operation after its handler function**: two modules' `list` once shared the operationId `list`, and the UI's generated types gave `GET /tokens` the message browser's answer. A handler named like another gets `operation_id = "..."` in `#[utoipa::path]` (`every_operation_has_its_own_id` guards it). **Schemas are named after their struct, and nothing guards those**: 0.7.4.4.1's `Change` (a deploy's) silently replaced retention's `Change` in `ui/openapi.json`, and only the UI's type check noticed (retention.tsx lost `started_at`). Name a response struct after its operation (`DeployChange`, `DeployGate`). If check.sh then fails in the UI step with the stale types, `git checkout -- ui/openapi.json ui/src/api/schema.d.ts` and run it again: the UI is checked before the document is regenerated.
- **Playwright sign-in waits until the URL has left `/sign-in`**: clicking "Sign in" and navigating at once can cancel the request (CI ran a test signed out), and the sign-in page has an h1 too, so "an h1 is visible" proves nothing.
- **Docs reference and schemas (0.6.8.1):** a config field's doc comment is user-facing text: it becomes the JSON Schema's description (VS Code hover) and the reference page. Write it to the bar (what, why, when not, `Default:`, `Example:`); `every_setting_is_described_for_people` fails on a missing one or one that names code. Every config type has `#[cfg_attr(test, derive(schemars::JsonSchema))]`; a field parsed by hand (`deserialize_with`, durations) needs `#[cfg_attr(test, schemars(with = "crate::schema::shapes::…"))]`, else the schema says the wrong shape (the agreement test against `src/schema/good|bad/*.yaml` catches it; a new setting needs a use in a good file). The schema test rewrites `docs/schema/*.json` and fails once ("run again": the binary embeds them). `ductus reference docs` (check.sh runs it) rewrites `docs/reference/` and the SUMMARY block; new metrics go in `api::METRICS`, audit actions in `ductus_store::AUDIT_ACTIONS` (+ schema.md + the UI map), Event Log IDs in `service/messages.rs` `ABOUT`; every CLI option needs a doc comment (test). `${...}` is refused even in a YAML comment of a file read with `parse_yaml`. **The site (0.6.8.1 part B):** `scripts/dev/docs-check.sh` builds the book into `target/book` and runs lychee offline with anchors over the **built HTML** (mdBook makes the ids and rewrites `.md` links; the markdown alone can't show whether an anchor lands); `--network` checks other sites too. The same script runs in `docs.yml` (every docs change; weekly network check that reports without failing) and in check.sh when mdBook and lychee are installed (`scripts/dev/docs-tools.sh`). `docs.yml`'s `pages` job publishes only with the repository variable `DOCS_PAGES=on` (Todd's step; the comment there lists the rest). **Search (0.6.8.3): two builds of one book.** `target/book` (mdBook's search; links checked; the release's offline zip) and `target/site` (`docs-site.sh`: mdBook's search off through `MDBOOK_OUTPUT__HTML__SEARCH__ENABLE=false`, `<main>` and the page's first `<h1 id=` marked for Pagefind, then `pagefind`; what Pages serves). `docs/site/search.js` (book.toml `additional-js`) adds Pagefind's modal only when there's no `#searchbar` and the page isn't `file://`: keep both conditions, or the zip shows a search that can't work. Pagefind's Component UI styles carry three ID-weight `:is(*, #\#)` per rule: an override needs one more (`search.css`). `docs-search-check.cjs` tries both searches in a browser (docs.yml, after both builds; by hand with `ui/node_modules/playwright`). **Timing Pagefind**: 1.5 searches in a Web Worker, whose requests DevTools' throttling neither slows nor counts, and Playwright's `waitFor` re-checks at up to 500 ms intervals: throttle in the test server and stamp times in the page (history.md, 0.6.8.3 part A). **The "Write interfaces" pages' code (0.6.8.2 part B)** is `examples/guides`' (a real project: `ts` blocks start with the file's path and are checked word for word against it; its `ductus test` and `validate` run in the CLI tests): change the project and its tests first, then quote it. An SDK change that alters what those examples do fails there. **Any change to Cargo.lock or `ui/package-lock.json`** (a dependency added, bumped, dropped, or a dev-dependency of ours) needs `bash scripts/dev/dependencies.sh`: `the_libraries_page_is_current` (CLI tests) compares the page's recorded checksums. A notable library leaving the build fails the script: update its list.
- **Accessible names in the UI:** an `sr-only` span adds a space before itself ("Where it's stuck" + `<span sr-only>: lab</span>` reads "Where it's stuck : lab"): start sr-only text with a space and a word, or scope the test by its region instead. A `<label>` wrapping a `<select>` includes the options' text in its name, so `getByLabel("Vendor")` matched both the select (option "Vendor") and the textbox: use `getByRole("textbox", { name })`. Links inside running text need more than color (axe `link-in-text-block`): `p a` is underlined in `index.css`.
- **Docs in the same commit, in full (0.6.8.2):** a change to a setting, command, API operation or anything someone could notice updates its doc comment (the reference), the guide page that explains it (`docs/install/`, `docs/configure/`, the top-level pages) and, when it could surprise, a nuance. YAML examples start with `# <file>` (`, in part` for some settings) and are checked against the schema and the engine (`every_yaml_example_in_the_guides_is_valid`, ductus-core); every top-level setting and connector is linked from a guide (`every_setting_is_explained_in_a_guide`, CLI crate, names the link to write); commands shown were run, outputs are what they printed.
- **Playwright projects run in a chain (`playwright.config.ts` `dependencies`):** one failing test in an early project (an axe finding on `/api-reference`, say) skips every project after it, so a new spec at the end (`releases.spec.ts`) silently doesn't run. Read the summary's "did not run" count, not only the failure. A new API type can trip the API reference's axe check: its schema links sit beside `[]`/`| null` text (`link-in-text-block`), so they're underlined.
- **A release's page and big reports (0.7.4.5):** a check's report holds `validate`'s whole output, ~340 KB at 1,001 interfaces, and a deployed release gathers a check per deploy: `GET /releases/{id}` carries only each environment's newest report (5.1 MB before), `GET /releases/{id}/checks/{check}` the others. Anything new that lists checks or reports: measure it at 1,001 (`bench-release.sh`'s page part) before shipping.
