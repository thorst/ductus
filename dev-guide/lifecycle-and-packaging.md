# Engine lifecycle, Windows, packaging, releases

Read before changing: `ductus dev`, Windows (service, MSI, native build), systemd, the handover, replay, code versions, history, releases, the release job. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- **Deploys in place (0.7.5) in the CLI tests:** a code-only release no longer hands over, so the engine before is the engine after. The tests' `Terminate` (and `Child`) kill their process on drop: the old `drop(engine); let engine = running().await;` after a deploy now kills the engine. Keep the handle (`same(&engine)` checks it's still that pid) and drop only after a deploy that needs the handover. To force one in a test, change one of the project's own files (`code::is_project_file`: ductus.yaml, resources.yaml, docs-schema.yaml, `environments/`, `secrets/`); a `notes.md` isn't one, and its release goes in place with nothing to apply.

- **`ductus dev` (dev.rs)** uses zonky's Postgres binaries (Maven Central, `postgresql_embedded` feature `zonky`), not theseus-rs's: those link the host's `libxml2.so.2`, which Ubuntu 26.04 doesn't have (it ships `.so.16`), so Postgres wouldn't even start. Pinned to 18.6.0 (`VERSION`). The crate's TLS is rustls (aws-lc, like the rest): no OpenSSL; it added 2.5 MB to a 127 MB binary. `File::try_lock` on `.ductus/dev.lock` is the "already running" check (the OS frees it however the process ends); a `postmaster.pid` left by a killed engine means a Postgres still running: `pg_ctl stop` first. `PostgreSQL::is_running` only checks that the pid file exists.
- **Windows (0.6.1):** `cargo build --release -p ductus` works natively (MSVC; VS 2019 Build Tools are enough; Rust 1.99). **Keep `CARGO_HOME` and `CARGO_TARGET_DIR` on one drive** (here both on D:): rusty_v8's build.rs makes a directory symlink otherwise, which needs Developer Mode or an elevated shell ("Failed to create symlink"). From PowerShell: `$env:CARGO_HOME="D:\cargo-home"; $env:CARGO_TARGET_DIR="D:\target-win"`; the binary and the MSI (`packaging/windows/build.ps1`, WiX 5 via `dotnet tool`) are in `D:\target-win`. `cargo` isn't on the Git Bash PATH. Installing the MSI needs an elevated shell (UAC): `scripts/demo-windows.ps1`, started with `Start-Process powershell -Verb RunAs`, needs a database: `ductus dev --database-only` prints one. The service code is `ductus-cli/src/service.rs` (`windows-service`); the engine takes `EngineOptions.stop_request` (the service manager's Stop) and `on_started` (Running is reported then). `--env-file` (`envfile.rs`) is read before clap, so `env = ...` options see it. `pg_ctl start -w` from a PowerShell tool call hangs the call (the server keeps its stdout): redirect or use `ductus dev`.
- **Windows (0.6.5.1):** CI's `windows-tests` job runs `cargo test --release` on `windows-latest` against `ductus dev`'s Postgres (Rust cache shared with `windows`, saved by `windows-tests`). Windows takes ~2 s to report a refused connection (it resends the SYN after the reset), so **every outgoing TCP connection the engine makes itself goes through `ductus_mllp::net::{connect, socket}`** (two SYN retransmissions via `SIO_TCP_INITIAL_RTO`: refused in ~1 s; none would give up on one lost SYN), never `TcpStream::connect` (doctor's "refused" vs "no answer" depends on it; reqwest, ssh and ldap connect by themselves). `localhost` is `::1` first there, so a test with `localhost` and a short timeout against an IPv4 listener spends ~1 s on `::1`. Test helpers that run bash scripts (`PgTls`, slapd) return None on Windows with a note, before looking at `DUCTUS_TEST_*=required`. The repo's own checkout on Windows has `core.autocrlf=true`; Git for Windows on the runner does too: a test that runs `git` names `-c core.autocrlf=...`. On Windows `Path::is_absolute` needs a drive: `/etc/x` joins onto the project's drive (`Resources::without_drive` warns). Run the suite natively here with `CARGO_HOME=D:\cargo-home` and `CARGO_TARGET_DIR=D:\target-win` and a `ductus dev --database-only` URL in `DUCTUS_DATABASE_URL`/`DUCTUS_TEST_DATABASE_URL`.
- **The service's account, the Event Log, the `stopped` marker (0.6.5.3):** `crates/ductus-cli/src/service/` (`run.rs` the service, `eventlog.rs`, `messages.rs`, `account.rs` for `ductus service account` and the installer's hidden `ductus service installed`). **Event Log text is a MESSAGETABLE built into ductus.exe** (`build.rs` encodes `messages.rs`'s table, embed-resource runs rc.exe): a new event ID is a row there (the test reads the table back as Windows does). The engine's log lines that become events are matched by message: their texts are constants in `ductus_runtime::events` (use them in the `tracing` call, `"{}", events::X`); any other ERROR line is event 1100, once a minute per message and target. The installer runs `ductus.exe service installed` after InstallServices (SID type unrestricted, the logon right, event 1005 when the account needs its password); which accounts need a password is `ductus_core::service_account::Kind` **and** the `NEEDSPASSWORD` condition in `ductus.wxs`: change both. Windows' account lookup doesn't take `.\name` (the service manager's way of writing local accounts): replace the dot with `COMPUTERNAME`. **`msiexec /i` of the same MSI file again is a maintenance run, not an upgrade** (nothing removed or reinstalled): `demo-windows.ps1` takes two builds (`-Msi`, `-UpgradeMsi`; each build has its own ProductCode) and checks "Installation completed". A process that formatted our events (`Get-WinEvent`, Event Viewer) holds ductus.exe as the message file: the next uninstall/upgrade waited 152 s in InstallValidate (Restart Manager off by policy here); the demo reads events in a child `powershell`. PowerShell 5.1 turns a native program's stderr into an exception under `$ErrorActionPreference = "Stop"` (the demo's `Native` helper); `net user NAME PASS /add` asks Y/N for passwords over 14 characters. Don't run `ductus dev` from `D:\target-win\release\ductus.exe` while rebuilding it (the file is locked: copy it first).
- **Listening sockets and systemd (0.6.6.2):** every listener the engine opens goes through `ductus_runtime::systemd::listen(host, port)` (never `TcpListener::bind`): under the package's `Type=notify` unit it takes the socket systemd kept for that address (`LISTEN_FDS`/`LISTEN_FDNAMES`, named `tcp-<host>-<port>`, `:` → `_`) or binds and hands it to systemd's store (`FDSTORE=1`). A listener closed on purpose must leave the store first (`systemd::release`, as a drain's MLLP close does) or systemd's copy keeps accepting; `systemd::stopping()` (before the stop closes gates) turns that off; `run` calls `abandon()` on any error so a failed start is refused, not a black hole. Outside systemd (no `NOTIFY_SOCKET`) it's a plain bind. The notify protocol is our own ~40 lines over `libc::sendmsg` (`SCM_RIGHTS`), no libsystemd. Tested with a fake notify socket (unit tests) and under real systemd 255 and 252 in `demo-packages.sh`. In that demo, `on "pgrep -f '[d]uctus gen' ..."`: on Rocky's bash a `bash -c` with a redirect doesn't exec its command, so `pgrep -f 'ductus gen'` matched its own wrapper and every wait ran to its timeout.
- **The handover (0.6.6.3):** `crates/ductus-runtime/src/handover.rs` (control socket, spawning the successor, the takeover's side) and the `takeover` branches of `run_engine`. In a takeover, nothing that changes an interface's rows may run before `claim_now` (it's `take_charge`/`settle_in`, after the old engine said `Released`); anything new in the start that does goes there too, and anything that only reads or registers may stay before. Background tasks that judge or act per interface (alerts, certificate checks) start after the takeover (`background`), or two engines act at once. systemd ignores a takeover's notify messages until the old engine sent `MAINPID` (`NotifyAccess=main`): `systemd::Sockets::main` tracks it, so don't add a `notify` that bypasses `notify_main`. The engine re-execs the path it was started as (argv[0]), not `/proc/self/exe`. Tests: `a_handover_refuses_nothing_and_a_failed_one_leaves_the_engine_running` (CLI, Linux, `DUCTUS_CONTROL` in a temp dir), `demo-packages.sh` under real systemd, `scripts/bench-handover.sh` at 1,001 interfaces. A process a handover started isn't the test's child: stop it by pid (`Terminate`). `gen` is a reserved word in Rust 2024: name a variable `sender`.
- **Replay (0.6.6.4):** `crates/ductus-runtime/src/replay.rs` (runs the code: one isolate on its own thread, one call at a time) and `replay/report.rs` (the comparison, field diffs, text/JSON/HTML); the CLI's `replay.rs` runs the other version as `ductus replay --emit` (JSON lines) and merges the two streams by `(interface, message id, destination)`: **both sides must produce rows in that order** (interfaces by name, messages by id, destinations by name; each message's functions run in the config's destination order), so never parallelize one side without the other. **The engine and the replay decide alike through `worker::Outcome::of` and `worker::meta`**: change how the worker reads a function's result or builds `meta` only there. The `--emit` line format is read by *later* versions (a 0.7 replay runs a 0.6.6.4 installed one): only add fields (with `#[serde(default)]`), never rename or remove. `Isolate::pin_clock` replaces `Date` and `Math.random` before any module loads; `set_clock` before each call. `ReplayServices` refuses writes and marks the call, so a caught error still makes the row not comparable. A record's quarantine caused by the receiver is recognized by the worker's wording (`report::receiver_refused`: "rejected (AR)", "HTTP <n>", "gave up after"): reword those and that function together. **"Identical" is claimed only for what was compared whole (0.6.8.3)**: a sent output against the other version's or a kept one, or a filter/quarantine with its reason (no output exists); a send matched only by the record's "sent" is `same_decision` ("same decision (outputs not compared)"). `Report::outputs_not_compared` is the one sentence the text, the JSON (`outputs_not_compared`), the HTML and `upgrade --check`'s ⚠ all print: change it there.
- **Releases (0.6.8.3 part B):** ci.yml's `release` job (`needs` all four; on a `v*` tag, or `gh workflow run ci.yml -f dry_run=true`) runs `scripts/dev/release-files.sh` (gathers the .deb/.rpm/.tar.gz/.msi/.zip from the `linux-packages` and `windows-installer` artifacts, opens each for its version, builds the docs zip and the CycloneDX SBOMs, writes `SHA256SUMS`), then on a tag attests and makes a draft pre-release (`packaging/release-notes.md`, `@VERSION@`). `scripts/dev/release-version.sh` gives `RELEASE_VERSION`: a tag must equal Cargo.toml; a dry run with `--apply` rewrites Cargo.toml and the workspace crates' Cargo.lock entries to `0.0.0-dryrun.<run>` in that job's checkout (keeps CRLF on Windows). **Anything checking a version string checks the binary's own** (Cargo.toml's `[workspace.package] version`), never `0\.6\.`: `demo-packages.sh` derives its two package versions and checks from it, or a dry run fails it. **Rust is pinned in `rust-toolchain.toml`** (CI runs `rustup toolchain install`, no `dtolnay/rust-toolchain`; rustup auto-installs it locally; a bump rebuilds everything, ~19 min for check.sh); nfpm by version and digest in the Dockerfile. `dist/` is in `.dockerignore` (the release step packages the demo's engine build again, cached). The release job's tools: `docs-tools.sh` + `release-tools.sh` (cargo-cyclonedx, rpm, msitools). cargo-cyclonedx writes a file beside *every* workspace crate: release-files.sh deletes them.
- **The v0.6 demo (0.6.8.4):** `scripts/dev/systemd-box.sh` holds the systemd-container helpers (`box_network`, `box_images`, `box_start`, `on`, `gap`, `wait_*`) that `demo-packages.sh` and `demo-v06.sh` source; both run in CI's `packaging` job, demo-v06 after demo-packages with `BUILD=0` (its own container and network names, so they can't clash). demo-v06's `run '<command>'` is the command exactly as first-interface.md and upgrade.md show it (`@DEB_OLD@`, `@DEB_NEW@`, `@ARCHIVE_NEW@` for versions); blocks marked `<!-- scripts/demo-v06.sh -->` are checked against those lines (`the_pages_show_what_the_v06_demo_runs`), so a changed step changes the page in the same commit, with outputs from the transcript the demo writes. The downgrade's "newer migration" is a stand-in row (9999) in `_sqlx_migrations`: both packages hold one program. `demo-windows.ps1` needs a third MSI (`-NewerMsi`, the next minor version, built in CI) to go back from; its senders use TLS from step 3b on, so a new step that sends uses `Send` (which counts what the receiver should have).
- **What runs, recorded (0.7.3.1):** an interface's code version comes from **the module loader** (`loader.rs` records every project file it reads: normalized text, SHA-256, imports from the same parse as the transpile; `Isolate::code_files` walks them from the interface's module), never from the type checker (1.2–1.4 s at 1,001 interfaces). Workers send each interface's files with their `Ready`; `deployment::versions` (off the async threads, **in a task beside the start since 0.7.4.2**: the record, the check and `save` take the versions from its `watch`; Todd's rule: anything the start doesn't need the result of goes beside it, never in its path) adds interface.yaml and asks `git.rs` (gix, `sha1` only: HEAD and the project's tree read **once**, never `lookup_entry_by_path` per file, which re-reads the `interfaces` tree each time); `deployment::record` writes it **after the interfaces are this engine's** (a plain start: after `background`; a takeover: after `claim_now`, beside `audit::handed_over`). A deployment that can't be recorded is an error, never a failed start. `code.rs` documents the hash's text (`sha256sum` lines): changing it changes every version, so don't. Who asked for a handover travels as `handover::Asked` in `Request` and `Predecessor` (`#[serde(default)]`: engines on either side may be older). `Store::record_deployment` reads first and writes only what's new (sorted, `ON CONFLICT DO NOTHING` for engines writing one file at once). Every engine start in tests and demos records a deployment in the shared test database (like audit rows; they're small and stay); store tests delete theirs with `forget_deployments` and make every file text unique (a `code_files` row is shared by content). **Each delivery's `code_version` (0.7.3.2)** is set only through `Done::code_version` in `update_deliveries`: a new way for a worker to save a decision must carry it (the worker's `code_version()` waits for `deployment::Decided` once), and a new write that sets a delivery's status for any other reason (a person, the engine without code) sets it NULL, keeping the old one in `message_actions.previous_code_version` when there's a row. The ids come from `Store::save_versions`, spawned by the start right after the versions are computed (never awaited in the start path, and never after `claim_now` in a takeover: its workers would wait during the sending pause); `record_deployment` takes those ids. A migration that alters `messages`, `deliveries` or another busy table starts with `SET LOCAL lock_timeout = '2s'` (0027) and alters the least busy table first; `migrations::refusal` words the timeout. Replay's `Event::Interface` gained `code_version` (only added, `serde(default)`).
- **History (0.7.3.3):** `ductus_runtime::history::read` is the one timeline (CLI, API, UI): a new source goes there, with a key that sorts as the timeline does (`key()`: `<micros>-<kind rank>-<id>`, fixed width) and a page read "up to the cursor's time". The docs snapshot is saved by `record_deployment` (in its transaction, `docs::save` with the advisory lock), not by the start; a start without versions saves it with `deployment::docs_alone`. Any new reader of an interface's audit rows that leaves payload reads out must write the predicate exactly as `audit_log_interface_changes` (migration 0028) has it, in a statement of its own (a `$n OR …` flag can't use a partial index). gix walks need `object_cache_size_if_unset` and `set_pack_cache` (feature `pack-cache-lru-static`; we don't take `max-performance`, so nothing sets it by default): without the delta-base cache a 1,000-commit walk took 4× longer. `git::history` keeps walks until HEAD moves (`WALKED`). The handover's warnings travel in `ToOld::Ready.warnings`; a takeover waits for `deployment::check` (≤ 2 s) before `ready`, never after `claim_now`. Store tests that save the docs snapshot take `DOCS` (a save deletes every entry it wasn't given). A migration edited after a local test applied it: undo it on the dev database (drop its objects, `DELETE FROM _sqlx_migrations WHERE version = N`) before the next run; never once it's pushed.
- **Releases (0.7.4.3.2):** `ductus_runtime::release` is the one place that picks a release's files (`pick`), names them (`File`, texts normalized as code versions), computes the id and reads/writes the archive; 0.7.4.3.3's `POST /releases` must recompute the id with `release::id` and read with `release::read`, never a copy. Files come from git's object store (never `git archive` or the working tree: CRLF on Windows); "not committed" uses gix's `excludes` (git's ignore rules) and never walks `.ductus/` (releases are written there). The manifest is computed from an **unpacked copy**, and the gate runs `validate`/`test` **as child processes with `--read-only`** on its own copy (without it they write `tsconfig.json`/`.vscode/` into the copy, and a project they write into is "not committed" at the next release): anything they print about files goes through `release.rs`'s `inside` (the copy's path is never shown). A release made with `--no-tests` makes the gate run every test: a bench or test measuring "nothing changes" must check a release made with its tests. The manifest only adds fields (`serde(default)`); `FORMAT` is what a reader refuses above.
- **Releases stored (0.7.4.3.3):** `api/releases.rs` and the store's `releases.rs`. A received release is read with `release::read_bytes` (the same reader as files); the check rebuilds the archive from the database and runs the CLI's `release check --json` as a child (`handover::executable`, never `current_exe`: after a package upgrade `/proc/self/exe` is "(deleted)"), so the gate has one implementation: change it in the CLI. The child runs at nice 10 / below normal (measured: no difference to the engine's intake on 4 cores / 8 threads, which a check halves while checks run back to back; architecture.md "Stored, measured") and inherits the engine's environment (secret key, `--env-file` values): anything the gate needs must come from there or its arguments. One check per engine (`CHECKING`); tests that check through the API run one at a time per engine. `deploy` is "operators and above" in two places that must agree: `ductus_store::allowed_for`/`Principal::can` (refused at grant, inert on a viewer) and `LdapGroups::access` (a viewer's directory group gives none); the UI's `OPERATORS_ONLY` unticks it for viewers. The same files give the same release id every run: demos and tests delete their `releases`/`release_checks` rows (`forget_releases` in demo-release.sh) or the second run is "stored before"; `code_files`, `release_folders` and `release_blobs` rows are shared by content and stay.
- **Deploys (0.7.4.4.1):** `deploy.rs` (release mode, the "replaces" check), `api/deployments.rs`, the CLI's `deploy.rs`. **Release mode connects to the database before reading any project** (`run_engine`'s first block): the release decides `root`, so anything new that reads the project at the start must come after it, and a takeover's `predecessor()` is read there first (its `Asked::release` names the release). An engine with nothing deployed runs `DIR/none` (an empty `interfaces/`); the "no interfaces" refusal is skipped only then. **A deploy is a handover asked in-process** (`handover::Asker` → the control socket's own channel, `Reply::InProcess`): never spawn a successor any other way, or two handovers can run at once. The engine being replaced answers the request: its stop awaits the API server only *after* `Successor::released`, which is why the answer can come at all; keep it that way (moving the API's await before `released` deadlocks every deploy). The "replaces" check is one function (`deploy::replaced`) for the folder-mode warning at start and the deploy's refusal: change the rule there. **"Same person" is by name**: a deploy's is the token's or account's name, a folder-mode start's the OS account, so tests that want a refusal use two tokens. The deploy's own check and the new engine's start both run it; the new engine's warnings are what `deployment_changes.warning` keeps. **The project version is per project** (`project_running` joins `releases.project`): tests and demos on the shared database deploy projects with unique names (`release_project`'s temp folder) or an earlier run's version would be "someone else's". A gate run in tests makes `ductus-release-*` and `ductus-check-*` folders in the temp dir: a test that counts them sets its own `TMPDIR` (the deploy test's gate raced `the_gate_tests_…` once). Demos stop a release-mode engine by the pid in `engines` (`running` in demo-release.sh): after a deploy it isn't the script's child. **A demo whose releases have the same id every run must also unname the deployments that ran them** (`UPDATE deployments SET release_id = NULL …`, demo-release.sh's `forget_releases`): once the release is stored again, an earlier run's deployment makes "the release last deployed here" that one, and the "empty" release-mode engine starts on it (demo-release passed alone, then failed its second run inside demos.sh).
- **Promote and roll back (0.7.4.4.3):** where a release went is `ductus_store::Store::release_places` (this database's `deployments`, each environment's first, plus `release_places`: what files said, merged at every `POST /releases` **even when the release was stored before**, since a stored release keeps its first manifest). The record rides in the manifest's `deployed` (outside the id): never add an archive entry for it (`release::read_from` refuses entries it doesn't know, so older engines would refuse the file). `release::rewrite` adds it to a local file through a `.partial-<pid>` file and a rename. The environment's rules are one function (`deploy::rules`: requires, branches), the rollback target another (`deploy::rollback_target` over `release_runs`: consecutive deployments of one release are one run, `deployments.rollback` marks a rollback's first). `--force` never skips the rules; a rollback never meets them. `Asked::rollback` carries the flag to the new engine, which records it (`Who::rollback`). Tests and demos deleting releases also delete `release_places` (`testing::forget_releases`). `demo-promote.sh` makes three databases (`ductus_promote_{dev,test,prod}`) on the dev server and drops them: the dev login needs CREATE DATABASE. **On Windows the service writes only where the installer lets it** (`ductus.wxs`: `LOGDIR` and, since 0.7.4.4.3, `RELEASEDIR`, each with its own icacls custom action): anything new the service writes needs its folder and grant there, or it fails only as the installed service ("Access is denied", event 1003), never in CI's tests. `scripts/demo-windows-deploy.ps1` (CI's windows job, after demo-windows) deploys to the installed service; it moves an existing `C:\ProgramData\Ductus` aside and puts it back, so it's safe on a developer's machine.
- **The in-process handover (0.7.4.4.2):** without a control socket (Windows, containers, a plain `ductus run`) or as PID 1, a handover's new engine runs as a task in the same process (`handover::in_process`, a channel instead of the socket pair; `systemd::listen` keeps a copy of every listening socket on every system). So **an engine's run must leave nothing behind**: anything new that loops or waits for good (a listener loop, an hourly job, a background round, a thread) ends with the engine: spawn it under `ended` (`run_engine`'s token, `Engine::ended`; `token.run_until_cancelled_owned(fut)`) or a token cancelled at the stop, and never rely on "the process exits". A loop parked on a closed gate (the MLLP accept loop after a stop) waits forever otherwise; the API server outlives its 5 s wait through live-update streams. `tests/in_process.rs` counts tokio's live tasks and the threads across reloads: run it after adding anything that spawns. `run_one` is boxed with `+ Send` on purpose (an engine's future spawns the next one's: the compiler can't prove that cycle `Send`). Process-wide statics are shared by both engines while they overlap (`systemd::SOCKETS`, `handover::RELOADS`, the SDK's transpiled code): per-engine state never goes in one. The new engine's settings come from `EngineOptions::rebuild` (the CLI's `envfile::run_args_again`: clap's env lookup turned off, the env file read again; **never `set_var`** at a reload: other threads read the environment). SIGHUP is registered once per process (`listen_for_hangup`) when an engine takes handovers; `ductus dev` doesn't, so it still ends on SIGHUP. On Windows `ductus handover` runs `sc.exe control Ductus paramchange` (windows-service 0.8 can't send ParamChange itself) and the service accepts `PARAM_CHANGE`; its Stop is a `CancellationToken` every engine in the process sees (`Notify::notify_one` woke only one). The image has no `DUCTUS_PROJECT` (its working folder `/project` is the default): clap rejects an empty `-e DUCTUS_PROJECT=`, so release mode needed it gone. **Measure memory over many handovers, not one**: glibc keeps what an ended engine's threads freed (94 → 221 MB over ten at 1,001 interfaces, still rising) until give_back_freed_memory trims it; IN_PROCESS=1 ROUNDS=10 scripts/bench-handover.sh prints memory per round, and MALLOC_ARENA_MAX=2 tells allocator retention (flat) from a leak (still rising).
