# The VS Code extension (`editors/vscode`)

Read before changing the extension, or anything it reads: `ductus test --json`, `test --list --json`, `validate --json`, `--inspect`'s messages, the `launch.json` configurations `ductus types` writes. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- **It is a client of the CLI's `--json` only** (v0.7 design F): no language server, no second implementation of a check. A field it needs goes into the CLI's JSON first (only ever added: the pinned `test_reports_where…`/`validate_json_…` tests), and `src/lines.ts`'s types follow. Everything that doesn't need VS Code lives in `lines.ts` and is unit-tested under plain Node (`node --test`, type stripping: keep that file erasable-only and free of imports with no `.ts`).
- **Debugging from the Test Explorer spawns `ductus test --inspect=127.0.0.1:<free port> --json` itself and *attaches* js-debug** (`type: node`, `request: attach`), started when stderr says `waiting for a debugger on`. That way the extension reads the results from stdout while the debugger is attached (`--inspect`'s messages go to stderr, stdout stays JSON). The `ductus` debug type instead resolves to js-debug's *launch* with `attachSimplePort` (what `ductus types` writes and demo-debug.sh drives): there nobody reads stdout. Both are checked in a real VS Code (`test/e2e`); js-debug's attach to our inspector worked first time with `attachExistingChildren`/`autoAttachChildProcesses` off.
- **Test item ids are JSON arrays** (`["t", root, interface, name]`): VS Code refuses ids containing `\0` ("Test IDs may not include the … symbol"), its own separator.
- **The e2e tests' races are the tests' own**: discovery streams items (wait for the one you assert on, not the first), and a debug session's end arrives after the run that started it has finished; a test that waits for "a session ended" must wait for *its* session (`onDidStartDebugSession` by name), and a debugged test waits for `!activeDebugSession` before the next starts.
- **`npm run package` copies the repository's LICENSE** into the folder (gitignored) and `vsce package --no-dependencies`: the bundle (esbuild, `dist/extension.js`) is the only code shipped, so the libraries page (`dependencies.sh`) has nothing of it. The `.vscodeignore` is an allow-list.
- **`test/e2e` needs a display**: `xvfb-run -a` (installed in WSL and on CI's Ubuntu, with VS Code's libraries: libgtk-3, libnss3, libasound2, libgbm1). VS Code is downloaded once into `editors/vscode/.vscode-test` (gitignored). Its log is noisy (GPU, D-Bus, its built-in chat looking for a sign-in): demo-vscode.sh filters it. **On CI Mocha colours its ✔ marks** (FORCE_COLOR) despite `color: false`: the demo's greps found nothing and it failed with all 7 passing; it strips colour codes first (try it locally with `FORCE_COLOR=1`).
- **npm 11 doesn't run install scripts it hasn't been told to allow** (esbuild's, vsce-sign's postinstall): both work without them (esbuild's platform binary comes as an optional dependency).
- **Deploy to dev (0.7.6.3.1, `src/dev.ts`) talks to the engine's API directly** (`fetch`, Node's own: no dependency), the one place the extension isn't a CLI client: `POST /engine/reload` answers the same `ReloadReport` `ductus reload --json` prints. It finds the engine and token through `.ductus/dev-engine.json` and `.ductus/dev-token` only (never settings). The editor title's button shows on the `ductus.devRunning` context, set from a file watcher on `dev-engine.json` (no polling). The e2e test starts its own `ductus dev --api-listen 127.0.0.1:<free>` in the project copy and kills it with SIGTERM; `demo-vscode.sh`'s wrapper must set `CARGO_TARGET_DIR` or `BIN` falls back to the repo's `target/` (a stale binary).
- **Promote… (0.7.6.3.2, `src/promote.ts`, `src/engines.ts`) runs `ductus deploy --json`; it doesn't call `POST /deployments` itself**: the CLI stores a file first, fetches with `--from`, and writes the record of where it went into the release file, all of which a second implementation would get subtly wrong. Tokens reach it through `DUCTUS_API_TOKEN`/`DUCTUS_FROM_TOKEN` in its environment (`process.ts`'s `env`), never its arguments (other users can list them). The extension's own calls (`GET /session` to check a token, `/engine`, `/releases` for the picker) use `fetch`. A deploy that fails before the engine answers prints anyhow's `Error: …\n\nCaused by: …` on stderr and no JSON: the notification takes the first paragraph. Tokens are in `context.secrets` keyed `ductus.token:<url>`. **The e2e test answers the token prompt by replacing `api.engines.ask`** (an input box can't be typed into reliably from a test), and calls `api.promote.promote(choice)`, the command's flow without its pickers; `demo-vscode.sh` starts the two release-mode engines (own databases, ports 17883/17893) and hands their URLs and tokens over in `DUCTUS_E2E_ENGINES`. The test project's folder name is the release's project: the picker filters an engine's releases by it.
- **History and Debug this message (0.7.6.3.3, `src/history.ts`, `src/message.ts`)**: the History view reads only while visible (`onDidChangeVisibility`; an editor change marks it stale), so nothing runs for a hidden view. Your dev engine is a `Reach` (engine + token from `.ductus/dev-token`), not a `Signed` (no `GET /session` check); `Engines.get` takes either. Debug this message is a js-debug *launch* with `attachSimplePort` (as `debug.ts`'s `try`) whose `env` carries `DUCTUS_API_TOKEN`; `ductus try` checks the message is the named interface's. **The `vscode://` link's extension id is `ui/src/lib/vscode.ts`'s `EXTENSION`**, pinned to package.json's `publisher.name` by `vscode.test.ts`: when the Marketplace publisher replaces the placeholder, both change together. A link's engine must be dev's or a named one (`sameEngine`: localhost ≡ 127.0.0.1); anything else asks with a modal. **The e2e's dev engine is shared**: the Deploy to dev test leaves it running (stopping it on its own failure) for the History/Debug test after it, which stops it; `suiteTeardown` stops it if a test in between failed. The test calls `api.messages.fromLink(query)` rather than opening a `vscode://` URL (no browser, and VS Code's own "allow this extension to open the link?" prompt).
- **Code lenses, go-to-definition and `script:` links (0.7.6.4, `src/wiring.ts`) read `validate --json`'s `uses`**, kept per project by `problems.ts` from the run it makes anyway: no process of their own. The declarations come from the type checker (`check.js` `findExports`, run only with diagnostics, i.e. by `validate`), so a re-export resolves to the shared file; the interface.yaml places from `yaml::locate_value` (a scalar's span; a map's key falls back to `locate`). **A dirty document gets no lenses or definitions**: the run's lines may have moved, and a lens in the wrong place is worse than none. Lens clicks use VS Code's own `editor.action.showReferences` (arguments must be a `Uri`, a `Position` and `Location`s, not plain objects). Positions: Rust's columns count characters, VS Code's UTF-16 units; they differ only past the BMP, as for Problems. The e2e test asks VS Code through `vscode.executeCodeLensProvider`/`executeDefinitionProvider`/`executeLinkProvider`, so it checks what the editor would show; **those commands need the document open** (`openTextDocument` first), or they throw a bare "Illegal argument" from the workbench (no model for the URI).
- **demo-vscode.sh lists every e2e test by name and the `N passing` count**: add a new test to both. Until 0.7.6.4 it checked only those, so a new 11th test failing still printed PASS (10 passing, every listed one ✔); it now also fails on any `N failing` line.
- **`test` and `validate` write the editor typings only when they changed** (`write_if_changed`, 0.7.6.2): the extension validates on every save, and a rewritten `.ductus/types/ductus-sdk.d.ts` made VS Code's TypeScript server check the project again each time.
