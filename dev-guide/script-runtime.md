# Script runtime: V8, the loader, the SDK, validate/test

Read before changing: deno_core/V8, the module loader, ops, the runaway guard, the type checker, `console`, the inspector, `validate`/`test`. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- **deno_core 0.412**: scopes via `deno_core::scope!(scope, &mut runtime)`; try/catch via `v8::tc_scope!(let scope, scope)`. `deno_error` must be pinned `=0.7.1`. Ops: `#[op2]` + `#[string]` for `Option<String>` returns, `#[serde]` for JSON. Extensions via `deno_core::extension!` with `esm = [dir "src", "file.js"]`.
- `call_with_args`/`resolve` return futures that **don't borrow the runtime**; drive the event loop separately (`poll_event_loop`). That's how concurrent async transforms work.
- Module specifiers must be canonical paths (`file_url` canonicalizes); `..` in paths broke module identity once.
- TypeScript transpile removes unused imports: tests that check import behavior must *use* the import.
- **Type errors come from TypeScript 7's own `tsc`, a process (0.7.9.2, `tsc.rs`)**, not from V8: TS 7 is a Go program and 7.0 has no API, so the command line (`-p tsconfig.json --pretty false`, run in a temp folder holding the config, with `files` listing the project's paths, and the SDK typings) is the interface; validate's options are fixed in `tsc.rs` `OPTIONS`, never the project's tsconfig. **`tsc` panics without its `lib.*.d.ts` beside it** ("bundled: …/lib.d.ts does not exist; this executable may be misplaced"): ship and fetch the npm package's whole `lib/`, never `tsc` alone. It prints paths **relative to its working folder** (`../../p/a.ts`): `parse` joins them to the temp folder and takes out `..` lexically; never canonicalize one side only (Windows runners' temp is an 8.3 short path). **tsc can't open Windows verbatim paths** (`//?/C:/…`, what `canonicalize` gives: a release unpacked for its check has them): every deploy and gate test failed on Windows CI with TS6053 "not found" until `check` gave them plainly (`plain_path`) and mapped its findings back. Exit 1 or 2 with lines = errors (2: in the config); anything else, or a failure that printed nothing, is `tsc`'s own failure (`DUC127`), and a line `parse` can't read is kept as code 0 (shown as `DUC127`, never dropped). Where it's found: `DUCTUS_TSC` alone when set; else `<exe dir>/typescript/`, `<exe dir>/../lib/ductus/typescript/`, the per-user cache `typescript-<TSC_VERSION>/` (`scripts/dev/tsc.sh`; tests and CI need it run first: check.sh does). A version bump: `tsc.sh`'s `VERSION` and both SHA-256s (npm's `dist.integrity` is SHA-512 of the same tarball: compare to be sure), `TSC_VERSION` (a test keeps them equal), `dependencies.sh`; then demos for the docs' `types: no errors (TypeScript …)` outputs.
- **deno_core reads `extension!` `esm = [...]` files from the build machine's disk at every isolate start** (by absolute path; only a startup snapshot embeds them): an installed binary panicked "Failed to initialize a JsRuntime: No such file or directory". `ops::extension()` replaces the list with `ascii_str_include!` (`the_extension_reads_nothing_from_disk`). Any new JS in an extension goes through it. Packaging tests (`demo-docker.sh`, `demo-packages.sh`) run the binary away from the source tree, which is what catches this.
- **Runaway guard (`ductus-script/src/guard.rs`)**: terminate only from inside an `IsolateHandle::request_interrupt` callback (runs on the isolate's thread; check the call generation first), never `terminate_execution` from the watchdog thread (a finished call's successor would be killed). Reading the stack there needs a context: the main context is kept in an isolate slot (`MainContext`) and entered with `v8::scope_with_context!`. After termination, `cancel_terminate_execution` (deno_core re-arms termination in `exception_to_err`). A termination during the event loop **drops all queued microtasks**, so every in-flight async transform on that isolate hangs: fail them all (worker's `interrupted` watch). `Isolate::settle` stringifies errors: use `drive` + `output` where a typed error (`Runaway`) must survive.
- **Loading code into a running isolate (`Isolate::evaluate`, 0.7.5.1): drive the event loop only until the module's own `mod_evaluate` future resolves, never `run_event_loop` to idle.** Idle means every op in flight, other interfaces' slow `fetch()`/`db()` included: a deploy's load waited 202 ms for another interface's 300 ms lookup, holding every interface on the thread (the worker's `Gate` is closed during a load), and the wall-time guard would count it. But the module's result comes from a promise `then` (a microtask) and can resolve **a tick after** the loop reports idle: treating the first idle as "never settles" failed starts at 1,001 interfaces (not reproducible with 300 in a test). Poll again on idle (bounded), as deno_core's own `with_event_loop_future` does. And poll the loop **before** the future, its error winning: a module that throws at its top level resolves `mod_evaluate` with **Ok** and reports the exception through the loop (watching only the future loaded it: "entry not installed"). Tests: `a_module_that_throws_at_its_top_level_doesn_t_load`, `code_loads_while_another_interface_s_call_is_in_flight`; the 1,001 case only `scripts/bench-deploy.sh` reaches.
- **HL7 definitions (`sdk/src/schema.ts`) are runtime behaviour, not only editor help**: `isComposite` decides whether `seg[n]` is a string or a Field, so defining a segment turns its simple fields into strings for existing code. A new segment or type needs: its field count in `schema.test.ts`'s v2.5 table, a sample message that reads it by name, its name in the nuance's list (`docs/nuances/transforms.md`) and formats.md's table, and a release-notes line. Every type it names must be in `DATATYPES` or `PRIMITIVES` (a test fails otherwise; a typo would silently make a composite field read as a string).
- **deno_ast wants the byte order mark stripped** before `parse_module` (it `debug_assert`s, so only debug builds panic; release copies the text). `loader::parse` strips it.
- **Sockets belong to the runtime that opened them.** The sqlx pool is shared with intake: worker threads must run store calls on the main runtime (`Worker::db`), or a busy V8 thread delays other interfaces' ACKs.
- **The code analysis is Rust (`analysis.rs`, 0.7.9.1), not the type checker**: `db`/`api` names, imports, global `console` calls, exports with places, async/waits and the lints `DX1`–`DX5` come from deno_ast parsed **with `scope_analysis: true`**, names followed through imports, aliases, namespaces and re-exports (`Project::export`/`binding`/`expression`). Never match a name by its text: compare `Ident::to_id()` (a local `db` has another `SyntaxContext` than the import), and a global is `ctxt == ParsedSource::unresolved_context()` (that's how `console` is told from a parameter named `console`). Positions: swc's `BytePos` starts at 1 (`StartSourcePos`); columns are UTF-16 units (`Lines::at`), as TypeScript and editors count. validate's thread runs `analyze_syntax` and `tsc` side by side (`Types::check` in project.rs); nothing there needs V8 or a runtime entered any more.
- **Places and findings (0.7.1):** every project YAML file loads through `ductus_core::yaml` (`parse`, `substitute`, `from_value`): its errors are `yaml::Located` (stage + key, or the parser's position) and display as before. A new rule in `InterfaceConfig::validate` uses the `refuse!([key...], ...)` macro (or `yaml::at`) so `validate --json` can point at it; a new check across interfaces returns `yaml::Problem` (text, interface, key). **A new `validate` finding needs a `DUC` code in `findings::CODES`** (with what to do: it's the reference page `reference/validate.md`; `every_code_is_listed_and_every_listed_code_is_used` reads project.rs) and goes through `Report` (`report.add`, never `println!`), or `--json` loses it; the text output must stay as it was. A code keeps its meaning: new check, new code. The JSON of `test --json` (JSON Lines) and `validate --json` is a contract for editors and CI: only add fields (`test_reports_where…`/`validate_json_…` pin the keys). An error from interface code is shown through `ductus_script::errors::readable` (the worker's reason, `ductus test`); replay compares reasons without its `(file:line:col)`. The SDK's `internal()` (testing.ts) and `errors::internal` must name the same frames. **`cargo test -p ductus-core` alone rewrites `docs/schema/*.json` with keys sorted** (serde_json's `preserve_order` comes from another crate in the workspace): `git checkout docs/schema` after it, or test the workspace.
- **`console` in interface code (0.7.1 follow-up):** deno_core's own console writes straight to stdout; ops.js replaces it (wrapped by `Deno.core.wrapConsole` with V8's, so an inspector sees the lines too) and every line goes through `op_ductus_console`, which reads `ops::Console` from the OpState: `Log` (the engine and replay: tracing target `script`, the place from the stack, the environment's `console:` level via `Isolate::console_to_log`) or `Captured` (`Isolate::tests`, `capture_console`; the SDK runner takes each test's lines with `__ductus_console_take`). An isolate that can run project code where stdout is a contract (`--json`, `--emit`) must capture or log, never be left on the default. **ops.js must stay ASCII** (`ascii_str_include!`: a `µ` in a comment is a compile error). validate's `DUC206` reads the type checker's `Analysis::console` (calls of the *global* `console`, `topLevel` when outside every function).
- **The inspector (0.7.2.1):** an inspected isolate (`Isolate::with_inspector`) **must run on a current-thread runtime of its own thread**: deno_core's inspector spawns `!Send` tasks (`deno_core::unsync::spawn`), and on the CLI's multi-threaded runtime one ran on another worker and panicked ("RefCell already mutably borrowed", printed but the run went on). `wait_for_debugger` also needs a Tokio context. The server (`ductus_runtime::inspect`) is on its own thread: never serve it from the isolate's. A paused frame's `url` is empty in CDP (deprecated): tests find the script by `location.scriptId` from `Debugger.scriptParsed`. A session that ends while paused lets the call go on (V8). Every new place that debugs (`try`, `dev --inspect`) goes through `inspect::Target` with the isolate's `DebugSwitch`, or the guard kills paused calls. A test that sets a tracing subscriber sees swc's debug lines too when it's the first in the process to load the SDK: filter by target. `scripts/demo-debug.sh` drives VS Code's js-debug (`scripts/dev/js-debug.sh` fetches it, pinned by version and SHA-256; `scripts/dev/dap-client.mjs` speaks DAP as VS Code does, answering js-debug's `startDebugging` for the child session; program output needs `outputCapture: "std"`). **`ductus dev --inspect` (0.7.2.3)**: `EngineOptions::inspect`; a debugged interface gets a worker thread of its own (`worker::spawn_thread`'s `inspector`), and **`drive_event_loop` must keep a pending poll on the event loop even when nothing is in flight**: deno_core wakes only the task that last polled it when a debugger's message arrives (with the old "ready → wait for kick" an idle interface never answered a debugger; the CLI test catches it). Code that runs after a session ends goes in `inspect::Attached`'s drop, not after the bridge's loop (a server shutdown drops the task). The engine's stop calls `Inspector::close` first, so a paused call can't hold the stop; that message is then sent or left pending depending on a race with the workers' stop (both happen: the test accepts either and checks it's delivered once after the next start). `dev` opens the port before Postgres. `demo-debug.sh`'s dev part reads the configuration from the `launch.json` `ductus types` writes (`dap-client.mjs` `DAP_CONFIG`) and waits for js-debug to verify the breakpoint before sending (in already-loaded code it's placed asynchronously); its trap stops a dev left behind before deleting the folder (else its Postgres runs on in a deleted folder). **`ductus try` (0.7.2.2)** is `ductus_runtime::try_message`: the replay's `ReplayServices`, `decide` and `seed` for one message on a thread of its own (current-thread runtime + LocalSet, as replay; the inspector needs it); it must decide exactly as replay and the worker do, so change those, not a copy. Destinations are run by name (the config's map is sorted), as the engine's workers and replay. `demo-try.sh` reads a stored message from the database and through the API (`--from`), checking the audit row and that the receiver got nothing more.
- **Loading code into a running worker thread (0.7.5.1, `worker::Command::Replace`):** `Isolate::add_functions` holds `&mut Isolate` across awaits, and on a running thread the isolate is an `Rc<RefCell>` that the event-loop driver and every in-flight transform borrow: a borrow held across an await makes theirs panic ("already mutably borrowed"). The thread's `Gate` is closed for the load: `Script::transform` waits at `Gate::opened` before `begin_function` **and before `settle`** (the load's own `run_event_loop` settles other interfaces' promises), the driver uses `try_borrow_mut` and is kicked after. That `run_event_loop` also waits for every op in flight on the isolate, so a load lasts at least as long as the slowest async call there. A runaway during a load comes back as `ductus_script::LoadRanAway` (same text as before): V8 dropped every queued continuation, so the worker tells `interrupted` and the calls in flight retry. A file loaded again from the same path is the old module (V8 keys by URL): only new folders (a release's) load new code.
- **A fresh isolate for a running thread (0.7.5.3.3, the isolate budget) goes on a new thread.** rusty_v8 150 enters an `OwnedIsolate` when it's made and panics ("must be dropped in the reverse order of creation") when isolates on one thread are dropped out of order, so "make a new isolate beside the old one and drop the old" can't work on the same thread. `Kept::renew` spawns a new worker thread with no jobs, `Command::Load`s every interface there (held, not started), then per interface `Replace` with no jobs on the old thread (handing a respond-mode interface's requests) and `Command::Start` on the new; the old thread ends once no strong sender of its commands is left (its `Budget.me` is a `WeakUnboundedSender` for that reason) and it hosts nothing. The count is `worker::LOAD_COST` per load (from `Isolate::code_bytes_read`, the loader's bytes read); re-measure with ductus-script's ignored `superseded_code_costs` if loading changes. In folder mode a renewal compares the files the new thread loaded with `Interface::code` (set at start, `add`, `replace`): it must never load an edit nobody reloaded. **Measure its memory with `give_back_freed_memory` after each renewal** (it's there): without the `malloc_trim`, bench-deploy phase 10 still rose 278 → 297 MB over 100 deploys (glibc keeps an ended thread's arena), with it flat at ~230 MB.
- **Key functions (0.7.7.3, `ductus_runtime::key_functions`)** run on one thread per engine (made at the first load), one isolate with no `Services`, never a worker's (a slow transform there would hold senders' ACKs). The SDK binds them with `__key` (not `__invoke`): synchronous, the answer always a string, a promise refused there. `Isolate::add_keys` loads the module with `DEFAULT_TIMEOUT` but registers `KEY_TIMEOUT` (50 ms) for its calls: a first load evaluates the SDK too, far longer than a key call. The thread blocks on a `std::sync::mpsc` between commands (the isolate needs a runtime entered, `block_on` only for a load); one message a trip costs ~60 µs of thread wake-ups in WSL whatever the channel (tokio's measured the same), a batch's messages share them. A module path loaded again (a deploy in place) loads under a new generation, so its new text is read; the first load of a path keeps generation 0 (so shared imports load once). **A deploy that changes only code takes `replace_interface`, which keeps the intake's `Settings`**: it loads the key functions again and `Intake::rescript`s, or the old key code would go on. Superseded key code stays in that isolate until the engine restarts (tiny: no budget renewal as workers have). `Document::read` of a `KeyPath::Script` is None without the thread's values, which is how `validate`'s fixture check (DUC207) leaves such keys out. validate's DUC208 reads `Export::r#async`/`waits` from `analysis.rs` (only the exported function's own body; async = `async` or a declared `Promise`/`PromiseLike` return type, no inferred types).
- **`ductus test` runs one test a call (0.7.6.1).** The SDK's `__runTests` takes `index` (the test at that place among those `filter`/`names` choose; `[]` past the last), and `run_suite` (ductus-cli project.rs) calls it per test. It used to be one call for the whole suite, with results in a JS array: a runaway (V8 drops every pending continuation, the runner's own included) lost them all and the CLI printed "failed to load tests". Now a `Runaway` from `run_tests_with` (typed from both `call` and the event loop: keep it so, no `.context` on that path) is that test's failure; the old isolate is **dropped before** the fresh one is made (rusty_v8: a thread's isolates must drop in reverse creation order), the fresh one loads the same files (its load-time `console` discarded), and names the runaway test by listing `index`. Under `--inspect` the old isolate is kept (the debugger's session is its) and the rest are `notRun`. A test isolate's limit is `--timeout` (default `DEFAULT_TIMEOUT`, 5 s), never the interface's `timeout`: `Isolate::set_tests_timeout` changes the suite entry's guard budget, which `arm_for` (the call) and `arm_any` (the event loop, the shortest registered budget) both read; set it on a fresh isolate too. Loading the test files keeps 5 s. CLI tests that make a test run away pass a short `--timeout` (300 ms, 1 s) rather than wait 5 s.
- **Changing an interface's destinations while it runs (0.7.5.1 item 3, `in_place.rs`):** a worker finds its wake-up and its lanes' drain state **by its destination's place** (`Wake::get(slot, index)`, `Lanes::watch(index)`), so a destination added, removed or reordered gets a new `Wake` (never a resized one), and is refused (`NeedsHandover`) when the interface's lanes were changing at the start: `Lanes.changing` stays `Some` after it settles, sized for the start's count. Per-destination counts live in `control::RunningDestination`, not `InterfaceStats` (whose counts must go on), and everything that shows destinations reads that list, never `config.destinations()` zipped with another vector. **A replacement worker must read first**: the start's `Waiting` list makes a worker skip its first read when its interface had nothing waiting, but the worker it replaces may have stopped mid-batch; `Interface::jobs` gives replacements an empty one. `Intake::retarget` waits until no store holds the old targets (`Arc::strong_count`) before `reconcile`, or a message stored with the old destination list would be missed.
- **`ductus bench interface` (0.8.2, `load_test.rs`) mocks lookups as the engine's `Services`**, each answering after a latency **on its own timer thread** (`load_test::Timer`, condvar deadlines), never `tokio::time::sleep`: tokio's timer counts whole milliseconds and rounds up, so a 1 ms mock waited 2 and a message with two lookups measured ~3 ms slower than its code. **On Windows a condvar's timeout ends on the scheduler's ~15.6 ms tick** (a 1 ms mock waited 14 in CI, and the report blamed "the threads outnumber the cores"): there `load_test::Wakeup` waits on a high-resolution waitable timer plus an auto-reset event that a new deadline sets (`WaitForMultipleObjects`, nothing polls): 1 ms waits ~1.6 ms, 40 ms ~40.6 (native, 2026-11-27). Even so a call after an idle wait is ~0.3 ms late and the code after it runs slower (the CPU waking; WSL, 2026-11-27): that's real, and `waited_ms` reports it, so don't "fix" it by spinning (that would burn the core the per-stage CPU numbers measure). **And the slowness lasts past the wake-up (0.8.2.4)**: with 20–40 ms mocks, `decode` (pure compute) took 30–40 µs against 4 µs with 0 ms mocks, the code 10× too, so `wall - lookups_ms` is the code's *cold* pace. Anything that extrapolates to a busy thread (the verdict's "without the waits", respond mode's capacity and its CPU at the peak) uses `Load::own_warm_ms` from a second 1 s run with `Mocks::at_once()`; a queued interface's CPU at its peak stays the measured (cold) one, since its worker really waits on each message. `--real` can't make the second run, and says so. Writes are answered as done, not refused as `try`'s are. A runaway ends the run (the engine would restart the isolate: no number would mean anything). Test mocks (`mock.db` in a test file) are JS closures and can't be lifted into a load test: rows come from `--rows NAME=FILE.json`. **Per-stage times (0.8.2.2)** come from the SDK's `__invokeTimed` (bound only by `Isolate::add_functions_timed`; the engine's `__invoke` is untouched): it calls `__ductus_stamp(n)` (ops.js → `op_ductus_stamp`, which records an `Instant` only when `Isolate::time_stages` put `ops::Stamps` in the OpState) at 0 start, 1 message read, 2 result there **or thrown** (a quarantine is still timed), 3 serialized. Keep it the same as `__invoke` in everything but the stamps (`formats.test.ts` compares them). The function's own time is stage 1→2 less the lookups' waiting, counted as a **union** (`load_test::Waiting`: `Promise.all` of two 5 ms lookups is 5 ms, not 10). CPU per message is the thread's CPU clock (`thread_cpu`: Linux `CLOCK_THREAD_CPUTIME_ID`, Windows `GetThreadTimes` in ~15.6 ms ticks, else None). The heap is read three quarters into the warm-up and the code warms again after (`low_memory_notification` can drop compiled code). A test can't compare against a second `Isolate` made on the same thread (rusty_v8 panics "do not belong to the same Isolate"); and `Date.now()` counts whole milliseconds, so a 20 ms busy loop in JS may be 19.x ms by `Instant`.
- **`validate` and `test` on threads (0.7.4.3.1):** `spread::in_order` (ductus-cli) runs a job per interface on threads, each with a current-thread runtime, and hands results back in the interfaces' order, so what's printed is what one thread printed: anything new that `validate`/`test` print per interface goes in the ordered callback, never from a worker thread. **The one exception is `test --json` (0.7.6.1, Todd's call for the Test Explorer): its lines are printed from the suite's thread as each test ends** (`run_suite`'s `told`; `println!` locks stdout per line, so lines never mix), and the text output still comes from the ordered callback (`Ran`). A new per-test field goes in `test_json` and `test_text` both. **Each interface keeps an isolate of its own there**: sharing isolates as a start does made a verdict depend on load order (code reading another interface's `globalThis` passed one run in three). **A `JsRuntime` made on a plain `std::thread` aborts** the first time V8 posts a delayed task ("created outside of a tokio runtime context"): enter a runtime first (`runtime.enter()`, as validate's type-check thread did while it ran TS 6 in V8). The SDK's JavaScript is transpiled once per process (`loader::sdk_javascript`): an SDK change needs nothing else.
