# Script runtime: V8, the loader, the SDK, validate/test

Read before changing: deno_core/V8, the module loader, ops, the runaway guard, the type checker, `console`, the inspector, `validate`/`test`. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- **deno_core 0.412**: scopes via `deno_core::scope!(scope, &mut runtime)`; try/catch via `v8::tc_scope!(let scope, scope)`. `deno_error` must be pinned `=0.7.1`. Ops: `#[op2]` + `#[string]` for `Option<String>` returns, `#[serde]` for JSON. Extensions via `deno_core::extension!` with `esm = [dir "src", "file.js"]`.
- `call_with_args`/`resolve` return futures that **don't borrow the runtime**; drive the event loop separately (`poll_event_loop`). That's how concurrent async transforms work.
- Module specifiers must be canonical paths (`file_url` canonicalizes); `..` in paths broke module identity once.
- TypeScript transpile removes unused imports: tests that check import behavior must *use* the import.
- TypeScript 6 is vendored (`vendor/typescript`) for type checking because TS 7 is a native Go binary that can't run in V8.
- **deno_core reads `extension!` `esm = [...]` files from the build machine's disk at every isolate start** (by absolute path; only a startup snapshot embeds them): an installed binary panicked "Failed to initialize a JsRuntime: No such file or directory". `ops::extension()` replaces the list with `ascii_str_include!` (`the_extension_reads_nothing_from_disk`). Any new JS in an extension goes through it. Packaging tests (`demo-docker.sh`, `demo-packages.sh`) run the binary away from the source tree, which is what catches this.
- **Runaway guard (`ductus-script/src/guard.rs`)**: terminate only from inside an `IsolateHandle::request_interrupt` callback (runs on the isolate's thread; check the call generation first), never `terminate_execution` from the watchdog thread (a finished call's successor would be killed). Reading the stack there needs a context: the main context is kept in an isolate slot (`MainContext`) and entered with `v8::scope_with_context!`. After termination, `cancel_terminate_execution` (deno_core re-arms termination in `exception_to_err`). A termination during the event loop **drops all queued microtasks**, so every in-flight async transform on that isolate hangs: fail them all (worker's `interrupted` watch). `Isolate::settle` stringifies errors: use `drive` + `output` where a typed error (`Runaway`) must survive.
- **Sockets belong to the runtime that opened them.** The sqlx pool is shared with intake: worker threads must run store calls on the main runtime (`Worker::db`), or a busy V8 thread delays other interfaces' ACKs.
- **Type checker API (`check.js`)**: to know whether a call is the SDK's `db`/`api`, resolve the callee with `checker.getSymbolAtLocation` + `getAliasedSymbol` and check its declaration sits in `declare module "@ductus/sdk"`; don't match names (a local `db` would count, an alias wouldn't). `analyze(..., false)` skips `getPreEmitDiagnostics`, which is the slow part.
- **Places and findings (0.7.1):** every project YAML file loads through `ductus_core::yaml` (`parse`, `substitute`, `from_value`): its errors are `yaml::Located` (stage + key, or the parser's position) and display as before. A new rule in `InterfaceConfig::validate` uses the `refuse!([key...], ...)` macro (or `yaml::at`) so `validate --json` can point at it; a new check across interfaces returns `yaml::Problem` (text, interface, key). **A new `validate` finding needs a `DUC` code in `findings::CODES`** (with what to do: it's the reference page `reference/validate.md`; `every_code_is_listed_and_every_listed_code_is_used` reads project.rs) and goes through `Report` (`report.add`, never `println!`), or `--json` loses it; the text output must stay as it was. A code keeps its meaning: new check, new code. The JSON of `test --json` (JSON Lines) and `validate --json` is a contract for editors and CI: only add fields (`test_reports_where…`/`validate_json_…` pin the keys). An error from interface code is shown through `ductus_script::errors::readable` (the worker's reason, `ductus test`); replay compares reasons without its `(file:line:col)`. The SDK's `internal()` (testing.ts) and `errors::internal` must name the same frames. **`cargo test -p ductus-core` alone rewrites `docs/schema/*.json` with keys sorted** (serde_json's `preserve_order` comes from another crate in the workspace): `git checkout docs/schema` after it, or test the workspace.
- **`console` in interface code (0.7.1 follow-up):** deno_core's own console writes straight to stdout; ops.js replaces it (wrapped by `Deno.core.wrapConsole` with V8's, so an inspector sees the lines too) and every line goes through `op_ductus_console`, which reads `ops::Console` from the OpState: `Log` (the engine and replay: tracing target `script`, the place from the stack, the environment's `console:` level via `Isolate::console_to_log`) or `Captured` (`Isolate::tests`, `capture_console`; the SDK runner takes each test's lines with `__ductus_console_take`). An isolate that can run project code where stdout is a contract (`--json`, `--emit`) must capture or log, never be left on the default. **ops.js must stay ASCII** (`ascii_str_include!`: a `µ` in a comment is a compile error). validate's `DUC206` reads the type checker's `Analysis::console` (calls of the *global* `console`, `topLevel` when outside every function).
- **The inspector (0.7.2.1):** an inspected isolate (`Isolate::with_inspector`) **must run on a current-thread runtime of its own thread**: deno_core's inspector spawns `!Send` tasks (`deno_core::unsync::spawn`), and on the CLI's multi-threaded runtime one ran on another worker and panicked ("RefCell already mutably borrowed", printed but the run went on). `wait_for_debugger` also needs a Tokio context. The server (`ductus_runtime::inspect`) is on its own thread: never serve it from the isolate's. A paused frame's `url` is empty in CDP (deprecated): tests find the script by `location.scriptId` from `Debugger.scriptParsed`. A session that ends while paused lets the call go on (V8). Every new place that debugs (`try`, `dev --inspect`) goes through `inspect::Target` with the isolate's `DebugSwitch`, or the guard kills paused calls. A test that sets a tracing subscriber sees swc's debug lines too when it's the first in the process to load the SDK: filter by target. `scripts/demo-debug.sh` drives VS Code's js-debug (`scripts/dev/js-debug.sh` fetches it, pinned by version and SHA-256; `scripts/dev/dap-client.mjs` speaks DAP as VS Code does, answering js-debug's `startDebugging` for the child session; program output needs `outputCapture: "std"`). **`ductus dev --inspect` (0.7.2.3)**: `EngineOptions::inspect`; a debugged interface gets a worker thread of its own (`worker::spawn_thread`'s `inspector`), and **`drive_event_loop` must keep a pending poll on the event loop even when nothing is in flight**: deno_core wakes only the task that last polled it when a debugger's message arrives (with the old "ready → wait for kick" an idle interface never answered a debugger; the CLI test catches it). Code that runs after a session ends goes in `inspect::Attached`'s drop, not after the bridge's loop (a server shutdown drops the task). The engine's stop calls `Inspector::close` first, so a paused call can't hold the stop; that message is then sent or left pending depending on a race with the workers' stop (both happen: the test accepts either and checks it's delivered once after the next start). `dev` opens the port before Postgres. `demo-debug.sh`'s dev part reads the configuration from the `launch.json` `ductus types` writes (`dap-client.mjs` `DAP_CONFIG`) and waits for js-debug to verify the breakpoint before sending (in already-loaded code it's placed asynchronously); its trap stops a dev left behind before deleting the folder (else its Postgres runs on in a deleted folder). **`ductus try` (0.7.2.2)** is `ductus_runtime::try_message`: the replay's `ReplayServices`, `decide` and `seed` for one message on a thread of its own (current-thread runtime + LocalSet, as replay; the inspector needs it); it must decide exactly as replay and the worker do, so change those, not a copy. Destinations are run by name (the config's map is sorted), as the engine's workers and replay. `demo-try.sh` reads a stored message from the database and through the API (`--from`), checking the audit row and that the receiver got nothing more.
- **Loading code into a running worker thread (0.7.5.1, `worker::Command::Replace`):** `Isolate::add_functions` holds `&mut Isolate` across awaits, and on a running thread the isolate is an `Rc<RefCell>` that the event-loop driver and every in-flight transform borrow: a borrow held across an await makes theirs panic ("already mutably borrowed"). The thread's `Gate` is closed for the load: `Script::transform` waits at `Gate::opened` before `begin_function` **and before `settle`** (the load's own `run_event_loop` settles other interfaces' promises), the driver uses `try_borrow_mut` and is kicked after. That `run_event_loop` also waits for every op in flight on the isolate, so a load lasts at least as long as the slowest async call there. A runaway during a load comes back as `ductus_script::LoadRanAway` (same text as before): V8 dropped every queued continuation, so the worker tells `interrupted` and the calls in flight retry. A file loaded again from the same path is the old module (V8 keys by URL): only new folders (a release's) load new code.
- **Changing an interface's destinations while it runs (0.7.5.1 item 3, `in_place.rs`):** a worker finds its wake-up and its lanes' drain state **by its destination's place** (`Wake::get(slot, index)`, `Lanes::watch(index)`), so a destination added, removed or reordered gets a new `Wake` (never a resized one), and is refused (`NeedsHandover`) when the interface's lanes were changing at the start: `Lanes.changing` stays `Some` after it settles, sized for the start's count. Per-destination counts live in `control::RunningDestination`, not `InterfaceStats` (whose counts must go on), and everything that shows destinations reads that list, never `config.destinations()` zipped with another vector. **A replacement worker must read first**: the start's `Waiting` list makes a worker skip its first read when its interface had nothing waiting, but the worker it replaces may have stopped mid-batch; `Interface::jobs` gives replacements an empty one. `Intake::retarget` waits until no store holds the old targets (`Arc::strong_count`) before `reconcile`, or a message stored with the old destination list would be missed.
- **`validate` and `test` on threads (0.7.4.3.1):** `spread::in_order` (ductus-cli) runs a job per interface on threads, each with a current-thread runtime, and hands results back in the interfaces' order, so what's printed is what one thread printed: anything new that `validate`/`test` print per interface goes in the ordered callback, never from a worker thread. **Each interface keeps an isolate of its own there**: sharing isolates as a start does made a verdict depend on load order (code reading another interface's `globalThis` passed one run in three). **A `JsRuntime` made on a plain `std::thread` aborts** the first time V8 posts a delayed task ("created outside of a tokio runtime context"): enter a runtime first (`runtime.enter()`, as validate's type-check thread does). The SDK's JavaScript is transpiled once per process (`loader::sdk_javascript`): an SDK change needs nothing else.
