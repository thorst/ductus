# Scripts, demos, CI, WSL

Read before changing: bash scripts and demos, CI, WSL and the machine, benchmarking against an older build. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- **WSL's disk lives on E:** (`E:\WSL\Ubuntu\ext4.vhdx`, distro name `Ubuntu`, a 1 TB SSD of its own since 2026-11-24; before that `D:\WSL\UbuntuTest`, 2026-10-10 to 11-24, and C: before that). The repos stay on D: (`/mnt/d/...`); builds go to `~/target` inside the image. A synchronous 8 KB write takes ~2.2 ms there (`dd bs=8k count=200 oflag=dsync`: 0.44 s; the same on D: took 1.25 s, ~6 ms; NVMe C: was ~2.5 ms): benchmark numbers measured between 0.6.1 and 2026-11-24 were on D:, so re-measure before comparing. **To move it, export + import, never `wsl --manage --move`**: the moved 61 GB image did ~400 ms per synchronous write (commits took a second) while a fresh image on the same drive did 6 ms. Steps (2026-11-24, ~66 GB, about half an hour all told): `wsl --shutdown`; `wsl --export Ubuntu E:\WSL\ubuntu-<date>.tar`; read the tar to its end (`tar -tf` from Git Bash; its "unknown extended header keyword LIBARCHIVE.xattr" warnings are harmless); `wsl --unregister Ubuntu` (deletes the old image); `wsl --import Ubuntu <folder> <tar> --version 2`. `/etc/wsl.conf` (`[user] default=todd`, `systemd=true`) travels in the tar, so the user, Postgres, Docker and `~/target` come back as they were. Keep the tar until check.sh passes on the new image. Docker in WSL needs Ubuntu's `docker-buildx` and `docker-compose-v2` packages (installed). **The image only grows**: space freed inside WSL stays taken on D: (2026-10-25: 36 GB used inside, 48 GB image). check.sh ends with the build outputs' size and trims them past `TARGET_LIMIT_GB` (default 30): the incremental caches first, then `cargo clean` if still over (since 2026-11-22, after they reached 89 GB and filled D:). To give space back (Todd, as administrator, now and then): `wsl --shutdown`, then `diskpart` → `select vdisk file="E:\WSL\Ubuntu\ext4.vhdx"` → `attach vdisk readonly` → `compact vdisk` → `detach vdisk`. Not WSL's sparse-disk setting (`--set-sparse`): after the `--move` trouble, not worth the risk on this image.
- **check.sh runs the tests in release (`cargo test --release`), so `debug_assert!`s never fire there**, dependencies' included: a deno_ast assertion (a byte order mark passed to the parser) panicked only under a plain `cargo test -p ductus-script`, found in 0.7.5.1. When touching a crate, run its tests in debug once too.
- **A bench's cleanup finds its engines by command line (`pkill -f "ductus run --releases $WORK/releases"`), not from the database**: a deploy whose new engine failed left an engine the database didn't name, the bench dropped the database, and that engine held the API port for hours; the next run's engine exited at once and the bench waited forever for `started interfaces=`. Every wait for a start also checks the engine is still alive (`kill -0`).
- **A demo never waits without a limit, above all on `ductus gen`**: the sender retries forever when nothing listens. On 0.7.9.2's first CI run, demo-windows-deploy.ps1's deploys were refused, so nothing ever listened on the port, and its bare `$gen.WaitForExit()` held the Windows job for two hours until the run was cancelled. Bound each wait (`WaitForExit(120000)`, `timeout` in bash), kill the process on timeout and count it as a failed check.
- **demos.sh isn't every demo**: `demo-docker.sh`, `demo-packages.sh`, `demo-v06.sh` and the Windows `.ps1` demos run only in CI (packaging and Windows jobs). A change in what a command prints (0.7.5.1: a code-only deploy goes in place instead of "handed over") failed two of them after merging. Before closing a step that changes output, grep every `scripts/demo-*` (and `ci.yml`'s step names) for the old text, not only what demos.sh runs.
- **demos.sh stops at the first FAIL and keeps only each demo's last line** (`set -e`, `| tail -1`): the demos after it never ran (2026-11-23: demo-vscode's History/Debug flake at #25 skipped the last five), and a demo that cleans up its temp files (demo-vscode's `$LOG`) leaves nothing to read. Rerun the failing demo alone with its output in a file, **with `CARGO_TARGET_DIR=$HOME/target` exported** (demos.sh sets it; without it a demo's `BIN` falls back to the repo's own stale `target/` and fails at once with "unexpected argument '--releases'"), then run the demos after it.
- **A CLI test that fails mid-way leaves its releases deployed to `prod`** on the shared database (`forget_releases` runs at its end), and then `demo-release.sh` refuses to start ("several projects are deployed to `prod` on this database (.tmpXXXX, …)") or its step 14 runs that project instead of "nothing is deployed yet": the demo ends at the step's header with no PASS, and `demos.sh` (`set -e`) stops there. **Every test that deploys takes the `Releases::of(dir.path())` drop guard** right after making its project, before its engines (so it drops after them): `testing::forget_project_releases` on drop, panic or not (cli.rs; since 2026-11-25 all nine deploy tests, none cleaning up at its end any more). For a leftover: those `.tmp…` projects are test folders; forget their releases as `testing::forget_releases` does (`release_checks`, `release_places`, then `releases`, by project) and run the demo again.
- **Every pipeline in a bench that reads the engine's log ends `|| true`**, not only the first: a deploy that doesn't print a line (0.7.5.2.4 moved a stopped thread's "its new code runs" line to debug) made `grep` fail under `set -eo pipefail` as the last command of `phase`, and bench-deploy.sh ended with exit 1 and no message after a full phase. Run it with `bash -x` (stderr to its own file) to see which command it was. **Demos too, for a line logged beside the start**: demo-retention.sh failed inside demos.sh twice (2026-11-17, -18), always right after "the engine starts while ADT keeps coming", and passed alone: its `grep -o 'shorter retention not applied.*' run.log | sed …` ran before a busy engine had logged it. `wait_for` the line first (done there), then print it. **The CLI tests too**: `lanes_nothing_recorded_are_adopted_and_sent_first` read its log once at "started interfaces=" and failed on CI's `windows-tests` (2026-11-25, main at Version 0.7.0) because lanes.rs's `tell` logs "lanes changed" (and writes its audit row) beside the start; `wait_for_log` / `eventually` for anything a spawned task logs or writes.
- `cargo test` doesn't rebuild the `ductus` binary: `check.sh` builds it explicitly (a stale binary once hid a migration bug).
- Calling `wsl` from the Git Bash tool mangles `/mnt/...` paths: prefix `MSYS_NO_PATHCONV=1` (or use PowerShell). Don't put the text "ductus run" in a wrapper command line: `demos.sh` does `pkill -f 'ductus (run|...)'` and kills the wrapper.
- In scripts, never `cmd | grep -q x` under `set -o pipefail`: grep exits at the first match, `cmd` gets EPIPE, and the pipeline "fails" (bit the `ductus status` waits once its output grew). Use `grep x >/dev/null` (and `sed -n 1p`, not `head -1`). Report commands now end quietly on SIGPIPE (`quiet_on_closed_pipe` in main.rs), but under pipefail that's still exit 141; never give `run`/`gen`/`sink` the default SIGPIPE (a closed socket would kill the engine). And start the engine directly (`"$BIN" run &`), not in a subshell (`(cd p && "$BIN" run) &`): a background subshell in a non-interactive script ignores SIGINT, so `kill -INT` never reaches the engine and `wait` hangs.
- Comparing against an older version: build it from a `git worktree` into its own target dir (`CARGO_TARGET_DIR=~/target-base`). Versions before 0.6.1 read `ops.js` from their source folder at run time, so keep that worktree until you're done. **Never build a worktree into `~/target`**: our build scripts have their folder baked in (`env!("CARGO_MANIFEST_DIR")`) and cargo reuses them by fingerprint, so after the worktree is deleted check.sh's test stage panicked ("vendor/typescript/lib missing" back when TS 6 was vendored, "the web UI isn't built") from a probe's `~/wt-sspi`. Fix: `cargo clean --release -p ductus -p ductus-core -p ductus-hl7 -p ductus-mllp -p ductus-script -p ductus-store -p ductus-runtime`.
- Demo waits must re-evaluate their condition: `wait_for 15 '[ "$(count $OUT)" -ge 3 ]'` (quoted, `eval`ed). Passing `"$(...)"` unquoted freezes the value and the wait silently runs to its timeout.
- Logs are plain text when stdout isn't a terminal (`with_ansi`), so demos can grep fields like `started interfaces=`.
- SFTP tests use a throwaway user-level `sshd` (openssh-server installed in WSL; its system service is disabled) on 127.0.0.1:2222; see `scripts/demo-files.sh`. Clean up child processes with a `trap` whose commands each end in `|| true` (`set -e` applies inside traps).
- CI "could not find native static library `rusty_v8`" on Build (Lint passes) = a stale rust-cache restored as a partial match. Fix: `gh cache delete --all`, then `gh run rerun <id>`. Always check the run after pushing.
- **WSL stops the distro** (Docker and containers with it, exit 255, nothing in the logs) once no `wsl` command has run for a while. Not a SQL Server crash. The local SQL Server container (`scripts/dev/sqlserver.sh`, Docker Engine installed in WSL) has `--restart unless-stopped`; check.sh starts it and waits for a real login before the tests. SQL Server tests use `DUCTUS_TEST_SQLSERVER=user:password@host:port`.
- tracing's plain log format puts the message before the fields: grep `interface stopped.*interface=x`, not the other way round.
- **The package of `crates/ductus-cli` is named `ductus`**: `cargo test -p ductus --test cli`, not `-p ductus-cli`.
- **A full drive under WSL's image turns WSL's filesystem read-only** (the image grows and can't; E: since 2026-11-24, D: before, and the story below is D:'s): 2026-11-14 D: hit 0 bytes free mid-session, and the next link failed with only `linking with cc failed`; inside WSL even `df` gave `Input/output error` and cargo said `Read-only file system`. Check `Get-PSDrive D` first when a build fails oddly. Fix: free a few GB on D: (Todd decides what), `wsl --shutdown` (it mounts writable again), then `cargo clean` inside WSL so the image has room without growing (43.6 GB freed that day). **Docker is the other big user inside WSL**: `docker system df` showed 52 GB (`/var/lib/containerd` + `/var/lib/docker`, which `du ~` never counts), 21.7 GB of it build cache from the packaging demos; `docker builder prune -af` and `docker volume prune -f` are safe (tagged images and `ductus-mssql` stay). Then compact (the vdisk steps above) to give it back to D:. (On C:, before the move, a benchmark loading 1M rows did the same: drop benchmark databases afterwards.)
- Python on Windows writes CRLF in text mode: pass `newline='\n'` when editing repo files from a script.
- **WSL's VM gets killed under memory pressure** (commit charge, not RAM): this machine has a 2-4 GB fixed pagefile, Edge holds ~18 GB, and a long `check.sh` died mid-run three times ("wsl.exe" exit -1073741571 / 253, `/tmp` emptied, Application Error events for wsl.exe, "low virtual memory condition" naming vmmemWSL in the System log). Work around it: `wsl --shutdown` first, `CARGO_BUILD_JOBS=4`, run the test stage per crate (`cargo test --release -p <crate>`); detached `nohup` jobs die with the VM (only an attached `wsl` command counts as activity). The kill can leave a truncated test binary (`Exec format error` in the CLI tests): delete `~/target/release/deps/ductus-*` and rebuild. A real fix is Todd's call (system-managed pagefile, or `memory=` in `.wslconfig`).
- **`[skip ci]` in the HEAD commit of a push skips CI for every commit in that push**, including an earlier code commit: a docs-only commit on top of a code commit must not carry it. Start a run by hand with `gh workflow run ci.yml --ref main`. The `windows` job's cold build takes ~35 min (the rust cache is kept on failure); a "Data limit exceeded" pull error in "Initialize containers" is the registry, not the code (`gh run rerun <id> --failed`). Since 0.6.5.1 the `test` job's Postgres is `ductus dev --database-only` (started after Build; its binaries cached by `actions/cache`), so every push runs the suite on what `dev` ships; demos get the login, host and port from the URL (`PGUSER_`, `PGPASS_`, `PGHOST_`, `PGPORT_`, `PGDATABASE_` in `scripts/dev/db.sh`; never hardcode `localhost`/5432 in a demo's resources.yaml). Our mirrored image `ghcr.io/thorst/ductus-ci-postgres:18` (public; made by `mirror.yml` monthly or `gh workflow run mirror.yml`) stays for `demo-packages.sh` (`POSTGRES_IMAGE`). A new image CI needs from a public registry goes through `mirror.yml` too. **CI skips pushes that change only `.md` files** (except `docs/schema.md`, which a store test reads) and cancels the run of the previous commit when a newer one is pushed to the same branch (`paths` and `concurrency` in ci.yml); a push with any code file in it runs everything, so no `[skip ci]` is needed for docs. A cold `windows` build is ~35 min but a warm one 10-14 min. **Pushes to a step branch (`0.7.6`) start no CI**: the push trigger covers only `main` and tags. Before asking Todd to review, start the branch's run by hand (`gh workflow run ci.yml -R thorst/ductus --ref 0.7.6`) and check its commit is the one you pushed. A `windows` job that hangs until the 60-min timeout keeps no log (`--log-failed` says "log not found"): read the step names and their times (`gh run view <id> --json jobs`; "Deploys to the service" normally takes ~14 s) and rerun with `--failed`.
- **Node from a plain WSL shell or script needs `~/.local/node/bin` on its `PATH`**: `check.sh` and `demos.sh` add it for themselves; anything else (`demo-ui.sh` alone, `npm run check` or `npx vitest` in `ui/`) doesn't, and without it `npx` resolves to the Windows one through WSL interop ("'playwright' / 'vitest' is not recognized as an internal or external command"), failing before any test runs; `demo-debug.sh`, `demo-vscode.sh` and `demo-v07.sh` run alone fail their debugger step with uutils' "timeout: failed to execute process: No such file or directory (os error 2)" (no `node`). `export PATH="$HOME/.local/node/bin:$PATH"` first.
- **Demos and tests that deploy releases name their interfaces per run** (`ui-release-$$` in demo-ui.sh, `rel-<nanos>` in the CLI tests): the "replaces" check judges a running version by the commit it came from, and each run makes a new git repository, so the same files deployed by an earlier run (another token, a commit this run doesn't have) refuse the next run's deploy. Release ids repeat across runs (they're the files' hash): forget them by project at the start and the end (demo-ui.sh's `forget_releases`). Since 0.7.5 a version that any deploy brought from a commit in the release's history is accepted, but a new run's first deploy changes versions an earlier run left (from that run's own repository), so per-run names stay.
- **Tests must hold under a parallel run** (the whole suite, many engines on one database), where a single statement can take seconds; each of these failed that way (0.7.5.1). Take a command's result from its **stdout alone** (a token, `--json`): stdout and stderr joined gets a slow statement's warning in it (until 0.7.5.1 one-shot commands logged to stdout, so the first line of `token create` was sometimes that warning, and the engine answered 401 "missing `Authorization`" because the `…` in it isn't valid in a header). Judge "wasn't held up" **by order, not by a time limit** (`services::…a_dedicated_pool…`: `select!` against the slow call), and warm a pool before timing anything. Never prove a port closed by **binding it again**: another test may take it the moment it's free (`systemd::tests::free` reads `/proc` instead). Waits for an engine's start or a handover allow a minute and **assert** at the end (a 10 s loop that falls through fails later, somewhere unrelated). Count days from **one `now`** (a run across UTC midnight is a day off). Doctor's checks in tests get a longer timeout when they aren't about one (`one_within`).
- **Bash reads a script file as it runs**, line by line: editing a `.sh` while `wsl ... bash script.sh` runs it (a test script in the scratchpad, say) makes the running shell read the edit at its old byte offset ("unexpected EOF while looking for matching"). Write a new file for the next run instead. A scratchpad script also needs `source "$HOME/.cargo/env"`: `wsl -- bash file.sh` isn't a login shell, so `cargo` isn't on its `PATH`.
- **Windows PowerShell 5.1 reads a UTF-8 file without a BOM as ANSI**: `Get-Content -Raw draft.rs | Add-Content cli.rs` turned `→` into `â†’` in the appended test (0.8.2.1). Plain `Get-Content` *shows* every such file garbled too, while the file is fine: grep the file, don't trust the console. Append or edit repo files with the editor's tools (or `-Encoding utf8` on both sides), and grep the diff for `â` / `Â` after any PowerShell file write.
- **CI's test database is `ductus dev --database-only`'s Postgres, and it runs with `fsync` off** (postgresql_embedded always starts Postgres with `-F`; settings in `configuration` come after it as `-c` and could turn it back on). A test that reads the server's settings (doctor's `settings` line, `pg_settings`) asserts names, not values: `logs_in_to_the_store_and_times_commits` asserted `fsync on`, passed here on WSL's own Postgres and failed both CI test jobs (0.8.1's merge, 2026-11-26). Server settings are tested with a throwaway cluster (`pgtls.sh`) or the pure `pg_settings::judge`.
- **A CPU or time limit in a CLI test runs against a debug build**: `bench interface`'s "waits take no CPU" asserted < 2 ms of CPU a message and the code alone took 2.04 ms in debug (passed on the step that wrote it, failed on the next with nothing slower). Assert the relation that is the point (CPU under half the 10 ms of waits), not a number measured once; check a suspected regression on the previous commit in a worktree (`git worktree add --detach /tmp/base HEAD`, its own `CARGO_TARGET_DIR`) before blaming the change (0.8.2.3).
