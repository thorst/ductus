# Scripts, demos, CI, WSL

Read before changing: bash scripts and demos, CI, WSL and the machine, benchmarking against an older build. Each note is something that already cost a debugging session; add a new one here (not in CLAUDE.md) when you solve something the next person would rediscover.

- **WSL's disk lives on D:** (`D:\WSL\UbuntuTest\ext4.vhdx`, distro name `Ubuntu`, since 2026-10-10; C: was full). A synchronous 8 KB write takes ~5 ms there (NVMe C: was ~2.5 ms): benchmark numbers in architecture.md before 0.6.1 were measured on C:. Never `wsl --manage --move` it again: the moved 61 GB image did ~400 ms per synchronous write (commits took a second) while a fresh image on the same drive did 6 ms; export + import made a fresh one. Docker in WSL needs Ubuntu's `docker-buildx` and `docker-compose-v2` packages (installed). **The image only grows**: space freed inside WSL stays taken on D: (2026-10-25: 36 GB used inside, 48 GB image). check.sh ends with the build outputs' size and says when to `cargo clean` (over 30 GB). To give space back (Todd, as administrator, now and then): `wsl --shutdown`, then `diskpart` → `select vdisk file="D:\WSL\UbuntuTest\ext4.vhdx"` → `attach vdisk readonly` → `compact vdisk` → `detach vdisk`. Not WSL's sparse-disk setting (`--set-sparse`): after the `--move` trouble, not worth the risk on this image.
- `cargo test` doesn't rebuild the `ductus` binary: `check.sh` builds it explicitly (a stale binary once hid a migration bug).
- Calling `wsl` from the Git Bash tool mangles `/mnt/...` paths: prefix `MSYS_NO_PATHCONV=1` (or use PowerShell). Don't put the text "ductus run" in a wrapper command line: `demos.sh` does `pkill -f 'ductus (run|...)'` and kills the wrapper.
- In scripts, never `cmd | grep -q x` under `set -o pipefail`: grep exits at the first match, `cmd` gets EPIPE, and the pipeline "fails" (bit the `ductus status` waits once its output grew). Use `grep x >/dev/null` (and `sed -n 1p`, not `head -1`). Report commands now end quietly on SIGPIPE (`quiet_on_closed_pipe` in main.rs), but under pipefail that's still exit 141; never give `run`/`gen`/`sink` the default SIGPIPE (a closed socket would kill the engine). And start the engine directly (`"$BIN" run &`), not in a subshell (`(cd p && "$BIN" run) &`): a background subshell in a non-interactive script ignores SIGINT, so `kill -INT` never reaches the engine and `wait` hangs.
- Comparing against an older version: build it from a `git worktree` into its own target dir (`CARGO_TARGET_DIR=~/target-base`). Versions before 0.6.1 read `ops.js` from their source folder at run time, so keep that worktree until you're done. **Never build a worktree into `~/target`**: our build scripts have their folder baked in (`env!("CARGO_MANIFEST_DIR")`) and cargo reuses them by fingerprint, so after the worktree is deleted check.sh's test stage panicked ("vendor/typescript/lib missing", "the web UI isn't built") from a probe's `~/wt-sspi`. Fix: `cargo clean --release -p ductus -p ductus-core -p ductus-hl7 -p ductus-mllp -p ductus-script -p ductus-store -p ductus-runtime`.
- Demo waits must re-evaluate their condition: `wait_for 15 '[ "$(count $OUT)" -ge 3 ]'` (quoted, `eval`ed). Passing `"$(...)"` unquoted freezes the value and the wait silently runs to its timeout.
- Logs are plain text when stdout isn't a terminal (`with_ansi`), so demos can grep fields like `started interfaces=`.
- SFTP tests use a throwaway user-level `sshd` (openssh-server installed in WSL; its system service is disabled) on 127.0.0.1:2222; see `scripts/demo-files.sh`. Clean up child processes with a `trap` whose commands each end in `|| true` (`set -e` applies inside traps).
- CI "could not find native static library `rusty_v8`" on Build (Lint passes) = a stale rust-cache restored as a partial match. Fix: `gh cache delete --all`, then `gh run rerun <id>`. Always check the run after pushing.
- **WSL stops the distro** (Docker and containers with it, exit 255, nothing in the logs) once no `wsl` command has run for a while. Not a SQL Server crash. The local SQL Server container (`scripts/dev/sqlserver.sh`, Docker Engine installed in WSL) has `--restart unless-stopped`; check.sh starts it and waits for a real login before the tests. SQL Server tests use `DUCTUS_TEST_SQLSERVER=user:password@host:port`.
- tracing's plain log format puts the message before the fields: grep `interface stopped.*interface=x`, not the other way round.
- **The package of `crates/ductus-cli` is named `ductus`**: `cargo test -p ductus --test cli`, not `-p ductus-cli`.
- **C: is nearly full and WSL's disk image lives there** (grows, never shrinks by itself): a benchmark that loaded 1M rows filled it and crashed WSL with I/O errors. Check `Get-PSDrive C` before loading big data; drop benchmark databases afterwards.
- Python on Windows writes CRLF in text mode: pass `newline='\n'` when editing repo files from a script.
- **WSL's VM gets killed under memory pressure** (commit charge, not RAM): this machine has a 2-4 GB fixed pagefile, Edge holds ~18 GB, and a long `check.sh` died mid-run three times ("wsl.exe" exit -1073741571 / 253, `/tmp` emptied, Application Error events for wsl.exe, "low virtual memory condition" naming vmmemWSL in the System log). Work around it: `wsl --shutdown` first, `CARGO_BUILD_JOBS=4`, run the test stage per crate (`cargo test --release -p <crate>`); detached `nohup` jobs die with the VM (only an attached `wsl` command counts as activity). The kill can leave a truncated test binary (`Exec format error` in the CLI tests): delete `~/target/release/deps/ductus-*` and rebuild. A real fix is Todd's call (system-managed pagefile, or `memory=` in `.wslconfig`).
- **`[skip ci]` in the HEAD commit of a push skips CI for every commit in that push**, including an earlier code commit: a docs-only commit on top of a code commit must not carry it. Start a run by hand with `gh workflow run ci.yml --ref main`. The `windows` job's cold build takes ~35 min (the rust cache is kept on failure); a "Data limit exceeded" pull error in "Initialize containers" is the registry, not the code (`gh run rerun <id> --failed`). Since 0.6.5.1 the `test` job's Postgres is `ductus dev --database-only` (started after Build; its binaries cached by `actions/cache`), so every push runs the suite on what `dev` ships; demos get the login, host and port from the URL (`PGUSER_`, `PGPASS_`, `PGHOST_`, `PGPORT_`, `PGDATABASE_` in `scripts/dev/db.sh`; never hardcode `localhost`/5432 in a demo's resources.yaml). Our mirrored image `ghcr.io/thorst/ductus-ci-postgres:18` (public; made by `mirror.yml` monthly or `gh workflow run mirror.yml`) stays for `demo-packages.sh` (`POSTGRES_IMAGE`). A new image CI needs from a public registry goes through `mirror.yml` too. **CI skips pushes that change only `.md` files** (except `docs/schema.md`, which a store test reads) and cancels the run of the previous commit when a newer one is pushed to the same branch (`paths` and `concurrency` in ci.yml); a push with any code file in it runs everything, so no `[skip ci]` is needed for docs. A cold `windows` build is ~35 min but a warm one 10-14 min.
- **`demos.sh` (or `demo-ui.sh`) from a plain WSL shell needs Node on its `PATH`**: `check.sh` adds `~/.local/node/bin` for itself only, and without it `npx` resolves to the Windows one through WSL interop ("'playwright' is not recognized as an internal or external command"), so the UI demo fails before any test runs. `export PATH="$HOME/.local/node/bin:$PATH"` first.
- **Demos and tests that deploy releases name their interfaces per run** (`ui-release-$$` in demo-ui.sh, `rel-<nanos>` in the CLI tests): the "replaces" check judges a running version by the commit it came from, and each run makes a new git repository, so the same files deployed by an earlier run (another token, a commit this run doesn't have) refuse the next run's deploy. Release ids repeat across runs (they're the files' hash): forget them by project at the start and the end (demo-ui.sh's `forget_releases`). Since 0.7.5 a version that any deploy brought from a commit in the release's history is accepted, but a new run's first deploy changes versions an earlier run left (from that run's own repository), so per-run names stay.
- **Tests must hold under a parallel run** (the whole suite, many engines on one database), where a single statement can take seconds; each of these failed that way (0.7.5.1). Take a command's result from its **stdout alone** (a token, `--json`): stdout and stderr joined gets a slow statement's warning in it (until 0.7.5.1 one-shot commands logged to stdout, so the first line of `token create` was sometimes that warning, and the engine answered 401 "missing `Authorization`" because the `…` in it isn't valid in a header). Judge "wasn't held up" **by order, not by a time limit** (`services::…a_dedicated_pool…`: `select!` against the slow call), and warm a pool before timing anything. Never prove a port closed by **binding it again**: another test may take it the moment it's free (`systemd::tests::free` reads `/proc` instead). Waits for an engine's start or a handover allow a minute and **assert** at the end (a 10 s loop that falls through fails later, somewhere unrelated). Count days from **one `now`** (a run across UTC midnight is a day off). Doctor's checks in tests get a longer timeout when they aren't about one (`one_within`).
- **Bash reads a script file as it runs**, line by line: editing a `.sh` while `wsl ... bash script.sh` runs it (a test script in the scratchpad, say) makes the running shell read the edit at its old byte offset ("unexpected EOF while looking for matching"). Write a new file for the next run instead. A scratchpad script also needs `source "$HOME/.cargo/env"`: `wsl -- bash file.sh` isn't a login shell, so `cargo` isn't on its `PATH`.
