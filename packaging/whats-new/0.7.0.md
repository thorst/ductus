## What's new in 0.7: the developer workflow

Building, debugging and promoting interfaces the way developers expect.

**Debugging, in any editor.** The engine speaks the debugger protocol VS Code, Chrome DevTools and
JetBrains already use, so breakpoints in your `.ts` files work with no extension:
`ductus test --inspect` for tests; `ductus try` runs one message through an interface, sending
nothing (`--message ID --from <engine>` takes a stored production message to your copy of the
code); `ductus dev --inspect <interface>` pauses only that interface while every other one keeps
receiving and sending. [Debugging](https://docs.getductus.com/write/debugging.html)

**The VS Code extension** (`ductus-@VERSION@.vsix` below): tests in the Test Explorer with each
failure on its `expect` line (expected and actual side by side), `validate`'s findings in Problems
as you save, debugging with no `launch.json`, **Deploy to dev** (your change applied in place in a
second or less), **Promote…** a release to test or prod, each interface's history, and **Debug in
VS Code** on a message's page in the web UI. [In VS Code](https://docs.getductus.com/write/vscode.html)

**Who changed what, and why.** Every interface has a code version computed from what it runs, and
every delivery records the version that decided it. `ductus history <interface>` and the History
tab put on one timeline the git commits on its files, each deployment (who and why), the audit
log, and its documentation's changes.

**Releases and promotion.** `ductus release` makes one exact artifact from a commit; `ductus
deploy` sends it to an engine through a gate (the target's own `validate` and the tests of what
changes); dev → test → prod with `--from`, `--rollback` to go back. A deploy that would overwrite
a colleague's newer work is refused unless forced with a reason. The Releases page shows what ran
where. [Releases](https://docs.getductus.com/operate/releases.html)

**Deploys that touch only what changed.** A deploy or `ductus reload` applies code, destinations,
sources, ports, variables, and interfaces added or removed **in place**, and an interface's other
settings by restarting that interface alone: the interfaces you didn't change never pause, and
messages already waiting take the new code. A change to `ordering` no longer needs a drain.
[Deployments](https://docs.getductus.com/operate/deployments.html)

**Also:** ordering keys for real feeds (a repetition chosen by content, `PID-3[.5=MR].1`;
composite keys; JSON/XML filters; regular expressions; a key function in TypeScript; and an alert
when a key reads empty); **PGP** on file and SFTP connectors; a **time zone** per schedule; 22 more
HL7 v2.5 segments; `ductus new interface --source internal`; `ductus test` and `validate --json`
with every result's file and line; `validate` runs TypeScript 7's own `tsc`, shipped with Ductus
(0.3–0.6 s on a small project, under half the memory).

**Before you upgrade from 0.6:** `destination:` is gone. Every interface names its destinations
under `destinations:`, each with its code in a file of its own (`script:`); `ductus validate`
says what to write. Then `ductus upgrade --check` as always.
