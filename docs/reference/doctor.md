# Doctor findings

Besides timing durable commits, `ductus doctor` reads the engine's Postgres settings that decide whether a commit is durable, how much the server caches, whether there are connections for an engine and a handover, and whether old rows are cleaned up (one query of `pg_settings` and a count of `pg_stat_activity`, on its own connection). Its `settings` line shows each as set; each finding below is said after it with its code.

A **warning** is a risk to messages or to a start, and makes the check a warning. A **note** is tuning (marked `(tuning)`) and leaves the check passed: Postgres's defaults are sized to start on any machine, not for a database server of its own. Doctor says what a setting is and what it's usually set to, never a number for the database's server, whose RAM and disks it can't see unless it runs there. To see what a change does, [`ductus bench`](cli/bench.md) before and after, and `ductus bench compare` the two.

| Code | Kind | What it means, and what to do |
|---|---|---|
| `DOC001` | warning | **`fsync` is off.** Postgres doesn't flush its writes to the disk, so a crash of the database's server (power, the kernel) can corrupt the database, not just lose its last moments. Off is for throwaway test databases only: set `fsync = on` in `postgresql.conf` and reload. |
| `DOC002` | warning | **`synchronous_commit` is off.** Commits don't wait for the disk, so a strict interface's ACK no longer means the message is on disk: a crash of the database's server can lose the last moments' messages (up to three times `wal_writer_delay`, 600 ms by default), as a relaxed interface can. Set it `on` for the engine's login (`ALTER ROLE ductus SET synchronous_commit = on`), and use `durability: relaxed` for the interfaces that can afford it instead. |
| `DOC003` | note | **`commit_delay` is set.** Each commit waits up to `commit_delay` microseconds for other transactions to share its disk flush, when at least `commit_siblings` are open. It can raise what many strict sender connections store a second, and adds up to that wait to each ACK. Whether it helps is the disk's: compare `ductus bench` with it and without (`ductus bench compare`). |
| `DOC004` | note | **`shared_buffers` is Postgres's default.** `shared_buffers` (the memory Postgres caches the database's pages in) is 128 MB or less, Postgres's default, sized to start on any machine. On a database server of its own, about a quarter of its RAM is usual (a restart applies it); doctor can't see that server's RAM, so the number is yours to work out. |
| `DOC005` | note | **`effective_cache_size` is Postgres's default.** `effective_cache_size` is 4 GB, Postgres's default: the planner's guess of how much of the database the server's memory caches (Postgres's and the operating system's). It allocates nothing. On a database server of its own, half to three quarters of its RAM is usual. |
| `DOC006` | warning | **Too few connections for a handover.** `max_connections`, less the ones reserved for superusers (`superuser_reserved_connections`, `reserved_connections`), is below what two engines open: each opens up to its `--db-connections` (32 by default) and one for its lock, and a handover runs the old and the new engine for a moment. An engine that can't get a connection waits, then fails. Raise `max_connections` (a restart applies it), or lower `--db-connections`. |
| `DOC007` | warning | **Few connections are free now.** So many connections to the database's server are open now (all its databases count) that a starting engine, or a handover's new one, wouldn't get all it opens. See who holds them in `pg_stat_activity`; raise `max_connections` or close the idle ones (a pooler such as PgBouncer in front of other applications). |
| `DOC008` | note | **`random_page_cost` is priced for spinning disks.** `random_page_cost` is 4, Postgres's default, priced for hard disks: the planner then avoids indexes it would gladly use on SSD or NVMe, where 1.1 is usual. Leave it on hard disks. |
| `DOC009` | note | **`effective_io_concurrency` is 1 or less.** Postgres reads ahead one page at a time where it could ask for several at once (bitmap scans, and from Postgres 18 sequential reads too). On SSD or NVMe, 200 is usual; Postgres 18's default is 16. |
| `DOC010` | warning | **`autovacuum` is off.** Deliveries and messages are updated as they move, and without autovacuum their old row versions aren't cleaned up: tables and indexes grow and the engine's queries slow over days (retention drops whole partitions, but the current ones still fill). Set `autovacuum = on` and reload. |
