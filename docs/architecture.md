# Ductus architecture

How the engine works, and the rules that keep it correct. Read this before changing the runtime. What interface developers need to know about the resulting behaviour is in [nuances.md](nuances.md); the tables are described in [schema.md](schema.md) (for transparency, not an API).

## The shape of it

```
 sources                 store (Postgres)              workers                       destinations
 ───────                 ────────────────              ───────                       ────────────
 MLLP listener ─┐                                      pool thread 0..N  ─┐          MLLP client
 HTTP (queue)  ─┤   Intake          messages table ─► (shared V8 isolate) ├─► Sender ─ HTTP client
 File / SFTP   ─┼─► persist, then ─► (day partitions,   dedicated threads ─┘          File
 Schedule      ─┘   acknowledge      = the queue)      (own isolate)                 SFTP
                                                        │
 HTTP (respond) ───────────────► channel ──────────────►┘ transform(req) → HTTP response (no queue)
 Internal ◄──────────────────────────────────────────────── Route (destination `interface: x`): stored in
                                                            x's queue in the transaction that marks it sent
```

One binary (`ductus`) plus PostgreSQL. No other services. The engine also serves its REST API (`/api/v1`, default `127.0.0.1:7700`), which is how the UI, scripts and `ductus drain` see and steer it, and the web UI itself (embedded in the binary) on the same listener. Every listener can take TLS (see "TLS on our listeners").

## Invariants (never break these)

1. **Persist before acknowledge.** A source only ACKs (MLLP `AA`, HTTP `202`) after the message row is committed. If storing fails, the sender gets a retryable error (`AE`, `503`). Nothing acknowledged is ever lost by an engine crash. For files, "acknowledge" is moving or deleting the file: that happens only after every record in it is committed.
2. **At-least-once delivery.** A delivery stays `pending` until its destination confirms. A crash after sending but before recording `sent` re-sends it on restart; dedupe at ingest and idempotent receivers cover this. Sent statuses are flushed in batches of ≤50 and always before a retry back-off, so the re-send window is small.
3. **One owner per lane and destination = per-key order.** The ordering key (e.g. MRN) hashes (FNV-1a, stable forever: `ductus_core::partition_of`) to one of N virtual partitions ("lanes"). For each destination, each lane is owned by exactly one worker (slot), which processes its pending deliveries strictly by message id. A failed message blocks its slot's lanes *for that destination* until it succeeds or is quarantined: that's the price of ordering. Across engines sharing a database, each interface has one engine (`interface_owners`, see "Engines on one database"): nothing may read an interface's queue or change its rows before the engine has claimed it.
4. **Migrations are expand-only.** Never drop or rename a column/table in a migration that an older binary still uses. Older binaries tolerate unknown newer migrations (`set_ignore_missing`), so rollback = reinstall the previous binary.
5. **No credentials in interface code.** Secrets come from `secrets/<env>.json` (encrypted) via `${secret:NAME}` in YAML or `secret()` in code; connections are named resources (`resources.yaml`).
6. **Interface code is sandboxed from the network and filesystem** except through engine services (`db()`, `fetch()`, `env()`, `secret()`). Remote module imports are refused.

## Message lifecycle

Statuses: `0 pending`, `1 sent`, `2 filtered` (dropped on purpose: `return null` / `kill(reason)`, over a rate limit with `drop`, or its destination was removed), `3 quarantined` (needs a human), `4 duplicate` (dedupe hit; stored for audit, never queued). `last_error` holds the reason.

### Destinations and deliveries

- An interface has one destination (`destination:`, named `default`) or several (`destinations:` by name). Each destination has its own function (`transform:`, default `transform`), output format, `retry`, `rate_limit` (its own allowance) and `save_output`.
- **`deliveries`** (day-partitioned like `messages`): one row per queued message and destination, inserted **in the same statement** as the message (so still one commit per ACK). Its partial index `deliveries_queue (destination_id, message_id, partition_key) WHERE status = 0` is each destination's queue, in message order: a worker's read of 50 stops after 50 matching rows, so it costs the same with 1k or 500k waiting (~1.3 ms). With the lane second (`deliveries_pending`, before migration 0011), Postgres would have had to sort a lane set's whole backlog, so it walked each partition's primary key instead, past every delivered row: ~300 ms a read with 1M delivered messages ahead of a 10k backlog, i.e. a destination back from an outage drained at ~170 messages/s. Rows carry `status`, `attempts`, `last_error` and, with `save_output`, `output`.
- **One worker per (slot, destination).** Each runs the destination's function on the original message (with `meta`: `id`, `receivedAt`, `destination`, and `origin` for a routed message), then delivers. A destination that's down blocks only its own lanes; the others keep going. Ingest wakes every destination's worker for the lane's slot (`Wake`).
- **`messages.status` is the overall status**: pending until no delivery is pending; then quarantined if any is, else sent if any is, else filtered. `Store::settle` sets it in a statement of its own **after** the delivery update commits: of two destinations finishing a message at once, the later always sees both done (in one statement, each could see the other pending: write skew). Settle locks the message rows in id order (`ORDER BY id FOR UPDATE`, a statement of its own) and only then reads their deliveries (a second statement, so a fresh snapshot): destinations settle overlapping sets at once, and left to the plan the lock order could differ between two of them (a deadlock, seen once with routes); and a resend moves a delivery from final back to pending while holding the message's lock, so a settle that had read the deliveries before waiting would mark the message done with a delivery pending again (`a_resend_while_another_destination_settles_leaves_the_message_pending` fails without it). A worker whose statuses committed but whose settle failed retries the settle alone (`settle_saved`), never the status write: by then a delivery may have been resent. Delivery updates only change deliveries that are still pending, so a retried flush changes nothing twice. Older binaries read only `messages.status`, so rolling back still works.
- **Reconcile at startup** (`Store::reconcile`, three queries for all interfaces): deliveries for pending messages that lack one (stored by an older version, or a new destination); pending deliveries to removed destinations → filtered; pending deliveries whose message an older version finished → its status. Only interfaces with something waiting are reconciled (`Store::with_waiting`: two loose index scans over the pending indexes, ~20 ms at 1,001 interfaces with or without a 300,000 backlog); the others have nothing for it to change. Messages left pending with no pending delivery (`Store::settle_finished`) are settled right after the start: workers read deliveries, never `messages.status`.
- The script host loads an interface module **once** and binds one entry per destination (`Isolate::add_functions` → `FunctionId`s); runaways are attributed per interface (`InterfaceId`), so every in-flight call of that interface takes the blame.

### Routes between interfaces

- A destination `interface: <name>` routes to another interface, which has `source: internal` (no listener; only routes fill it). `ductus_core::config::check_routes` (validate and startup) requires the target to exist with that source and to read the format the destination outputs, and refuses loops.
- The routing worker has no `Sender`. A routed message joins the worker's flush batch (≤50, or after 20 ms, or at the end of a read), and `Intake::accept_routed` on the **target's** intake stores the batch: `Store::finish_routed` updates this destination's deliveries (pending ones only, `RETURNING` which) and inserts, for exactly those, the target's messages and deliveries (its keys, dedupe and destinations; `origin_id` = the source message) **in one transaction**. Then settle, then the target's lanes are woken. So each hop is exactly once: a crash before the commit routes again; a retry after it finds the deliveries done and routes nothing.
- That commit skips the flush wait (`synchronous_commit = off`): nobody outside the database has been told anything, so a lost commit is lost whole and the deliveries are still pending.
- Routed inserts don't pass the target's drain gate (they were received before the drain); the drain waits for them through the pending counts.
- Startup builds every queued interface's `Intake` before any worker, since a route's worker holds its target's.

Worker per delivery: function → outcome:
- deliver → rate limit → send → `sent` (batched)
- `Filter(reason)` → `filtered`
- `Quarantine(reason)` (transform threw, `quarantine()`, AR, 4xx) → `quarantined`
- `Retry` (error text contains `[ductus:transient]`, e.g. DB unreachable) → back off 1s→60s, retry the same message (order kept)
- `Runaway` (the code ran past its `timeout` without pausing, or filled the isolate's heap) → `quarantined`; three timeouts in a row or one heap overflow **stop the interface** (`health.rs`): its messages stay `pending` until the code is fixed and the engine restarted; respond-mode requests get 503
Delivery failures: transient → back off and retry (forever unless `retry.max_attempts`); permanent → quarantine.

### Files (file and SFTP sources)

- One `FileWatcher` per interface over a `Backend` (local folder or SFTP connection). Each poll lists the folder; a file is ready when its size and time are unchanged since the last poll (or its `marker` exists). Dot-files are skipped. Ready files go oldest first, one at a time; a failure stops the poll so later files wait (file order kept).
- `split: records` streams the file through `split::Records` (256 KB buffer, never the whole file): HL7 per MSH, CSV per record with the header prepended, others per line. Records go to `Intake::accept_batch` 500 at a time (or 4 MB): **one transaction stores the records and the file's progress** (`source_state`: size, time, byte offset, records, done).
- After a crash, the saved offset is where reading resumes (same size and time) or the file is read again from the start (it changed). `done: true` is saved with the last batch, so a crash before the move doesn't read the file again. Then move/delete, then the progress row is deleted.
- Unsplit files (one message each) are capped at 256 MB; bigger ones are left in place with an error.

### Schedules

- `schedule::run` sleeps until the next due time (re-checking the clock every minute), then `Intake::accept_scheduled` stores a message `{"due", "previous"}` **and** the schedule state (`anchor`, `previous`) in one transaction, unless a run of this interface is still pending (then the run is skipped). The worker runs `transform` on it like any message; the transform's input format is JSON and `format`/`output` describe what it produces.
- `ductus_core::schedule::Timing`: `every` runs at start then every interval; `cron` (croner, server local time) waits for its next time. Missed runs collapse into one run on start (`anchor_after`).

## Engines on one database (0.6.2)

- **One engine per interface.** Each engine run (`instance`, the id `engine.start` logs) holds a session advisory lock with a random key on a connection of its own for its whole life (`Store::lock_engine`, `ownership::Owner`; `engines` table). Alive = the lock is held (`pg_locks`): Postgres frees it however the process ends, so there's no heartbeat and no timeout to wait out after a crash. The lock connection sets TCP keepalives (10 s, 3 × 5 s) so a vanished host's session (and lock) goes within ~25 s instead of the OS default ~2 h, and `idle_session_timeout = 0`.
- **The start sequence:** load and check the project (nothing touches the database) → connect and migrate → lock → **claim** every queued interface in one transaction (`Store::claim`: delete owner rows whose engine isn't alive, `INSERT … ORDER BY interface ON CONFLICT DO NOTHING`, read who owns the rest; all or none, rolled back if any is owned) → **the lanes guard** (`Owner::guard_lanes`) → then everything that changes an interface's rows (docs snapshot, reconcile, retention, workers, listeners). A refused start writes `engine.refused`, deletes its `engines` row, closes the lock connection and exits 3 (`ownership::Refused`; systemd `RestartPreventExitStatus=3`). Claims are sorted, so two engines claiming overlapping sets at once wait for each other and the later one sees the earlier's rows (`two_engines_claiming_the_same_interfaces_at_once_one_wins`). Respond-mode interfaces aren't claimed (no queue). A clean stop deletes its claims and sets `stopped_at` after the workers have finished. Measured at 1,001 interfaces: claiming ~16 ms (fresh or from a dead engine), ~3 ms for its own rows again.
- **Losing the lock** (`Owner::watch`: the lock connection is checked every 2 s with a 3 s timeout): `Ownership` turns false, so workers (in `hold_while_paused`), file watchers and schedules wait; intake keeps storing. The engine takes the same lock key again (retrying while the server still holds the old session) and claims again; if another engine owns an interface by then, it stops with exit 3. The ping is well inside the keepalive window, so an engine cut off from the database pauses before another can claim its interfaces.
- **The lanes guard:** `interface_applied` keeps each interface's lanes (`partition_count()`: `partitions` with an ordering key, else 1). Lowered or never recorded → `Store::stranded` counts waiting deliveries in lanes ≥ the new count (the waiting rows of those destinations read once from the queue index in a materialized CTE, filtered at the smallest limit, then matched to each limit; a per-destination `LATERAL` count let the plan seq-scan a big partition once per destination: 18 s at 1,001 destinations with 300,000 waiting, against 18–55 ms now); any → refused. Raised with messages waiting → warning + `interface.partitions_raised`. Only changed values are saved. `ductus validate` runs the same check read-only (`Store::connect_read_only`: no migrations, since it may run with a newer binary than the engines there), plus retention changes running, waiting for a confirmation or starting at the next start.
- **Visibility:** `GET /engine` has `holds_interfaces` and `others` (live engines on the database with what they own); the Overview shows both.

## TLS on our listeners (0.6.3)

- **Certificates are resources.yaml entries** (`certificates:`; `ductus_core::resources::CertificateEntry`): a pair from files (`cert_file`/`key_file`, relative to the project) or from PEM text (usually secrets), or a CA alone (`ca`/`ca_file`). Listeners name them: `tls: { certificate, clients: { ca, subjects } }` on MLLP and HTTP sources and on `api` in ductus.yaml (`ductus_core::tls`: the shape, subject patterns, and `check` for names and kinds). HTTP interfaces on one port share its `tls` (`check_endpoints`).
- **Loaded before the database** (`ductus-runtime/src/tls.rs`, `Certificates::load`): every entry, each pair's key checked against its certificate (`CertifiedKey::from_der`), expired ones refused, so a start with a broken certificate changes nothing. `ductus validate` runs the same per entry.
- **One rustls `ServerConfig` per listener** (TLS 1.2 and 1.3, aws-lc, the same stack as the outbound connections), whose certificate comes from a resolver (`Pair`, a `ResolvesServerCert` behind a lock): **reload** swaps what the resolver hands out, so new connections get a renewed pair without rebuilding anything. One task checks every file-backed pair every minute, by a SHA-256 of both files' contents (a renewal of the same key type is often the same size, and copies can keep the old time); no database work. A changed pair that doesn't load is logged once per distinct content and the old one stays.
- **Client certificates:** rustls's WebPKI client verifier against the named CA, wrapped (`ClientCheck`) to match the leaf's subject (`CN`, `O`, `OU`, `C`, `L`, `ST`, `DC` by OID) and DNS names against `subjects`.
- **Handshakes never hold up the accept loop:** MLLP runs it on each connection's own task (`ductus_mllp::serve_with`: an `open` step before the first frame; the listener still closes at once on a drain). HTTP sources and the API use `tls::Listener` (axum's `Listener`): TLS connections are accepted and handshaken on their own tasks, finished ones handed to the server through a channel; the API wraps it in `tap_io` so axum's `ConnectInfo<SocketAddr>` (the audit log's address) still works. Handshakes time out after 10 s. Refusals are logged with a plain reason at most once a minute per listener and address (`Refusals`).
- **The API over HTTPS** sends HSTS (a year). `api.listen` off loopback without `tls` warns at start and in validate (the session cookie is `Secure`).
- **Outbound (0.6.3.2): one way to verify** (`tls::Trust`): the platform verifier (`rustls_platform_verifier`: the system's roots and its checks, the name against the host) plus the CA `ca:` names, and the pair `certificate:` names as the client certificate through a `ResolvesClientCert` (the same `Pair`, so a renewal applies to client certificates too). Names are `ConnectTls { ca, certificate }` (`ductus_core::tls`: `tls: true | { ca, certificate }` on MLLP destinations, flat `ca`/`certificate` on `apis:`, HTTP destinations with a `url`, `alerts.smtp`, webhooks and the heartbeat; LDAP's `ca` is a name); `tls::outbound` + `check_outbound` refuse wrong names and kinds in validate and at start. `Certificates::client` builds one `ClientConfig` per distinct `ConnectTls` and shares it (MLLP destinations naming the same CA share settings and session cache). Users: `ductus_mllp::Client::with_connect` (the client's connect step: a `tokio_rustls` handshake within the send's timeout, its refusals turned into a temporary error's words by `tls::outbound_failure`); reqwest via `tls_backend_preconfigured` (ALPN h2 + http/1.1 set by us) for HTTPS destinations, `api()` (a client per API that names TLS) and webhooks; ldap3's `set_config`; lettre takes certificates rather than settings (extra roots + identity from the pair's PEM; same platform verifier; the transport is rebuilt when the client pair's hash changes). Doctor builds its handshake from the same `Trust` with its recording verifier around the platform one, and after a finished handshake waits up to 500 ms for a TLS alert (TLS 1.3's refusal of a client certificate comes then).
- Not yet (0.6.3.3–4): our certificates in `certificate_status` and their alerts, the UI's "Ours", `ductus cert request/show`, `gen`/`sink --tls`. (0.6.3.3 done: see Certificates below.)

## Retention

- Each interface keeps its messages for one of three windows (`retention:` 1w/3w/7w, i.e. 7/21/49 days; default from ductus.yaml, else 7w): its **tier**. Longer history belongs to the source systems or an archive (optional cold storage is planned); the engine isn't a data warehouse. Tiers and periods are chosen for partition count (statements Postgres can't prune pay for every partition): a weekly tier costs about window ÷ 7 partitions, the daily 1w tier one per day, about 24 in all. Shifting a window by a few days changes that by a fraction of a partition, so windows are whole weeks. A message and its deliveries are stored in the interface's tier and always share it (`tier` column, part of both primary keys). Old messages go by dropping whole partitions (`Store::drop_expired`, hourly, 5 s after startup, and after each retention change): a partition goes once its whole period is older than its tier's days.
- **The held area** (migration 0014): an expired partition holding messages someone still needs (pending: a destination down or paused for months; quarantined, unless the interface says `quarantined: purge`) doesn't stay: those messages move, each with **all** its deliveries, to tier `0` (`messages_held`/`deliveries_held`, partitioned by month), and then the partition drops like any other. Without it, one waiting message kept its whole period for every interface in the tier (a receiver held three months ≈ double the disk; unresolved quarantines, growth without bound). The move (`Store::hold_step`, from the hourly run in `ductus-runtime/src/retention.rs`) walks the partition's primary key in batches of 1,000, busy at most half the time, locking messages then deliveries in id order. Held rows are still partitions of `messages`/`deliveries`: they stay in their destination's queue (same index, same order) and in the message browser; nothing reads or writes by tier. A worker whose update meets a row moved under it gets a serialization failure (40001) and runs the statement again (`retrying` in the store: every statement that updates messages or deliveries goes through it, deadlocks too), and finds the row where it is now; the stress test fails without it. A month that's over is dropped whole once nothing in it is unfinished (no row deletes; the disk goes back at once); the current month isn't, since more can still come. Held tables are created when first needed, one table per transaction. Counted hourly (every held row, so not per API call): `held` in `GET /retention`, `ductus retention`, `ductus_held_messages`/`ductus_held_bytes` in `/metrics`. Measured (`HISTORY=100000 scripts/demo-held.sh`, WSL): 300,000 pending messages with 2 deliveries each moved in 58 s (three partitions of 100,000, 18–22 s each, ~5,000/s with the throttle), then delivered in order in 174 s once the destination was resumed (~1,700/s, a single destination's usual rate). Its effect on ingest during a move isn't measured yet.
- **Kept instead of dropped:** a partition with rows of an interface whose retention is now longer than the tier (a change still moving them) waits for the change. These are reported (`kept` in `GET /retention`, `ductus retention`).
- **Drops don't block:** each partition is detached with `DETACH PARTITION CONCURRENTLY` (no lock that conflicts with inserts or reads; it waits for queries that started earlier instead), checked again (re-attached if it got unfinished messages meanwhile), then dropped. `deliveries` first. An interrupted run is finished by the next (pending detaches `FINALIZE`d, detached leftovers dropped).
- **Changing retention** applies to old messages too (`ductus_store::retention`, `ductus-runtime/src/retention.rs`). The `retention` table holds each interface's applied tier and the running change. One change at a time per interface; a shorter value deletes messages, so it waits for `ductus retention confirm` (API: `POST /retention/{name}/confirm`). When a change starts, new messages go to the new tier at once (intake reads the tier from a shared atomic), and a background task works through the interface's rows in other tiers in batches of 1,000, busy at most half the time: finished messages past a shorter window are deleted with their deliveries; the rest move into the new tier with their deliveries, in one statement. Pending messages aren't touched (a worker is updating them) and move once delivered; the change ends when none are left. Quarantined messages move but are never deleted; past the window they stay in their old tier (and go to the held area when it expires). Held messages within the new window move back like any other.
- **Moving rows and settling:** a message another destination just finished can be moved while a settle statement has it in view; Postgres can't re-check a row that moved partitions and raises a serialization failure (40001), so `settle` retries (it's idempotent). Found by the stress test.
- **Why tier first, then periods:** with days × tiers (~690 leaves per table), statements Postgres can't prune by partition paid for every leaf: the worker's queue read went 8.8 → 20 ms, its delivery update 3.9 → 9.6 ms, the message browser 0.2 → 9.6 ms; at ~100 leaves (the first five-tier design, 7/30/90/180/365) they were back to 5.9, 4.8 and 1.4 ms (pgbench on WSL, prepared statements); three tiers (1w/3w/7w) bring it to ~24. And statements that find messages by `(id, received_at)` pairs carry the batch's `received_at` range (`span`): without it, Postgres priced looking up each message in all ~100 partitions above scanning them, and settling 50 messages read every `messages` partition (84 ms instead of 1.8 ms on 375k rows, and growing with the table).
- Rows stored by engines that don't know tiers go to the 7w tier (the longest) (the column default); the first start of an interface moves its rows to its own tier (that's how migration 0010's copy of older data gets its tiers).

## REST API and drain mode

- **`/api/v1`** (`ductus-runtime/src/api/`): axum, one listener (`api.listen` in ductus.yaml, default `127.0.0.1:7700`, `off` to disable; `--api-listen` overrides). Routes are declared with `utoipa_axum::routes!`, which builds the router and the OpenAPI document (`/api/v1/openapi.json`) from the same handler annotations: the spec can't drift from the code. The UI will use only this API.
- **Who calls (`Caller`, a `Principal`):** a **user** (signed in with a password) or a **token**. Roles: viewer (read), operator (+ drain, pauses, resend/edit, connection checks), admin (+ users and tokens, and every permission). Two permissions go beyond a role (`users.permissions`, `api_tokens.permissions`): `payloads` (read message payloads and saved outputs; editing needs it too) and `audit` (the audit log, below). A token that belongs to a user (`api_tokens.user_id`) acts as that user at most: role = the lower of the two, permissions = the intersection, and it stops when the user is disabled. Handlers call `caller.require(Role)` / `require_permission(..)`; `api/mod.rs` has one table (`ACCESS`) of who may call every operation, and a test fails for an operation without a row.
- **Tokens:** `Authorization: Bearer dux_<64 hex>`. Stored as SHA-256 hashes (`api_tokens`); every call looks the hash up (an index hit) joined to the owner, so revoking or disabling works at once. Service tokens (no owner) are made by admins or on the server with `ductus token create`; users make their own under `/me/tokens` (listed as `<user>/<name>`). Migration 0018 revoked every token made before users existed.
- **Users** (`users`, `ductus_core::password`, `api/users.rs`, `api/me.rs`): local accounts with argon2id hashes (hashing runs on blocking threads, at most 4 at once, so sign-ins can't take intake's cores); wrong passwords count per username (`failed_logins`, lockout window and length in `auth.lockout`); a password an admin chose sets `must_change_password`, and then only `GET/DELETE /session` and `POST /me/password` work (the `MustChange` extractor; everything else answers 403 `password_change_required`). The first admin is made on the server (`ductus user create`; `ductus dev` makes a `dev` admin).
- **Directory sign-in** (`auth.ldap`; `ductus-runtime/src/ldap.rs`, `ductus_core::ldap`, `ductus_store` `directory.rs`, migration 0022): `POST /session` checks a name a local account holds locally and only locally; any other name goes to the directory named by `auth.ldap.resource` (an `ldap:` entry in resources.yaml, so doctor, `ductus ports`, documentation fields and the certificate table cover it). One connection per sign-in (ldap3 over our rustls and platform verifier, plus the entry's `ca`): bind as the service account, find the person (`user_filter`, the username escaped per RFC 4515; more than one match is refused), refuse an Active Directory account disabled in `userAccountControl`, bind as them with the password (never an empty one: that would be an unauthenticated bind), bind back as the service account, read the groups (a base search per configured group; with `nested`, Active Directory's in-chain rule when the root entry says it's AD, else a walk up the groups, at most 8 levels), then highest role group wins. The account (`users.source = 'ldap'`, no hash) is made or updated in one transaction with its audit row (`user.create`, `user.directory_change`). Every `refresh` one task checks again everyone with a live session or token on one connection: a refusal sets `users.directory_refused_at` (the identity join treats it like `disabled_at`, so sessions and tokens stop; the sessions are deleted), logged once (`user.directory_refused`); a directory that can't be reached changes nothing. A wrong directory password counts toward the local lockout once the account exists. No `AuthProvider` trait: SSO (OIDC/SAML) is a redirect flow, not a password check, so its extension point is designed with it.
- **Browser sessions** (`api/session.rs`, migrations 0015, 0018): `POST /session` with `{username, password}` or `{token}` (the latter unless `auth.token_sign_in` is off) sets the cookie `ductus_session=dus_<64 hex>` (`HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api`), stored hashed in `api_sessions` with the user's or the token's id. `Caller` takes a bearer token first, else the cookie: a session acts as its user or token (one join, checked per call) and ends after 12 h idle, 7 days (`auth.session`), sign-out (`DELETE /session`), sign-out everywhere else (`DELETE /me/sessions`), a password change (every other session of that user), or when the user is disabled or the token revoked. Requests that change something with the cookie must carry `X-Ductus: 1`: a header other origins can't send without a CORS preflight the engine never grants, so the cookie can't be used cross-site (`SameSite=Strict` alone is the first line). `GET /session` says who is calling and with which permissions.
- **The audit log** (`audit_log`, migration 0019; `ductus_store::audit`, `ductus-runtime/src/audit.rs`, `api/audit.rs`): one row per thing done, with who (`By`: a user, a token, `system`, `anonymous`), how (`session`, `token`, `cli`, `engine`), the connection's address (`into_make_service_with_connect_info`), what, to what, the outcome and a `detail` document. **Rows are written with the change they describe**: a resend, edit or dismissal inserts its audit row first in its own transaction (its `message_actions` point at it with `audit_id`, and a request that finds nothing to do rolls the row back); account, token and session changes take an `&Audit` and insert it in the same transaction; a sign-in, a failed password (counted and logged together) and a sign-out likewise. Actions with no transaction of their own (pause, resume, drain, retention confirm, connection checks, an export of the log) write the row **first** (`record_first`) and are refused with 503 if it can't be written. A payload read is written before the payload is returned (`record_payload_read`: one row per actor and message per `audit.payload_read_window`; refused with 503 if the row can't be written). The engine writes `engine.start` (with how the previous run on the host ended: an `engine.start` without an `engine.stop` of its instance is a crash), `engine.stop`, `interface.stopped` (the runaway guard tells `Health`, which tells a channel, which a task drains), and `retention.change`. An hourly job (60 s after start, then every hour) sets `message_actions.previous_output` NULL once an action is older than its interface's retention (a copy of a payload must not outlive the message), and deletes `message_actions` and `audit_log` rows older than `audit.keep` (default 6 years, at least 1) in batches of 5,000. `GET /audit` needs the `audit` permission (`format=ndjson` is an oldest-first export, itself logged); `GET /me/activity` is the person's own rows (`audit_log.user_id`: the user, or the owner of a token).
- **Dismissing** (`Store::dismiss`, `POST /messages/{id}/dismiss`, `/messages/dismiss`): a quarantined delivery becomes `filtered` ("dismissed by NAME: reason", reason required), the message is set pending and settled again like after an edit, in the held area as anywhere. It locks the messages first in id order and moves deliveries final to final, so it adds no backward move to the locking rules.
- **Appearance** (`user_settings`, `GET/PUT /me/settings`): a user's theme and custom colors follow them to any browser; the UI keeps a browser copy for the first paint and for token sessions.
- **The web UI** (`ui/`, React; `api/ui.rs`): `crates/ductus-runtime/build.rs` embeds `ui/dist` (each file with a gzip copy when that's a tenth smaller) as a sorted static table; every path outside `/api` is served from it, unknown ones as `index.html` (the app's router shows the page) except under `/assets/`, whose content-hashed names are cached for a year (`immutable`); everything else is `no-cache`, so an upgrade shows at once. Every UI response carries a CSP (own scripts only, `connect-src 'self'`, no framing). Cargo never runs npm: without `ui/dist` a "build the UI" page is embedded, and `DUCTUS_REQUIRE_UI=1` (CI, check.sh) makes that an error. The UI's API types are generated from `ductus api-spec` (the OpenAPI document, without an engine) and committed as `ui/openapi.json` + `ui/src/api/schema.d.ts`; check.sh and CI fail when they don't match the binary. Operation ids must be unique (utoipa takes the handler's name; `every_operation_has_its_own_id`). **Size:** a first visit loads what `index.html` references, at most 300 KB gzipped (182 KB at step 7c); pages used rarely load on demand in chunks of their own (≤ 50 KB each), enforced by `ui/scripts/budget.mjs`. The API reference is one: our own renderer of `/api/v1/openapi.json` (3.7 KB gzipped, the document fetched when opened; no CDN, which hospital networks often block). Off-the-shelf renderers measured 128–1,256 KB gzipped (RapiDoc 128, Redoc 320, Swagger UI 447, Stoplight Elements 650, Scalar 1,256), wouldn't follow the UI's themes or its AAA high-contrast check, and Redoc and Swagger UI call `eval`/`new Function`, which the CSP forbids.
- **What it serves:** engine info and `/health` (no token: for load balancers); interfaces with state (running/stopped by the runaway guard), drain gate and each destination's pending/quarantined counts; the message browser (an interface's messages newest first, paged by id; one message with payload and deliveries); drain status, start and stop; pausing and resuming a destination; retention (each interface's, changes in progress, partitions kept) and confirming a shorter one; `impact`, `owners` and `doctor` as JSON (the same code as the CLI; doctor skips listening ports, which the engine itself holds); owners with who each is (`GET /owners`: an account, a team, an address or nobody, and whether it is the caller, which is the UI's "Mine"; `GET /owners/people`, the accounts that can own things); a preview of moving ownership (`POST /owners/reassign/preview`: `ductus_core::owners::reassign` on the project's interface.yaml files and resources.yaml as they are on disk, a warning when the new owner isn't an account, each file's changed lines, a unified diff for `git apply` and the CLI command; it writes nothing, since the project is the repository's and a server-side edit would be undone by the next deploy); token management; `/events`, Server-Sent Events with the same counts and each interface's and destination's health, sent whenever a count or a health state changes or a delivery finishes (the workers' in-memory counters, so a message resent and quarantined again between two counts still shows); `/metrics` for Prometheus and `/hotspots` (see Monitoring).
- **Message actions** (`api/actions.rs`, `ductus_store::actions`, migration 0016; operator): **resend** puts finished deliveries back to pending in place (`Store::resend`: locks the messages in id order, resets the chosen deliveries, records each in `message_actions` with what it was before, marks the messages pending; the lane's workers are woken through the interface's `Intake`). The message keeps its id, so its worker takes it next in its lane. Quarantined deliveries by default; named destinations whatever they ended as (a replay); `/messages/resend` takes up to 500 ids in one transaction. **Edit** (`Intake::copy_edited` → `Store::copy_edited`) inserts a corrected copy with keys read from the new payload (no dedupe, the original's `origin_id`), filters the original's quarantined deliveries to the copy's destinations ("replaced by edited copy N") and records the link (`copy_id`), in one transaction; refused for a destination where the original is still pending (a worker may hold it). `GET /quarantine` reads quarantined deliveries across interfaces from `deliveries_quarantined`.
- **Queue counts** come from the partial indexes (`deliveries_queue`, `deliveries_quarantined`): their cost grows with the backlog, not with what's kept (about 10 ms for 15k pending here). One **monitor** task (`control.rs`) counts every 2 s, only while someone is subscribed to `/events` or a drain is running, and shares the result with every subscriber.
- **Drain:** each interface has a `Gate` (`gate.rs`). Draining closes them all: `Intake` refuses to store (`gate::Closed`), MLLP listeners close their socket and connections (`ductus_mllp::serve_until`), queued HTTP answers 503 + `Retry-After`, file watchers and schedules wait for the gate. Every store holds a counted `Pass`; the monitor declares the engine **drained** once every gate is closed, no pass is in flight, and none of this engine's destinations has a pending delivery. With `stop`, the engine then exits (`Engine::shutdown`). Resume opens the gates; MLLP listeners bind again.
- **Stop** (`ductus_runtime::stop`; on Ctrl-C, SIGTERM, or drained with `stop`): close every gate and wait until no pass is in flight (each message being stored gets its ACK; an MLLP message being handled is still answered), then cancel the workers' `stopping` token. A worker treats it like a pause (a transform or send under way finishes; it's checked before each message, before each send and in every wait: back-off, rate limit, pause, idle), saves its finished statuses and ends; a thread ends when its workers have (respond-mode workers once their HTTP server has answered what was in flight). Then last activity is saved once more and the API answers its requests in flight. All within `--stop-timeout` (30 s); past it, or on a second signal, the process exits and what was in hand is processed again at the next start (at-least-once, as after a crash). Before this, SIGTERM killed the process outright, as `kill -9` does.

## Monitoring

- **Counts and timings (`stats.rs`)** are atomics in memory, one set per interface, destination and resource, created at startup and shared by intake, the workers and the API: an increment per event, no lock, no write. They start at zero with the engine (Prometheus expects that). Intake counts received / duplicates / store failures; each destination's worker counts sent / filtered / quarantined / retries and times its function, each successful send, and receipt → sent (`received_at` to the moment it's handed over; routed messages when they're routed); respond-mode requests are timed in the responder; `db()`/`api()`/`fetch()` calls are timed per resource around the call on the main runtime (`ResourceCalls`: fixed at startup, so no lock).
- **Histograms** have 17 buckets (1, 2.5, 5 per decade from 0.5 ms to 10 s, then 1 min, 5 min, 1 h) plus a sum; quantiles are interpolated inside a bucket like Prometheus's `histogram_quantile`, means are exact. Few buckets because each is a series per destination.
- **Exposed** as `since_start` in `GET /interfaces` (counts, and mean/p50/p95 in ms), `resources` in `GET /engine`, and `GET /metrics` (Prometheus text format, viewer token: `ductus_messages_received_total`, `ductus_deliveries_total{outcome}`, `ductus_delivery_retries_total`, `ductus_delivery_latency_seconds`, `ductus_send_seconds`, `ductus_transform_seconds`, `ductus_http_request_seconds`, `ductus_resource_call_seconds`, queue gauges from the database at each scrape, `ductus_interface_stopped`, `ductus_draining`).
- **Expectations** (`monitor:` in interface.yaml, `ductus_core::monitor`): `active_within` (with optional `between` hours), `active_by` (a daily, weekly or cron deadline, its window from midnight or `from`), `behind` (messages waiting, the oldest one's age, or both; a destination may set its own). Pure functions of the times below, unit-tested with local times.
- **Last activity survives a restart or a failover** (`activity.rs`, migration 0012): intake and the workers mark `last_received`, `last_sent` and `last_error` in memory (`stats::Moment`: an atomic `fetch_max`, no lock), loaded from `interface_activity`/`destination_activity` at startup; one task saves the ones that changed every 5 s (two statements, whatever the volume; a time never moves back, so a second engine's older write can't undo a newer one). `watched_since` is when an engine first ran the interface: deadlines before it don't count. Rates and timings stay in memory.
- **Pausing a destination** (`ductus pause`, `POST /interfaces/{name}/destinations/{d}/pause`): written to `destination_activity` first, then a `watch` switch shared by the destination's workers (every slot). A worker checks it before each message, before each send (also after a rate-limit wait) and after each retry back-off; while paused it saves its finished statuses and waits on the switch, so it costs nothing. A send under way finishes. Pausing again with a reason adds it, keeping the original time and author (act first, explain after). The drain's "nothing pending" leaves paused destinations out. Resuming (`DELETE`, `ductus resume <interface> [destination]`) returns the pause it ended.
- **Evaluation** (`ductus_core::monitor::diagnose` and `interface_state`, pure; `Engine::diagnose` gathers the facts): per destination the waiting count and the oldest waiting message's age (`Store::oldest_pending`: one probe of the queue index per destination with a backlog, added to every snapshot), quarantined count, last sent and last error, pause, stopped interface, the last 5 minutes and the normal for this hour of the week. States, worst wins: paused > stalled (waiting over `STALL_AFTER` = 1 min and nothing finished for as long; the last error if it's newer than the stall) > error (quarantined) > behind (past `behind`) > ok. For a backlog over a minute old: the trend (catching up with an ETA = waiting ÷ (out − in), or not) and causes (burst: over 2× normal inflow and ≥ 5/min more; slow receiver: over 2× normal send and ≥ 5 ms more). Shown as `health` in `GET /interfaces`, `ductus_destination_state`/`ductus_interface_state`/`ductus_queue_oldest_seconds` in `/metrics`, and in `ductus status` with a token.
- **Rates and normal (`activity::Trends`):** the activity task samples each destination's counts every 5 s (received, finished, sends and their total time): a 5-minute window of samples, and when it last finished something. When the hour of the week changes, the hour just ended is learned if at least 15 minutes of it were watched (`Baseline::learn`: each hour moves 30% of the way to the new value), and the changed baselines are saved in one statement (`destination_activity.baseline_*`, migration 0013, 168 values per array). The window starts over with the engine; the baseline doesn't.
- **Hotspots** (`ductus_core::hotspots`, pure; `GET /hotspots`, `ductus hotspots`): for each destination with a backlog, `Store::lanes` counts the waiting deliveries per lane from the queue index and looks up each lane's first one (its key, attempts, last error). Since a worker handles its lanes one message at a time, a lane whose first message has failed attempts is the one its worker is retrying, and every lane of that worker waits behind it. From that: *blocked* workers (and whether the receiver took other messages since the blocking one arrived, i.e. the message is the trouble, not the receiver), *every worker blocked* (the receiver looks down), a worker or lane with most of the backlog (a hot key; 100 waiting at least), and lanes no worker owns (`ordering.partitions` lowered with messages waiting). On demand only: 300,000 waiting for one destination over 64 lanes takes ~40 ms (WSL), about what counting the queue costs.
- **Alerts** (`ductus_core::alerts`, pure; `ductus-runtime/src/alerts.rs`; `ductus_store::alerts`, migration 0020; `api/alerts.rs`): `alerts:` in ductus.yaml (the only section that may use `${...}`: it is read per environment, `Settings::alerts`) names an SMTP server, channels (email addresses, a webhook in `json`, `slack` or `teams` format) and rules (the first naming a state gives its severity and recipients; `owner` resolves to the email of the one account it names (`owners::find`; not a disabled one), else the `owners:` directory, else the owner text if it is an address). Three tasks run while the engine does, whoever watches: **judging** every 15 s takes one queue snapshot, `interface_state` and `diagnose` for everything (the same as the API), and `alerts::step` on each stored alert (`alert_state`, one row per interface and destination, made at start): fire, escalate (higher severity), change quietly, reopen (bad again within `settle`), recovering, recover, remind (every `repeat` until acknowledged). Paused destinations hold; states that need watching wait until the engine has run a minute (`error` and `stopped` don't). A change is written with its event and its notifications in one transaction, compare-and-set on `rev`, so two engines on one database record it once. **Sending** claims due rows of `alert_deliveries` (the outbox) with `FOR UPDATE SKIP LOCKED` and a two-minute lease, sends each on its own task (lettre over rustls with the platform verifier, as the HTTP client; reqwest for webhooks), and retries with back-off (30 s doubling to an hour, ten tries); at least once, like deliveries. Quiet hours make a notification due when they end; a recovery cancels what still waits and is sent only to an alert someone was told about. The **heartbeat** calls a URL every `every`. History is kept `alerts.keep` (a year). Acknowledge and silence are operator actions, written with their audit row. Measured (1,001 interfaces, WSL): 35 ms a round, +0.1% of a core, +7 MB.
- **Certificates** (`ductus-runtime/src/certificates.rs`, `doctor.rs`; `ductus_store` `certificates.rs`, migration 0021; `api/certificates.rs`): every `doctor.schedule` (6 h; the first 60–120 s after start) the engine runs doctor's checks in `certificates` mode: DNS, TCP and the TLS handshake (after STARTTLS for the mail server) of what has a certificate: HTTPS APIs and destinations, the directory (ldaps://, or StartTLS written by hand like SMTP's: a 31-byte extended request), the alerts' SMTP server, webhooks and heartbeat (not Postgres: connected without TLS; not SQL Server: TLS inside TDS, v0.6). The verifier records the chain before judging it, so a certificate is read even when it isn't trusted. Each server's certificate goes to `certificate_status` (a check that couldn't read one keeps the earlier dates, `read_at`), each run to `doctor_runs` (the last 30; `POST /doctor` stores its run too). No code analysis in `certificates` mode (it only labels "used by"). Judging (the alerts task, every 15 s) reads the stored dates: the earliest expiry in the chain, whole UTC days, against `alerts.certificates.warn_days` (30/14/7): fire at the first step, escalate at each closer one and when expired (critical), no reminders before expiry, quiet change for a short renewal, recover after `settle` (`ductus_core::alerts::certificate_step`; `alert_state.stage`). `GET /certificates`, `ductus_certificate_expiry_seconds{side,resource,host,port}`. Measured: a check of 6 servers ~0.1 s. **Ours** (0.6.3.3, migration 0024 `side`): each `certificates:` pair the engine presents (a TLS listener's, the API's, a client certificate; `ductus_core::tls::presented`) is one target `cert:<name>:<this host>:0` (port 0: no remote row can collide, and one pair served on many ports alerts once), owner = the entry's, else its one interface's. Its row is built from the loaded pair (`certificates::our_row`), so judging, the API and the gauge read memory, not the table; the table is written at start (one transaction) and when `tls::Certificates::watch` (the minute's file check) or a connection check finds a renewal or a renewal that can't be used. In full mode doctor also connects to each TLS listener (loopback for `0.0.0.0`/`::`), records the chain served without verifying it, and judges the path (`judge_chain`: in order, ends at a root, a `certificates:` CA, or a root of the system's (`rustls-native-certs`)).
- **Respond-mode profile** (v0.4 demo, 2 queries + 1 HTTP call to another respond interface, local database): 2.1–3.0 ms in the engine on average; the three calls one after another ~0.5–0.7 ms each, the engine itself ~0.6 ms; curl sees ~0.4 ms more (HTTP both ways). The lever is in interface code (independent calls together), nuances.md.

## Threads and isolates

- **Shared pool** (default `isolation: shared`): `--threads` (default = cores) OS threads, each a tokio current-thread runtime + `LocalSet` + **one** V8 isolate hosting many interfaces. Each interface is one async task (`Worker`); shared interfaces have one slot (all lanes). See `docs/shared-pool.md` for the scoping rules interface authors follow.
- **Dedicated** (`isolation: dedicated`, `workers: N`): N threads, each with its own isolate, lanes split round-robin.
- V8 isolates can't move between threads; the isolate is `Rc<RefCell<Isolate>>` per thread and is **only borrowed for synchronous calls, never across an await**.
- **Async transforms**: `Isolate::begin` returns `Call::Done` (sync transform) or `Call::Pending` (a future not borrowing the isolate). A per-thread `drive_event_loop` task polls the JS event loop when kicked, so many interfaces can await DB calls concurrently on one thread. `settle` converts the result.
- Wake-ups: ingest calls `notify_one` on the owning slot's `Notify` (permit kept if busy); a 30 s idle poll is only a safety net.
- **Store calls from workers run on the main runtime** (`Worker::db`). The Postgres pool is shared with intake, and a connection's socket is served by the runtime that opened it: a connection opened on a worker thread stalled intake's commits (the senders' ACKs) whenever that thread was busy in V8. Measured in the runaway demo: one sender's 200 ACKs took 4.0 s instead of 0.9 s; a pass-through run 3.3 s → 0.5 s.

### Runaway scripts (`ductus-script/src/guard.rs`)

- Every call into V8 is **armed** with a deadline: the interface's `timeout` (default 5 s, 10 ms–10 min) for its `transform`, the module's for loading it. A single `script-watchdog` thread checks all isolates every 10 ms and, past a deadline, calls `IsolateHandle::request_interrupt`. The interrupt runs **on the isolate's thread inside the running code**: it checks the call is still the one armed (generation counter), reads the JS stack to find whose code it is (module URL, then folder), and calls `terminate_execution`. `disarm` then cancels the termination; the isolate stays usable. Terminating only from inside the interrupt means a call that finished in the meantime can never be hit.
- The event loop runs continuations of *any* interface, so it's armed with the **shortest** budget on the isolate; when it passes, the interrupt extends the deadline to the budget of the interface found on the stack (or the longest, if none is found).
- Heap: each isolate is created with `heap_limits(0, isolates.heap_mb)` (`ductus.yaml`, default 512). Near the limit V8 calls our callback: we raise the limit by a quarter (or the process dies) and stop the running call the same way, then run a full GC.
- **A termination in the event loop drops every queued continuation** (V8 clears the microtask queue), not just the runaway's: every async transform in flight on that thread will never settle. The worker's `drive_event_loop` signals them all (`watch`): the culprit gets the `Runaway`, the others a transient error and are retried.
- Limits: code in a shared module resumed after an `await` has no interface file on its stack, so it can't be attributed: all in-flight transforms are retried and it can recur. While runaway code runs, its thread's other interfaces wait up to `timeout`.

## SDK ↔ engine protocol

- Each interface is loaded through a generated glue module: `export const run = (raw) => __invoke(entry.transform, raw, formats)` where `formats` = `InterfaceConfig::format_spec()` (`{"input", "output", "http"}`).
- `__invoke` decodes the payload by format, calls `transform`, serializes the result. Special results: `null` → filtered; `kill(reason)` → string prefixed `ductus_script::KILL`; errors containing `QUARANTINE` / `TRANSIENT` markers are classified by the worker.
- Respond-mode HTTP: the engine passes a JSON envelope (method, path, params, query, headers, body); the SDK returns a JSON envelope (status, headers, body).
- Native ops (`ops.rs` / `ops.js`): `op_ductus_db_query/execute/fetch/variable/secret`, exposed to the SDK as `globalThis.__ductus_ops`. The runtime implements the `Services` trait (`services.rs`); parameters are always bound.
  - Postgres: queries are wrapped as `WITH ductus_q AS (<sql>) SELECT json_agg(...)` so Postgres produces the JSON.
  - SQL Server (`mssql.rs`, tiberius): `$1` → `@P1` outside literals/quoted names/comments; rows are converted in Rust to match Postgres's JSON (numbers, ISO 8601 times, `\x` hex binary, upper-case GUIDs; unnamed columns `column<N>`); first result set only. Own small pool: a connection goes back only after a call that succeeded (a failed one may be mid-response or inside an open transaction); idle > 5 min is closed (firewalls drop quiet connections); Azure/AG routing is followed once; named instances via SQL Browser.
  - `fetch()` (`services.rs` `http_fetch`, one shared reqwest client): the engine returns every status as a response and marks only network errors/timeouts transient; the SDK turns 5xx/408/429 into transient errors unless `retry: false`. Responses capped at 16 MB; messages never show the query string or URL password.
  - `api(name)` uses the same op with `api` set and a path as `url`; the engine (`resolve_api`) puts the path under the API's URL, adds its headers (the code's win) and its timeout, so tokens stay in `resources.yaml` and never enter V8. HTTP destinations with `api:` are resolved the same way when their sender is built.
  - Under `ductus test` the SDK swaps the ops for mocks (`mock.db/fetch/env/secret`, reset before each test; unmocked calls fail with how to mock them), and tests may be async (`run_tests` drives the event loop).
  - Pools: one shared pool per database resource (`max_connections`). A dedicated interface can have its own (`dedicated_pools: { patient_db: 4 }`), created once and shared by its worker threads; its `db()` calls use it before the shared one (a bulkhead: a busy interface can't starve the others). Shared-pool interfaces can't: the calling interface isn't known inside a shared isolate.
  - DB and HTTP calls are spawned on the **main multi-thread runtime**, not the worker thread's: a socket is served by the runtime that opened it, and a worker thread busy in V8 would delay its replies.
  - Temporary (message waits and retries): connection/TLS errors, pool timeouts, deadlocks, failovers, **login failures and missing databases** (fixed by fixing config; quarantining every message would be worse). Everything else (SQL errors) is permanent → quarantine.

## Storage

- `messages`: partitioned by **retention tier** (`tier`, LIST: `messages_t7` ... `messages_t365`), then by time (`received_at`, RANGE): a day for the 1w tier, a week for 3w/7w (`messages_t21_20261005`, tiers named in days, partitions by the period's first day, bounds at midnight UTC). About 24 leaves per table; see Retention below for why. Partial index `(interface, partition_key, id) WHERE status = 0` (the queue of older versions; still used to find pending messages). `deliveries` has the same tiers and a partition for every `messages` partition, with the same bounds (copied from the catalog). Partitions created 3 days ahead, hourly, **one table and tier per transaction** (`messages`, then `deliveries`): one transaction holding both tables deadlocked with status settling, which reads `deliveries` then updates `messages` (migration 0006; reproduced 8/8 by `partition_maintenance_never_deadlocks_with_settling`), and one holding two tier tables deadlocks with queries, which lock every tier in creation order (found by the stress test, migration 0010). Each waits at most 2 s for its lock (`lock_timeout`), then gives up until the next hour: a partition DDL waiting behind a long query makes every later insert queue behind it (measured: an insert waited the whole 4 s of a "report"; `partition_maintenance_never_holds_up_inserts`). Startup retries for up to a minute. **Last resort:** when tomorrow's partitions are still missing (every hourly try for two days was blocked), maintenance waits for the lock however long it takes (`lock_timeout = 0`, logged as a warning): new messages wait behind it for as long as the blocking query runs, which beats having nowhere to store them at midnight (`partition_maintenance_waits_when_the_day_is_close`). With nothing to create, maintenance takes no lock at all. **Locking rules** and the stress test that checks them (`everything_at_once_without_lock_errors`: inserts with colliding dedupe keys, a batch writer, three destinations draining, partitions created, keys purged, all at once; it catches the old deadlock 3/3): see `decisions.md` "Locking" in the planning repo, and CLAUDE.md.
- `dedupe_keys(interface, key, seen_at)`: checked and claimed in the same transaction as the message insert (one commit).
- `durability: relaxed` sets `synchronous_commit = off` for that insert only.
- `source_state(interface, key, value jsonb)`: what sources remember (file progress `file:<name>`, `schedule`). Always written in the same transaction as the messages it accounts for.
- Batched inserts (`Store::insert_batch`) use one `INSERT ... SELECT FROM unnest(...) WITH ORDINALITY ORDER BY n` (ids keep the batch's order) and claim dedupe keys in bulk (repeats inside the batch are duplicates after the first).

## Performance notes (measured, WSL, 2.5 ms fsync disk)

- One sender connection is bounded by one durable commit per ACK: ~443 msg/s strict, ~868/s relaxed; 16 connections ~2,100/s (group commit).
- SDK: ~14.8k realistic ORU transforms/s per thread. Embedded V8 call overhead is negligible.
- 1,001 interfaces: ~111 MB, 0 idle CPU. Ready (launch → `started`) in 0.69–0.83 s warm, 1.3 s with a cold file cache (0.6.2, WSL D: disk; it had grown to 4.9–5.2 s by v0.5, unmeasured since v0.3's 0.4 s). Where it went: retention applied in one transaction per interface (3.3 s; now one read, plus writes only for changes), every worker reading its queue at once through the 32-connection pool (startup tasks queued behind ~1,000 reads; now only interfaces with something waiting read at start), reconcile over the whole backlog for every interface (now only those with something waiting), destinations registered with a conflict check each (now read first). Each step's time: `RUST_LOG=info,ductus_runtime=debug` ("start: …"). Over a Unix socket (or with `TCP_NODELAY`) the start is 0.35 s: sqlx 0.9 doesn't set `TCP_NODELAY`, and statements with large parameters (1,001-element arrays) wait ~40 ms for a delayed ACK over TCP. Message flow is unaffected (fan-out benchmark within noise with and without it). Fixed upstream (transact-rs/sqlx#4336, after 0.9.0): the next sqlx release brings it.
- File ingest (`split: records`, `durability: relaxed`): ~100k CSV rows/s (300,000 rows, 13 MB, 500 per transaction); ~155k before status per destination (a delivery row costs about as much to insert as the message). Strict MLLP ingest (16 connections) unchanged: ~3,100/s either way, it's bound by the commit flush.
- Fan-out (`scripts/bench-fanout.sh`, 6,000 messages, 16 connections, strict, file destinations): 1 destination 3,125 ACKs/s, all delivered in 3.9 s; 5 destinations 3,081/s, 3.6 s (8,444 deliveries/s); 25 destinations 1,710/s, 8.0 s (18,776 deliveries/s). Ingest holds up to 5 destinations; at 25 the drain's status writes (~19k/s) compete with ingest for the same database. A single destination drains at ~1,500/s: a shared interface has one worker per destination (`isolation: dedicated` with `workers: N` for more). With retention tiers (v0.5 step 5; fresh databases, two runs each, before → after): 1 and 5 destinations unchanged within noise; 25 destinations ingest 1,663–1,751 → 1,394–1,445 ACKs/s and deliver 4–13% slower (each message writes 25 delivery rows, whose key now includes the tier). A fresh database has ~15 partitions per table; after 7 weeks, ~24 (see Retention). At steady state (every partition a database has once its longest window has passed; two runs each): five tiers (115 partitions per table) → four (46): everything delivered 1 destination 5.9–6.5 → 4.8–5.0 s, 5 destinations 5.3 → 4.1–4.2 s, 25 destinations 12.3–12.7 → 9.3–9.4 s (~12,000 → ~16,000 deliveries/s); ingest unchanged for 1 destination, ~8% higher with 5 and 25. 50 destinations (step 6, three tiers at steady state): ~500–700 ACKs/s, everything delivered in ~16 s (~19,000 deliveries/s): delivery throughput is flat from 25 destinations up, ingest falls with each delivery row the ACK waits for (guideline in nuances.md). The queue index (migration 0011) changed none of these (fresh tables: no delivered rows ahead of the queue); it matters once a day of delivered traffic sits ahead of a backlog (queue read ~300 ms → ~1.3 ms).
