# Nuances: releases

What could surprise you here, why it is so, and what to do. Each entry has a level, 1 (day one) to 5 (expert): the [index](index.md) lists them all by level.

## A release is the commit, not the folder (level 1)
- **What:** `ductus release` carries HEAD's files (the project's folder of the commit), read from git's own store, not what's in the folder. A file changed and not committed, deleted, added with `git add` but not committed, or new and not ignored by `.gitignore` refuses the release, named. `--uncommitted` carries such files as they are in the folder instead (a deleted one is left out), and the release lists them; `ductus release check` then says so with a ⚠.
- **Why:** a release must be something anyone can find again: the same commit, the same release. A file only on your disk would deploy code nobody can read in git.
- **What to do:** commit, or add the file to `.gitignore` if it's yours alone (`out/`, notes). Keep `--uncommitted` for trying a release out on a test engine. `.ductus/` is never looked at: it's where releases are written.

## The same commit gives the same release id, whatever the reason or the machine (level 2)
- **What:** the release id is a hash of the files the release carries (each text without a byte order mark and with `\n` line ends), not of the archive. Two releases of one commit have one id even with different `-m` reasons, made on Linux and on Windows (where Git checks files out with CRLF), on different days. Their archives may differ (the manifest says who, when and why), and so may their files' sizes on disk.
- **Why:** the id answers "is this the same code?", which is what promotion and rollback need; who made it and why are recorded beside it, not in it.
- **What to do:** compare releases by id, never by the archive's checksum. To recompute an id by hand: `sha256sum` each file under `project/` in path order, as `ductus release 1` lines ([how](../operate/releases.md#the-release-id)).

## Texts are carried normalized; other files byte for byte (level 3)
- **What:** a file that is UTF-8 without a NUL byte is a text: carried without a byte order mark and with CRLF pairs as `\n` (an HL7 fixture's lone `\r` segment ends are kept). Anything else (an image, a spreadsheet, a file in Latin-1) is carried exactly as committed and listed in the manifest's `binary`.
- **Why:** the same as for code versions, so a Windows checkout and a Linux one are the same release; a file that isn't text can't be "normalized" without breaking it.
- **What to do:** nothing usually. A CSV fixture saved in Latin-1 is carried byte for byte (still the same on every machine); save it as UTF-8 if you want it treated as text.

## A committed private key refuses the release (level 1)
- **What:** a committed file holding a PEM private key (`-----BEGIN … PRIVATE KEY-----`) or named like a key store (`.key`, `.p12`, `.pfx`, `.jks`) refuses the release, named. Certificates (public) are fine.
- **Why:** a release is copied to CI, to servers and (from 0.7.4.3.3) into the database: a key in it is readable by everyone who handles it.
- **What to do:** `git rm --cached <file>` and commit; keep keys out of the project (`*.key` is in the `.gitignore` `ductus init` writes) and name them in resources.yaml by a path on the server. The key stays in git's history: if the repository was shared, replace the key.

## Code imported from outside the project refuses the release (level 2)
- **What:** an interface whose code imports a file outside the project folder (an absolute path, or `../` reaching above the project) can't be released: the release can only carry the project. An absolute import is named in the refusal; a relative one that reaches out fails to load from the unpacked copy, with the path it looked for.
- **Why:** the release must run the same code wherever it goes; a file outside it would be whatever that server has at that path.
- **What to do:** move shared code into the project (`lib/` is the place) and import it from there.

## The gate tests what the release changes there, by code version (level 2)
- **What:** `ductus release check --env prod` runs the tests of the interfaces whose code version differs from what runs on prod's database (and those new there). An interface whose code is unchanged isn't tested again, even if its tests changed: they ran when the release was made, on the same code. A change only to the project's own files (resources.yaml, environments, secrets) selects no tests: `validate` checks those. Without the database, or for a release made with `--no-tests`, every test runs.
- **Why:** at a thousand interfaces every test takes seconds more than the few that matter, and a test of unchanged code in an unchanged binary can't give a different answer.
- **What to do:** `--all-tests` when you want them all anyway (a new Ductus version on the server, say). Give the gate the environment's database, read-only (`DUCTUS_DATABASE_URL`): without it the gate can't say what changes.

## "What runs there" is what the engines recorded, not what the folder holds (level 3)
- **What:** the gate compares the release with the versions the environment's engines recorded at their last start or handover (0.7.3), not with files on the server. An interface removed from the project still has its last record there; one that never ran there is "new".
- **Why:** the record is what's known to have run; a folder may have been changed since without a start.
- **What to do:** if the gate says nothing changes but you expected it to, check what the engines run (`GET /interfaces/{name}` `code`, or the interface's History tab).

## The tests at release time run in `dev` (level 3)
- **What:** `ductus release` runs the tests with `--env dev` unless you say `--env`: `${...}` in interface.yaml are filled from `environments/dev.yaml` for them. The release itself is the same for every environment (code versions count interface.yaml as written).
- **Why:** tests run without databases and connections; the environment only fills values in.
- **What to do:** when a test depends on an environment's values, make the release with that `--env`, or rely on the gate, which runs the changed interfaces' tests in the environment it checks.

## Checking a release on an engine runs its code there, with that environment's secrets (level 2)
- **What:** `POST /releases/{id}/check` runs `ductus release check` on the engine's server, as the engine's account, with its environment's values, its secret key and its database (read-only): `validate` loads every interface's code and the tests of what changes run it. It needs the `deploy` permission, which only operators and admins can have (giving it to a viewer is refused; a directory group can't give it to one either).
- **Why:** a check is only worth something where the environment is: its secrets, its certificates, its database. That also means whoever may check a release may run code with prod's secrets, which is what deploying will be.
- **What to do:** give `deploy` to the people and the CI token that ship changes, as carefully as `payloads`. Every check is in the audit log (`release.check`) and kept with the release.

## A check on the engine slows its intake while it runs, and runs one at a time (level 3)
- **What:** the check runs on the engine's server as a separate process, spread over every CPU as `validate` and `test` are, for seconds (at a thousand interfaces: 6 s, 10 s with every test). Measured on a 4-core machine, one interface's intake fell from ~800 to ~650 messages a second over a run that overlapped one check, and to about half while checks ran back to back; ACKs waited up to ~0.1 s instead of ~0.03 s. Nothing was refused or lost. The process runs at a lower CPU priority (nice 10 on Linux, below normal on Windows), which made no measurable difference there. A second check while one runs on the same engine is refused with 409 ("try again when it ends"). The call answers when the check ends.
- **Why:** a check is only worth something where the environment is, and `validate` at scale needs the CPUs it uses. Half of ~800 a second is still far above what a busy feed sends (a large hospital's ADT feed: tens a second at its peak), so messages wait milliseconds, not minutes.
- **What to do:** check once per release you mean to ship to that environment, not on every commit: like any work added to a running engine (reports, exports, replays, frequent polling), its value has to be worth what it takes from the messages meanwhile. On an engine that runs near its limits, check against a test engine sharing prod's configuration, or run `ductus release check` on another machine given prod's database (read-only) and secret key. In CI, retry on 409 after a pause, or check one environment at a time.

## The same release stored twice is stored once, with its first manifest (level 2)
- **What:** `POST /releases` with a release whose id is stored already answers 200 with `"new": false`, who stored it and when, and changes nothing: a second archive of the same commit made with another `-m` reason keeps the first one's manifest (who made it, why).
- **Why:** the id is the files ([above](#the-same-commit-gives-the-same-release-id-whatever-the-reason-or-the-machine-level-2)); a release is what it carries, and storing it twice would give one release two stories.
- **What to do:** say why a change ships where it ships: in the deploy's reason (0.7.4.4), not in a second `ductus release -m`.

## Stored releases are kept (level 3)
- **What:** releases stored on a database stay there, with their checks: nothing deletes them. A release adds only what earlier ones and the engines' code versions don't already hold (each text once, each folder's file list once), plus its manifest (hundreds of KB at a thousand interfaces) and its commit history (20 KB per 1,000 commits).
- **Why:** a deploy, a rollback and "what did prod run in March" choose among stored releases; what's measured is small next to messages.
- **What to do:** nothing at the sizes measured ([releases](../operate/releases.md#measured)). A repository with a very long history (100,000 commits) adds 2 MB a release: tell us if that matters to you.

## An engine in release mode runs nothing until a release is deployed, and its API starts on its defaults (level 1)
- **What:** `ductus run --releases` (DUCTUS_RELEASES) runs the release last deployed to its environment for its project on its database. Before the first deploy there is none: the engine starts with no interfaces (`started interfaces=0`), says so in its log, and waits. Its REST API listens where `--api-listen` (DUCTUS_API_LISTEN) says, else on 127.0.0.1:7700, without TLS and without an allow list: those settings are in the project's `ductus.yaml`, which arrives with the first release.
- **Why:** in release mode the project is in the database, not in a folder on the server; there's nothing else to read them from yet.
- **What to do:** deploy the first release from the server itself (`ductus deploy … --to http://127.0.0.1:7700`), or set DUCTUS_API_LISTEN for that first deploy on a network you trust. From the first release on, `ductus.yaml`'s `api:` settings apply.

## A deploy is refused when it would undo someone else's work, and a release is the whole project (level 2)
- **What:** for each interface a release changes, the version running there must be the deployer's own, or come from a commit in the release's history (a colleague's merged work), and not from files never committed; the files outside every interface (`ductus.yaml`, `resources.yaml`, `environments/`, …) are held to the same rule. Otherwise the deploy is refused before the gate runs, naming the interface, whose work it was, when they deployed it and why it would be undone. Because a release is the whole project, a colleague's deployed but unmerged work on another interface refuses your release too: it would put that interface back. "The same person" is by name: the token's or account's that deployed. A release made without git is held against the release it names as its base (`ductus release --over`).
- **Why:** two people deploying from their own branches would otherwise undo each other's changes without either knowing; merging first is what makes a release carry both.
- **What to do:** merge their commit and release again (what's in `main` is assumed shippable). To undo their change on purpose, `ductus deploy --force -m "why"`: the audit log (`release.force`) names each interface and whose work, and the deployment's history keeps the warning.

## A rewritten history is accepted once a deploy brings the same files from it (level 3)
- **What:** the "replaces" check judges a running version by the commits it was deployed from. A version first deployed from a commit your history no longer has (after a squash, a force-push, or moving the project to a fresh repository) is accepted when any later deploy ran the same version from a commit your history has, with its files committed there (since 0.7.5). Until such a deploy, a release from the rewritten history that changes that interface is refused as if it undid someone's work. Folder mode's warning follows the same rule.
- **Why:** the version is a hash of the files, so the same files from a new commit are the same work; but only a deploy records that a commit in your history holds them. The check doesn't compare file contents with other histories.
- **What to do:** after rewriting a history, deploy a release from it that leaves the interfaces as they run (it's accepted: nothing they run changes), then go on as usual. Or, once, `ductus deploy --force -m "history rewritten"`: the audit log keeps why.

## A deploy reuses a recent passing check only when nothing was deployed there since (level 2)
- **What:** a deploy runs the gate (`ductus release check` against that environment and database) unless a check of the same release passed there within DUCTUS_DEPLOY_REUSE_CHECK (default 1 h), run by the same Ductus version, with **no deployment of any kind recorded in that environment since**: a restart, a handover, another release (and never a check from before the engine you deploy to started). Then it reuses that check and says which (`gate: reused check #12 …`); otherwise it runs the gate and says why none could be reused. `--all-tests` never reuses one.
- **Why:** a check says the release fits the environment as it was at that moment; any start or deploy can change what it would find (another interface's version, the database's migrations).
- **What to do:** check a release on the engine (`POST /releases/{id}/check`) when you want to know before the change window, then deploy within the hour; set DUCTUS_DEPLOY_REUSE_CHECK=0 to run the gate at every deploy.

## In release mode the files on the server are the database's copy (level 2)
- **What:** each release is unpacked from the database into `<DUCTUS_RELEASES>/<release id>/` the first time an engine runs it there (a deploy in place unpacks it before applying); the running release, every release an interface still runs from (after deploys in place, an interface a deploy left alone runs the code it loaded from its own release's folder), and the two used last are kept, older folders removed. A folder without its marker file (`.ductus-release`, written last) is unpacked again. An edit to those files on the server is never deployed and is replaced the next time the folder is unpacked.
- **Why:** the database holds what was released, gated and recorded; a folder only mirrors it so the engine can read it like a project.
- **What to do:** change the project, release, deploy. To look at what runs, read the folder, or the release itself (`GET /releases/{id}`).

## A deploy applies by a handover: to a new process under systemd, in the engine's own process elsewhere (level 1)
- **What:** a deploy that changes the project's own files read at a start, or moves a port from one interface to another, applies by the handover ([the others go in place](#a-deploy-goes-in-place-unless-it-changes-the-projects-own-files-level-1)): a new engine runs the release beside the old one, then takes over (receiving never stops). Under the package's systemd unit (a control socket) the new engine is a new process; on Windows, in a container and under a plain `ductus run` it runs in the engine's own process, so the Windows service stays Running and the container never restarts ([nuance](upgrades.md#without-a-control-socket-the-handover-runs-in-the-engines-own-process-level-2)). The deploy's answer comes from the engine being replaced, once the new one sends; it says which (`✓ handed over to ductus 0.7.0 (pid 4598)` or `✓ handed over to a new engine in this process`). Only `ductus dev` takes no deploys (409).
- **Why:** one way to apply a release everywhere, with the same promise: nothing refused, a release that can't start changes nothing.
- **What to do:** nothing differs for the person deploying. On Windows and in containers, leave room for a second engine's memory during the deploy, as on Linux.

## A deploy goes in place unless it changes the project's own files (level 1)
- **What:** a deploy works out what the release changes here, per interface, from the two releases' code versions and interface.yaml files (the answer's `·` lines, `plan` in the API). Every change to an interface is applied **in place**, in the running engine, one of two ways. A change to its code (any file its version counts), `script`, `destinations` (added, removed or changed), `output`, `retry`, `rate_limit`, `timeout`, `about`, `custom`, `monitor`, `alert` or `source` goes **between two messages**: each changed interface's workers finish the message in hand on the old code, then go on with the next on the new one. A change to what a start sets up for it (`format`, `ordering`, `workers`, `isolation`, `dedicated_pools`, `durability`, `dedupe`, `retention`, `quarantined`, or queue ↔ respond mode) **restarts that interface alone** ([nuance](#an-interface-whose-start-time-settings-change-restarts-alone-level-2)). Either way every other interface never pauses and no new engine starts. A changed `source` moves, swaps or restarts alone ([nuance](#a-source-changed-in-place-moves-swaps-or-restarts-alone-level-2)); an interface added or removed goes in place too, whatever its source ([nuance](#an-interface-added-or-removed-in-place-starts-or-stops-alone-level-2)). Only these need the handover, and the answer names which: the project's own files read at a start (`ductus.yaml`, `resources.yaml`, `docs-schema.yaml`, this environment's `secrets/<env>.json`, or a variable whose new value changes what `resources.yaml` or `alerts:` fill in), a port moving from one interface to another, and the first release on an engine (a new binary, too, is a restart or a handover). A new value in this environment's `environments/<env>.yaml` goes in place, judged by what it changes in each interface ([nuance](#a-variables-new-value-reaches-what-it-fills-in-and-the-code-that-names-it-level-2)); another environment's file changes nothing here. A release that changes nothing an engine runs (a README, a test, a fixture) is applied in place with nothing to apply: recorded, and the engine runs it from then on. A deploy in place is recorded as a deployment of its own (`how` = `deploy`, the release it applied), and `ductus history` says "deployed a → b in place".
- **Why:** the everyday deploy (a code fix, a destination added) shouldn't pause every other interface's sending, and neither should a rarer change to one interface's settings: those are set up per interface, so one interface can be set up again alone. The project's own files are read once, by the whole engine.
- **What to do:** nothing for the everyday deploy. To keep handovers to a change window, deploy with `--in-place-only`: a release that needs the handover is refused before the gate runs, saying why, and you deploy it again without the flag in the window.

## An interface whose start-time settings change restarts alone (level 2)
- **What:** a release that changes what a start sets up for an interface (`format`, `ordering`, `workers`, `isolation`, `dedicated_pools`, `durability`, `dedupe`, `retention`, `quarantined`, or its HTTP source between queue and respond mode) restarts that interface in the running engine, the answer saying so (`(in place, restarting alone: `ordering` changed …)`, then `restarted alone (N ms)`). Its claim, listener, gate and counts stay: its senders never notice, and what it receives meanwhile is stored and ACKed as always (the new settings apply from the first message stored after its intake switches, which waits for any store in flight). Its workers all stop between messages (each finishes the message in hand, as at a stop), then its lanes are decided as a start decides them (a changed `ordering` adds lanes after the old ones, which are read first: [ordering](ordering.md)), its retention applied as a start applies it ([a shorter one waits for a confirmation](retention.md)), and its new workers start on the new settings, where a start would place them (a dedicated interface's on threads and database pools of its own). Sending pauses for that interface alone, while its workers stop and start again (22–57 ms measured at 1,001 interfaces: [the guide](../operate/releases.md)). A respond-mode request that arrives meanwhile waits and is answered by the new workers. Changing to respond mode gives its claim back (what its queue holds stays stored, as for a removed interface); changing to queue mode claims it (refused, the whole deploy, when another engine runs it), and a respond-mode request still waiting then gets an error. A new `format` applies to messages received from then on: those already stored are read by the new code as they were received (as after a handover).
- **Why:** these settings shape how messages are stored, laid out in lanes or run, so they can't change between two messages; but they're set up per interface, and stopping every worker of one interface before starting the new ones means no lane ever has two owners, whatever its new number of workers.
- **What to do:** nothing usually. Before changing `format`, let the interface's queue empty (`ductus status`), or make sure its new code reads what's already waiting. Changing between queue and respond mode changes what its callers get back (202 and a stored message, or the code's answer): agree it with them.

## An interface added or removed in place starts or stops alone (level 2)
- **What:** a release that adds an interface starts it in the running engine: claimed (a `Refused` 409 when another engine runs it, nothing changed), its lanes, destinations and retention set up as a start sets them, its code loaded, then its source started: its MLLP listener, file or SFTP pickup or schedule, or its HTTP route (beside the others on its port, or on a new server; respond mode too). Host names in its `allow:` list are looked up before it listens. A removed interface stops taking messages (its gate closes and what it was storing finishes), its source stops (its port is closed by the time the deploy answers; MLLP connections finish the message in hand; its HTTP route answers its requests in flight, and its server closes when no other interface's route is on it), its workers stop between messages, and its claim is given back. What waits for it stays stored for whichever engine runs it next: added again (here or on another engine), it sends what waited, in order, and its pickup reads what landed in its folder meanwhile; until then nothing reads that folder, and an MLLP sender is refused a connection. A [retention change](retention.md#one-retention-change-at-a-time-per-interface-level-3) it was running stops after its batch and carries on once an engine runs it again. The other interfaces never pause. One case still goes by the handover, decided as the deploy applies (the answer's steps say why): a port, or an HTTP method and path, moving from a removed interface to an added one.
- **Why:** an interface's source can start and stop without touching anything else, HTTP routes included (each request is answered by the routes current when it came); a port changing hands can't, here, without refusing a connection for a moment. The handover keeps the socket open across the change.
- **What to do:** nothing for most changes. To retire an interface, let its queue empty first (`ductus status` shows what waits) or it waits, stored, for an engine that runs it. A deploy adding an interface another engine runs is refused whole, naming that engine: stop it there first, or move it with that engine's next deploy. To keep a port's move out of business hours, deploy it with `--in-place-only` outside the window (it's refused, saying why) and again without the flag in the window. A removed interface's alerts stay as they were, no longer judged, as after a handover that leaves it out.

## A source changed in place moves, swaps or restarts alone (level 2)
- **What:** a release that changes an interface's `source` applies it in the running engine, the interface's other parts as for any change in place, its source by kind:
  - **An MLLP port or host moved:** the new port listens first, then the old one closes as a drain closes it: each open connection finishes the message in hand (stored, then ACKed) and is closed. A sender still pointed at the old port is refused from then on; one pointed at the new port connects at once. Nothing it had an ACK for is lost, and nothing is stored twice.
  - **TLS or `allow:` on the same port:** swapped in the running listener, which never closes. New connections get the new certificate and are judged by the new list. Open connections keep their TLS session (and the certificate they were shown) until they reconnect. Open connections from addresses the new `allow:` refuses are closed after the message in hand (its ACK sent; logged `allow: closing a connection its new list refuses`); a sender in the middle of a frame has it read, stored and ACKed first. On HTTP, a connection between requests closes at once; a large response written in several parts can be cut short, and its caller sees a closed connection.
  - **An HTTP route** (path, method, port, TLS, `allow:`): moved on the server for its port, beside the other interfaces' routes there, or to another server (which listens first). A request in flight is answered by the routes it came to; the next one by the new routes. The port's TLS and `allow:` are the same for every interface on it (`ductus validate`), so a release changes them for all of those interfaces together, and the server swaps them as the first of them is applied.
  - **A file or SFTP pickup, or a schedule:** the old one stops as a stop stops it (between messages), then the new one starts. Two pickups of one folder never run at once. A file the old pickup was reading is read again by the new one if it's still in the folder it reads (records already stored carry on from where they were, as after a restart).
  - **Another kind of source** (a file pickup becoming an MLLP listener, say): the new one starts first when it listens, the old one stops, and the other way round when it doesn't.
  - **Between queue and respond mode:** the interface restarts alone ([nuance](#an-interface-whose-start-time-settings-change-restarts-alone-level-2)), its route answered the new way once its new workers run.
  The handover applies these instead, saying why: a port, or an HTTP method and path, moving from one interface to another (two interfaces swapping ports included); an interface listening on its own port another way (MLLP becoming HTTP there, or another host). A new port that another program holds fails the deploy in place (everything put back), and then the handover, naming the port.
- **Why:** a listener can open a second socket before closing the first, but not hand one socket from one interface to another without a moment refused; the handover can. Q3 of 0.7.5.2: a removed address is usually a security decision, and MLLP connections stay open for weeks, so waiting for them to reconnect could leave a refused sender connected for that long.
- **What to do:** move a port in two steps with its senders: deploy it, then repoint the senders (they're refused at the old port meanwhile and send what they kept once repointed), or have them send to both ports for the change. A port set by an environment variable moves the same way when only the variable's value changes ([nuance](#a-variables-new-value-reaches-what-it-fills-in-and-the-code-that-names-it-level-2)). To narrow an `allow:` list, agree the addresses with the senders' owners first: an open connection from one you left out is closed by the deploy, and is refused when it reconnects. The listener's refusals (`source_allow.refused` and the last refused address in the API's interface status) count from the deploy, since the new list is counted afresh.

## A variable's new value reaches what it fills in, and the code that names it (level 2)
- **What:** when a release changes a value in this engine's environment file (`environments/prod.yaml` on prod), the deploy fills each interface's interface.yaml in with the old values and the new ones and compares them. An interface whose filled-in settings differ is changed by the same rules as an edit of interface.yaml: `port: ${MLLP_PORT}` with a new value moves the port in place (the answer says `source (MLLP_PORT)`), `retention: { days: ${DAYS} }` restarts the interface alone. An interface whose code names the variable as text (`env("EMPI_URL")`) is loaded again between messages (`code reads EMPI_URL`), so a value it kept after its first read is read again. Every other interface isn't touched, even one that names the variable where its value didn't change anything. From the deploy on, `env()` returns the new values in every interface, and a new `console:` applies to the next line logged. The answer lists the environment file's changes (`· environments/prod.yaml: MLLP_PORT "6661" → "6666"`) and each interface they reach, with its values. Its code version doesn't change (a version is the files as written, the same in every environment), so the interface's history shows the deployment as "deployed new values: MLLP_PORT "6661" → "6666" in place", and `ductus history --source` / `--destination` show it under the parts the values reach. Values are recorded as written: put nothing secret in variables (that's what `${secret:NAME}` is for). Secrets aren't compared: a change in `secrets/<env>.json` takes the handover. Another environment's file (`environments/test.yaml` on prod) changes nothing and goes in place. A restart in folder mode records no values (it has nothing to compare with).
- **Why:** variables are how one project runs everywhere, so a host or port that differs per environment belongs in one, and moving it shouldn't cost every interface a pause. Decrypting secrets to plan a deploy would put them in memory for nothing; they change rarely.
- **What to do:** read the answer's `·` lines before deploying with a changed variable: they name every interface it reaches. Code that builds a variable's name at run time (`env("PORT_" + site)`) isn't found by name: its next `env()` call sees the new value, but a value it kept isn't read again until its code changes or the engine restarts; name variables as plain strings. `env()` at a module's top level fails `ductus release` (there are no services while a release loads code): read variables inside functions.

## A deploy in place is all or nothing (level 2)
- **What:** a deploy in place applies every changed interface at once. If one can't be applied (its new interface.yaml doesn't load, or its code doesn't load on one of its threads), the ones already applied are put back on the code they ran (one restarted alone is restarted again on its old settings, lanes it added and stored nothing in taken back), and the deploy goes by the handover instead (the answer's steps say why); with `--in-place-only` it's refused (500) and everything runs as it did. A destination added and then put back this way had its waiting messages queued for it and then filtered, as a removed destination's are.
- **Why:** an engine runs one release, never part of one: what runs is always what one deployment recorded.
- **What to do:** nothing usually: the gate already loaded the code. If the steps show a put-back, read the error they name.

## A deploy in place pauses the changed interface while its code loads (level 3)
- **What:** each changed interface stops between two messages on each of its threads, its new code loads into that thread's isolate (about a millisecond for an interface's code), and its new workers start. While the code loads, nothing else runs code on that thread: the other interfaces sharing it wait that millisecond too (their calls in flight go on, and the load doesn't wait for them). Its new workers then wait for the new code version to be saved (milliseconds) before saving their first decision. Code with top-level `await` makes the load wait for it, counted against the interface's `timeout`. Code an interface no longer runs stays in its isolates' memory until the next handover or restart (measured at 1,001 interfaces: about 130 KB a deploy of one interface once settled, 36 MB over 100 deploys).
- **Why:** V8 runs one thing at a time on a thread and loads code between tasks; a module once loaded can't be unloaded.
- **What to do:** nothing for most deploys. Keep slow work out of a module's top level (do it in the transform, or cache it on first use): it holds every interface on the thread while the module loads. An engine deployed in place hundreds of times between restarts: hand it over (`sudo ductus handover`; a `systemctl reload` goes in place since 0.7.5.3) in a quiet hour now and then to give that memory back.

## Where a release went, and its branch, are labels in its file, not proof (level 2)
- **What:** an environment with DUCTUS_DEPLOY_REQUIRES reads where a release was deployed from the record its file carries (written by `ductus deploy` into the file it deployed, and by `GET /releases/{id}/file`, which `ductus deploy --from` fetches) and from its own database's deployments. DUCTUS_DEPLOY_BRANCHES reads the branch the release records. Both are fields of the manifest, outside the release id and unsigned: anyone holding the file can edit them, and the release keeps its id. An engine whose environment happens to be named `test` writes a record like any other.
- **Why:** test and prod have separate databases, so prod can only learn about test from what it's given; signing releases is a later step.
- **What to do:** treat the rules as a guard against mistakes, not against someone determined. What keeps work that isn't in `main` out of production is who can deploy there: CI building releases from `main` and holding the only tokens with the `deploy` permission on test and prod. Give people tokens without `deploy` on those engines.

## An environment's rules aren't skipped by `--force`; a rollback isn't held to them (level 2)
- **What:** a deploy refused by DUCTUS_DEPLOY_REQUIRES or DUCTUS_DEPLOY_BRANCHES (409, before the gate runs) stays refused with `--force`, which only concerns the "replaces" check (someone else's work). A rollback (`ductus deploy --rollback`) is never held to them: the release ran in that environment before. The report and the audit row (`release.rollback`) say so.
- **Why:** the rules are what the operator decided an environment takes; a person deploying shouldn't be able to waive them in passing. Going back to what ran there yesterday mustn't wait for a test environment.
- **What to do:** to deploy outside the rules on purpose (an emergency fix straight to production), change the setting in ductus.env and reload (`sudo systemctl reload ductus`, or the Windows service's reload: a changed setting hands over): the handover is recorded. Put it back after.

## A rollback brings back the whole project, secrets included, but not the database (level 2)
- **What:** a rollback deploys an earlier release, and a release is the whole project: every interface's code and interface.yaml, `ductus.yaml`, `resources.yaml`, `environments/`, and `secrets/*.json` **as they were then** (a secret rotated in the later release comes back with its old value). It doesn't change the engine's own settings (ductus.env, `DUCTUS_*`, the secret key), the binary, or the database: migrations come with the binary, never with a release, so a rollback runs none (the schema only grows, and the earlier release runs on it as the gate checked). What the later release did stays done: messages it sent stay sent.
- **Why:** a release is one exact, checked artifact; going back means running that artifact again, not reversing each change.
- **What to do:** after rotating a secret, release again with the new one rather than rolling back over it (or rotate it again after the rollback). A rollback that changes an interface's lanes (`ordering.partitions` went up in the later release) is fine with messages waiting: they're sent first ([nuance](ordering.md#after-a-change-of-ordering-new-messages-of-a-key-wait-for-its-older-ones-level-4)).

## A destination a rollback brings back doesn't get what waited while it was gone (level 3)
- **What:** when a release removed a destination, the deliveries waiting for it were filtered when that release was applied, at its start or in place ([nuance](destinations.md#adding-removing-or-renaming-a-destination-level-3)). Rolling back to a release that has the destination brings it back for new messages, under its old id: its pause, counts and history come back with it; the filtered deliveries stay filtered.
- **Why:** filtering is a decision recorded per delivery; a rollback doesn't rewrite what was decided while it wasn't there.
- **What to do:** find them in the message view (status filtered, that destination, the time between the two deploys) and resend them, or replay them.

## The default rollback skips releases a rollback left (level 2)
- **What:** `ductus deploy --rollback` without a release goes to the last release run in that environment before the current one, **skipping any release that a rollback left**. After A → B → rollback (back to A), the next `--rollback` goes to the release before A, not back to B. Only releases that ran in that environment can be rolled back to; any other is refused (409) with "deploy it". Restarts don't count as runs.
- **Why:** a rollback says "that release was bad"; a second rollback toggling back to it would undo the first.
- **What to do:** to go back to a release a rollback left (it was fine after all), deploy it by its id: `ductus deploy <id>` (held to the environment's rules, like any deploy).

## A release made on a detached HEAD records no branch (level 2)
- **What:** `ductus release` records the branch HEAD is on. CI often checks out a commit, not a branch (a tag, a pull request): HEAD is detached and the release records none, which DUCTUS_DEPLOY_BRANCHES refuses. `--branch NAME` names it then; on a branch, a different name is refused.
- **Why:** git doesn't know which branch a detached commit "belongs to" (it can be on several).
- **What to do:** in CI, `ductus release --branch "$GITHUB_REF_NAME"` (GitHub Actions; other CI systems have a variable for the branch built).

## A deploy from the Releases page waits for the gate and the handover (level 1)
- **What:** **Deploy** and **Roll back** on the Releases page wait for the engine's answer: the gate (seconds at a thousand interfaces, ~1 s when a check is reused), then the release applied, in place (milliseconds) or by the handover. After a handover the engine that answered is the one being replaced; the new one takes the same port, so the page goes on (sessions are in the database: nobody is signed out), its live updates reconnect and every screen is fetched again from the new engine. One deploy or check at a time per engine: a second gets 409 until the first ends.
- **Why:** the page shows the engine's own report (deployed, refused and why, or the gate's problems) rather than "started"; at these times a wait is simpler and clearer than polling.
- **What to do:** leave the dialog open until it answers. Closing the tab doesn't stop a deploy that started: look at **What ran here** or the audit log (`release.deploy`) for how it ended.

## What a release changes here is worked out from code versions, not checked (level 2)
- **What:** a release's page says which interfaces it changes, adds or removes in this environment by comparing its code versions with what this engine runs, and whether the project's own files (`ductus.yaml`, `resources.yaml`, `environments/`, `secrets/`) differ from the running release's. In release mode it also says whether a deploy would go in place or need the handover, and why, from the changed interfaces' interface.yaml files in the two stored releases; one case shows only when the deploy applies (an interface whose lanes are still changing after an `ordering` change takes a destination change by the handover). Nothing runs to say it: the gate (**Check first**, **Check against prod**) is what tells whether it works here. A change to an environment's values outside the release (ductus.env) shows nowhere. In folder mode, or while the engine's start is still being recorded, the project files' line and the whole section may be missing.
- **Why:** it's free (no gate, microseconds), so the page can say it before anyone asks.
- **What to do:** read it as "what would move"; run the check before deploying anything that matters.

## The `download` permission reads every release's code and encrypted secrets (level 2)
- **What:** `download` lets a token fetch any stored release's file (`GET /releases/{id}/file`) and nothing else: no deploy, no check, no upload. Any role may hold it (it's meant for a viewer token that another engine pulls with, `DUCTUS_PROMOTE_FROM_TOKEN`). The file carries the project's code and every environment's secrets, encrypted with each environment's own key. Directory groups don't grant it.
- **Why:** prod pulling from test needs a key to test that can't change test; `deploy` would be more than it needs.
- **What to do:** keep the token where the database's password is (ductus.env, readable by the service only). Each download is in the audit log (`release.download`, with who). Don't give `download` to people: they get files from the Releases page with `deploy`.

## Pulling from another engine trusts the system's CAs only (level 2)
- **What:** prod's engine calls test's (`DUCTUS_PROMOTE_FROM`) over HTTPS verified against the server's trusted CAs, as `ductus deploy --from` does; resources.yaml's certificates aren't used (they're the release's, and the release is what's being fetched). Plain `http://` works and sends the token in the clear.
- **Why:** the engine's own settings shouldn't depend on what a release carries.
- **What to do:** with a private CA, add it to the server's trust store (Linux: `/usr/local/share/ca-certificates` and `update-ca-certificates`; Windows: the machine's Trusted Root store). Use `http://` only on a loopback or a network you'd send the database password over.
