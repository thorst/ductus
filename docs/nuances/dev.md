# Nuances: local development

What could surprise you here, why it is so, and what to do. Each entry has a level, 1 (day one) to 5 (expert): the [index](index.md) lists them all by level.

## `ductus dev` is a development tool, not a way to run in production (level 1)
- **What:** `ductus dev` starts a Postgres of its own for the project (data in `.ductus/postgres`, one engine at a time per project) and runs the engine against it. It ignores `DUCTUS_DATABASE_URL`, uses default Postgres settings except `fsync`, which is off (the library that runs it starts Postgres that way: writes aren't flushed, so a crash of the machine, not of the engine, can corrupt its data; `ductus doctor` against it says `DOC001`), and nobody backs the data up. Postgres is downloaded once per user (about 30 MB).
- **Why:** to try an interface without asking anyone for a database. Production needs the DBA's Postgres (backups, monitoring, failover), and a message the engine has acknowledged must survive what the DBA protects against.
- **What to do:** use `ductus dev` on your own machine; everywhere else set `DUCTUS_DATABASE_URL` and use `ductus run`. Without a download possible, unpack the Postgres binaries yourself and set `DUCTUS_POSTGRES_DIR`. `ductus dev --reset` throws the dev data away, which is also the way back after a power cut leaves dev's Postgres refusing to start. Numbers from `ductus bench` against dev's Postgres aren't a server's: bench a Postgres with `fsync` on.

## `ductus dev` reloads in place only (level 1)
- **What:** a running `ductus dev` applies the project folder when asked (`ductus reload` in the project's folder, or VS Code's **Deploy to dev**): the interfaces whose code or interface.yaml changed take it between two messages, added ones start, removed ones stop, the others never pause. Two kinds of change are refused instead, with nothing changed and a message saying to restart: what only a start reads (ductus.yaml, resources.yaml, docs-schema.yaml, the environment's secrets file), and any change to an interface under `--inspect`. Nothing applies a change by itself: saving a file changes what runs only once you reload (or with VS Code's `ductus.deployToDevOnSave`).
- **Why:** a server's engine applies those by the handover, a new engine started beside it, and `ductus dev` can't start a second engine on its own Postgres, debugger and lock. An interface under the debugger loads its new code on its debugging thread, which waits while you're paused at a breakpoint: the reload would wait with it.
- **What to do:** after changing ductus.yaml or resources.yaml, Ctrl-C and `ductus dev` again (it starts in well under a second). To run new code of an interface you're debugging, stop the debug session and start it again ("Ductus: debug this interface" restarts `ductus dev --inspect`).

## Your editor's help is the installed version's: run `ductus types` after an upgrade (level 1)
- **What:** completion, descriptions on hover and underlined mistakes in interface.yaml, resources.yaml and ductus.yaml come from the JSON Schemas `ductus types` writes into `.ductus/schema/` (with the SDK's typings in `.ductus/types/`), and those come from the `ductus` that wrote them. After an upgrade, a new setting is underlined as unknown and its description is missing until they're written again; on a laptop with an older `ductus` than the servers, the editor describes the older one. `ductus test` and `ductus validate` write them too.
- **Why:** the schemas are made from the engine's own types, so they say exactly what that version accepts, offline (an air-gapped site can't fetch them from a website), with no second copy to drift.
- **What to do:** run `ductus types` (or `test`) after installing a new version; keep developers' `ductus` at the version the servers run. `.ductus/` isn't committed, so each machine writes its own.
